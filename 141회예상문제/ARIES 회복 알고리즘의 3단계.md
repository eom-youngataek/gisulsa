### **ARIES 회복 알고리즘의 3단계**

***

#### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (왜 장애 후 "어디서부터 무엇을" 해야 하는가)
Ⅱ. ARIES 3단계 핵심 동작
Ⅲ. 단계별 비교 및 전제 조건
Ⅳ. 결론
```

포인트: 개요에서 \*\*"앞서 다룬 STEAL·No-Force 정책이 '버퍼 효율과 커밋 성능을 극대화하는 대신 Undo·Redo가 모두 필요해지는 트레이드오프'를 만든다면, ARIES(Algorithm for Recovery and Isolation Exploiting Semantics)는 그 트레이드오프를 WAL 위에서 분석(Analysis)→재실행(Redo)→취소(Undo) 3단계 정밀 수술로 완전히 해소하는 현대 RDBMS 회복의 사실상 표준이다 — 핵심은 단 두 가지: Redo는 '커밋됐든 아니든 로그에 있는 것은 전부 다시 실행', Undo는 '미커밋 트랜잭션의 변경만 역순으로 제거'"\*\*라는 한 줄로 시작하면 전체 맥락이 드러납니다.

***

#### Ⅱ. ARIES 3단계 핵심 동작

**가. 전제 개념**

| 개념         | 내용                               |
| :--------- | :------------------------------- |
| **LSN**    | 로그 레코드 고유 번호·단조 증가 / 모든 판단 기준    |
| **WAL**    | 페이지 디스크 기록 전 로그 먼저 / ARIES 전제 조건 |
| **ATT**    | 장애 시점 활성 트랜잭션 목록                 |
| **DPT**    | 버퍼 수정됐으나 디스크 미반영 Dirty Page 목록   |
| **RecLSN** | DPT 내 각 페이지의 첫 수정 LSN / Redo 시작점 |

***

**나. 3단계 핵심 동작**

| **핵심 척도** | **📊 1단계: 분석 (Analysis) 🚨**                        | **🔑 2단계: 재실행 (Redo) 🚨**                             | **🏁 3단계: 취소 (Undo) 💯**             |
| :-------- | :-------------------------------------------------- | :---------------------------------------------------- | :----------------------------------- |
| **시작점**   | **마지막 체크포인트 LSN**                                   | **DPT 내 최소 RecLSN**                                   | Redo 완료 직후                           |
| **방향**    | 로그 **순방향** (체크포인트→장애)                               | 로그 **순방향** (RecLSN→장애)                                | 로그 **역방향** (장애→트랜잭션 시작)              |
| **핵심 작업** | ATT 갱신(Begin→추가·Commit→제거) DPT 갱신(수정 페이지·RecLSN 기록) | **모든 로그 무조건 재실행** (커밋·미커밋 구분 없음) pageLSN≥로그LSN이면 Skip | **ATT 내 미커밋만** CLR(보상 로그) 기록하며 역순 취소 |
| **산출물**   | 장애 시점 ATT·DPT 확정 → Redo 시작점 결정                      | 장애 직전 DB 상태 완전 복원                                     | ACID 원자성 보장 / 미커밋 변경 전부 제거           |

***

#### Ⅲ. 단계별 비교 및 전제 조건

**가. ARIES 전체 흐름 도식화**

```
[로그 타임라인]

LSN: 100     200     300     400     500     600     700
     │       │       │       │       │       │       │
     CKPT   T1     T2      T1      T2      T3    CRASH
           Begin  Begin   Write  Commit  Begin    ↑
                          T1-P1                 장애

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
①분석 (LSN=100 → LSN=700 순방향)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ATT 확정: T1(미커밋)·T3(미커밋)
            T2는 Commit 확인 → ATT 제거
  DPT 확정: P1 (RecLSN=300)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
②재실행 (RecLSN=300 → LSN=700 순방향)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  LSN=300: T1-P1 재실행
  LSN=400: T2-Commit 재실행
  LSN=600: T3-Begin 재실행
  → 장애 직전 상태 완전 복원 ✅

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
③취소 (ATT: T1·T3 역방향)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  T3: LSN=600 취소 → CLR 기록
  T1: LSN=300 취소 → CLR 기록
  → 미커밋 변경 없던 일로 ✅

[최종 결과]
  T2: Commit → 데이터 영구 반영 ✅
  T1·T3: Abort → 변경 전부 제거 ✅
```

***

**나. 핵심 구분 암기표**

| 구분           | Redo 대상                          | Undo 대상            |
| :----------- | :------------------------------- | :----------------- |
| **커밋 트랜잭션**  | ✅ Redo (No-Force 때문에 디스크 미반영 가능) | ❌ Undo 안 함         |
| **미커밋 트랜잭션** | ✅ Redo (일단 전부 복원)                | ✅ Undo (원자성 보장)    |
| **핵심 원칙**    | **"로그에 있으면 전부 Redo"**            | **"미커밋만 역순 Undo"** |

→ 암기: **"Redo는 가리지 않고 전부, Undo는 미커밋만 역순으로"**

***

**(제언)** "ARIES는 Steal·No-Force 정책의 자유도를 WAL과 3단계 회복으로 완전히 보상하는 현대 RDBMS 회복의 표준입니다. **분산 DB·클라우드 환경에서는 체크포인트 대신 앞서 다룬 Raft 합의 로그와 결합한 분산 ARIES 변형이 CockroachDB·TiDB에서 구현되며, RTO 목표에 따라 체크포인트 주기와 로그 버퍼 크기를 함께 최적화하는 것이 회복 성능 튜닝의 핵심입니다.**"
