### Ⅱ. RM 스케줄링 원리 — "주기가 짧을수록 급하다"

| 개념                            | 내용                                                       |
| :---------------------------- | :------------------------------------------------------- |
| **정적 우선순위** (Static Priority) | 각 태스크의 우선순위는 **실행 전에 미리 고정**(런타임 중 안 바뀜)                 |
| **우선순위 결정규칙**                 | **주기(Period)가 짧을수록 우선순위 높음** — 자주 와야 하는 일이 더 급하다는 논리     |
| **선점형(Preemptive)**           | 더 급한(주기짧은) 태스크가 오면, 실행중이던 낮은우선순위 태스크를 **즉시 중단시키고 먼저 처리** |

→ 암기: **"자주 와야 하는 일이 늦으면 큰일나니까, 자주 오는 일부터 처리한다"** — 예를 들어 심장박동기(10ms마다 반드시)와 화면갱신(100ms마다)이 동시에 필요하면, **10ms 주기 태스크가 항상 우선**입니다.

### 도식화 제안

```
Task A (주기 10ms) ████──████──████──████  ← 우선순위 최고
Task B (주기 20ms) ──██──██──██──██──██   ← 중간
Task C (주기 50ms) ────────█──────────█    ← 최저

시간축: A가 도착하면 B,C를 선점(중단)하고 즉시 처리
```

→ "짧은 주기(잦은 요청)일수록 위쪽(우선순위 높음)"이라는 계단식 배치가 RM의 핵심 시각화입니다.

### Ⅲ. 스케줄가능성 검증 — Liu & Layland 공식 (계산문제 대비 필수)

**함정 방지: RM 규칙만 알면 절반. "이 태스크들을 다 처리할 수 있는지"를 검증하는 공식까지 가야 완성됩니다.**

```
U = Σ(Ci/Ti) ≤ n(2^(1/n) - 1)
```

| 변수     | 의미                              |
| :----- | :------------------------------ |
| **Ci** | 태스크i의 실행시간(Computation time)    |
| **Ti** | 태스크i의 주기(Period)                |
| **U**  | 전체 CPU **이용률**(모든 태스크의 Ci/Ti 합) |
| **n**  | 태스크 개수                          |

**주요 상한값 (외워두면 편함)**

| n  | 상한값 n(2^(1/n)-1)          |
| :- | :------------------------ |
| 1  | 100%                      |
| 2  | 약 **82.8%**               |
| 3  | 약 78.0%                   |
| ∞  | **약 69.3%**(ln2) — 최종 수렴값 |

→ 암기: **"태스크가 늘어날수록 안전마진(상한선)이 낮아져서 결국 69.3%로 수렴한다"** — 이 말은 **CPU를 100% 다 쓸 수 없고, 이론상 최대 69.3%까지만 안전하게 쓸 수 있다**는 RM의 근본적 한계입니다.

**계산예시**

> Task1(C=1,T=4), Task2(C=2,T=6) → U = 1/4+2/6 = 0.25+0.33 = 0.58\
> n=2 상한값 0.828 > 0.58 → **스케줄가능**

### Ⅳ. RM vs EDF 비교 — 핵심 변별력

| 구분            | **RM** (Rate Monotonic)                     | **EDF** (Earliest Deadline First) |
| :------------ | :------------------------------------------ | :-------------------------------- |
| **우선순위**      | **정적**(주기 기준, 고정)                           | **동적**(마감시한이 가까울수록 우선, 실행중 계속 변함) |
| **CPU이용률 한계** | **약 69.3%**(태스크多 시)                         | **100%**(이론상 최대활용 가능)             |
| **구현복잡도**     | **단순**(우선순위 고정, 오버헤드 적음)                    | 복잡(매번 재계산 필요)                     |
| **실무적용**      | **VxWorks 등 실제 RTOS에서 널리 사용**(예측가능성·단순함 선호) | 이론적으로 우수하나 오버헤드로 실무적용 제한적         |

→ 암기: **"RM은 단순하고 예측가능하지만 69%가 한계, EDF는 이론상 100%까지 쓰지만 복잡하다"** — 앞서 다룬 "FIFO vs LRU"(단순함 vs 최적성)와 같은 트레이드오프 구조가 여기서도 반복됩니다.

### Ⅴ. 결론 포인트 (오늘 시리즈 총연결)

RM의 본질은 \*\*"미래를 예측할 수 없는 동적 상황에서도, 미리 정해둔 단순한 규칙(주기 기준)만으로 안전하게 마감시한을 지킬 수 있는가"\*\*의 문제이며, 이는 앞서 다룬 SQMS/MQMS의 "평균효율 vs 예측가능성" 트레이드오프, 그리고 페이지교체알고리즘의 "OPT(이상적,불가능) vs LRU(근사,실용적)" 구조와 동일한 설계철학입니다 — **완벽한 최적해(EDF/OPT)보다 단순하고 예측가능한 근사해(RM/LRU)가 실무에서 선호되는 경우가 많다**는 결론으로 마무리하면, 오늘 다룬 스케줄링/자원배분 계열 답안들이 하나로 연결됩니다.

### **1. 답안 전개 스토리 (머릿속 핵심 흐름)**

> "비행기나 자동차 제어에 들어가는 실시간 운영체제(RTOS)는 속도가 빠른 게 중요한 게 아니라, 무슨 일이 있어도 '정해진 시간(데드라인) 안에 무조건 끝내는 것'이 생명이다. 이를 보장하기 위해 산업계에서 가장 널리 쓰이는 스케줄러가 바로 \*\*'Rate Monotonic(RM)'\*\*이다. RM의 철학은 아주 단순하고 직관적이다. '자주 발생하는 놈(주기가 가장 짧은 태스크)이 가장 급한 놈이니, 무조건 제일 높은 우선순위를 주자!'는 것이다. 프로그램 실행 전에 우선순위를 딱 박아두고(정적 할당) 선점형으로 뺏기 때문에, 스케줄러가 복잡하게 머리를 굴릴 필요가 없어 시스템 안정성과 예측 가능성이 최고다. 하지만 치명적 단점이 있다. '주기'만 보고 맹목적으로 순위를 주다 보니, CPU를 100% 꽉 채워서 쓸 수가 없다. 프로세스가 많아질수록 CPU 활용률 상한선이 대략 \*\*69.3%\*\*로 수렴해버린다. 그럼에도 불구하고 특유의 단순함과 엄청난 안정성 때문에, 69.3%의 한계는 그냥 CPU 성능을 빵빵하게 더 넣어주는 방식으로 무마하며 현업 최고의 스케줄링 기법으로 군림하고 있다."

### **2. 실제 답안에 쓸 핵심 내용 (암기용)**

#### **I. \[도입] 데드라인 엄수의 절대 표준, RTOS와 RM 스케줄링 개요**

* **정의:** 하드 리얼타임(Hard Real-time) 시스템에서, \*\*'주기(Period)가 가장 짧은 태스크(자주 발생하는 작업)에 가장 높은 우선순위를 고정적으로 부여'\*\*하는 **정적(Static) 우선순위 선점형** 스케줄링 알고리즘.
* **전제 조건:** 모든 태스크는 반복적인 주기(Periodic)를 가지며, 태스크의 마감 시간(Deadline)은 해당 태스크의 주기와 같다고 가정함.

#### **II. \[본론 1] Rate Monotonic(RM) 알고리즘의 동작 원리와 철학**

* **동작 원리:**
  * Task A의 주기 = 20ms, Task B의 주기 = 50ms라면, **주기가 짧은 A에게 무조건 더 높은 우선순위**를 부여함.
  * Task B가 실행 중이더라도, 주기가 짧은 Task A가 발생하면 즉시 CPU를 빼앗는 **'선점(Preemption)'** 방식.
* **장점 (왜 현업 표준인가?):** 실행하기 전에 우선순위가 이미 결정되어 있으므로(정적), OS가 중간중간 스케줄링을 계산하느라 발생하는 **오버헤드가 극도로 적으며, 동작 예측(Predictability)이 매우 완벽함.**

#### **III. \[본론 2] RM 스케줄링의 치명적 한계: 69.3% 상한선 법칙 (출제 1순위)**

RM 알고리즘은 CPU를 100% 활용하지 못한다는 수학적 한계가 있습니다. 이 공식을 답안에 쓰면 엄청난 차별화가 됩니다.

* **상한선 공식 (Upper Bound):** U=∑i=1n(Ci/Ti)≤n(21/n−1)*U*=∑*i*=1*n*​(*Ci*​/*Ti*​)≤*n*(21/*n*−1)
  * (C = 실행시간, T = 주기, n = 프로세스 개수)
* **의미:** 위 공식에 따라 태스크 개수(n)가 무한대로 커지면, **CPU 최대 활용률(Utilization)은 약 69.3% (ln2*ln*2)에 수렴**하게 됩니다. 즉, CPU를 69.3%까지만 써야 모든 데드라인을 100% 안전하게 지킬 수 있으며, 이를 넘어가면 스케줄링 실패(데드라인 오버)가 발생할 수 있습니다.

#### **IV. \[결론/제언] RM(정적) vs EDF(동적) 스케줄링의 융합 제언**

* **(키워드 위주 2줄 마무리)** "RM은 69.3%라는 CPU 활용률의 한계가 있지만 완벽한 안정성을 자랑합니다. 반대로 동적 스케줄링인 **EDF(Earliest Deadline First) 알고리즘**은 가장 마감 시간이 임박한 작업에 유동적으로 순위를 주어 CPU를 100% 쓸 수 있지만 오버헤드가 큽니다. 따라서 최신 자율주행 및 항공 임베디드 시스템은, 핵심 생명 유지 코어에는 안전한 **RM**을 배치하고, 인포테인먼트 등 비핵심 자원에는 활용률이 높은 **EDF**를 혼합하는 하이브리드 RTOS 아키텍처를 지향해야 합니다."
