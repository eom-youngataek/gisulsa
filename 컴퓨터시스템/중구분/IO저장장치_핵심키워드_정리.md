# I/O 및 저장장치 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 방식 분류 → 동작원리 → 비교

---

## 1. DMA (Cycle Stealing / Transparent, SG-DMA / RDMA)

**방식 분류**: CPU 개입없이 I/O장치와 메모리가 직접 데이터를 주고받는 전송방식. **버스점유방식**과 **활용형태**에 따라 세분화

**동작원리**
```
[일반 DMA 동작] CPU가 DMA컨트롤러에 전송정보(시작주소,길이등) 설정 → DMA컨트롤러가 
   메모리-I/O장치간 데이터를 직접전송(CPU는 그동안 다른작업수행) → 전송완료시 인터럽트로 CPU에 통지

[Cycle Stealing 방식] DMA가 버스를 "한 사이클씩 몰래 빌려서" 사용(CPU와 번갈아 버스점유)
   → CPU동작을 완전히 멈추지 않고 약간씩 느려지게만 함(시분할적 자원공유)

[Transparent 방식] DMA가 CPU가 버스를 사용하지 않는 유휴시점(Idle Cycle)에만 전송수행
   → CPU성능에 전혀 영향없음(가장 이상적이나 유휴시간이 부족하면 전송지연)

[SG-DMA(Scatter-Gather DMA)] 메모리상 흩어진(비연속) 여러 영역을 한번의 DMA설정으로 
   모아서(Gather) 전송하거나 분산해서(Scatter) 쓰기 가능 → 복사오버헤드 감소

[RDMA(Remote DMA)] 네트워크로 연결된 **원격서버의 메모리**에 직접 접근(상대방CPU 개입없이)
   → 네트워크스택 오버헤드를 우회해 초저지연 데이터전송
```

**비교**

| 구분 | Programmed I/O | 일반DMA | SG-DMA | RDMA |
|---|---|---|---|---|
| CPU개입도 | 매우높음(매바이트마다 CPU대기) | 낮음(설정만, 전송은 자동) | 낮음 | 거의없음(상대서버CPU도 미개입) |
| 적용범위 | 로컬 단일전송 | 로컬 연속메모리 | 로컬 비연속메모리 | **네트워크 너머 원격메모리** |
| 대표활용 | 구형/단순장치 | 일반디스크I/O | 네트워크패킷처리(흩어진버퍼) | 고성능컴퓨팅(HPC), AI클러스터간 통신 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 인터럽트(Vector방식) | DMA전송완료를 CPU에 알리는 메커니즘(이전파일과 연결) |
| 버스중재 | DMA컨트롤러도 버스사용권을 얻어야해 버스중재 메커니즘의 적용대상(이전파일과 연결) |
| CXL / RDMA | RDMA가 메모리시스템 도메인의 CXL.memory(원격메모리 직접접근)와 유사한 발상을 네트워크로 확장 |

## 2. RAID (0+1 vs 1+0)

**방식 분류**: 여러 디스크를 묶어 성능향상(스트라이핑) 또는 안정성향상(미러링)을 동시에 추구하는 RAID 0(스트라이핑)과 RAID 1(미러링)의 **결합순서에 따른 2가지 하이브리드**

**동작원리**
```
[RAID 0+1] 먼저 스트라이핑(0)으로 2개의 스트라이프 그룹생성 → 그 2개 그룹을 미러링(1)
   디스크1,2(스트라이프A) ←미러링→ 디스크3,4(스트라이프B)
   → 한쪽 그룹(A)에서 디스크1개 장애시, 전체 스트라이프그룹A가 손상된 것으로 간주
   → 미러링된 그룹B 전체에 의존(이미 디스크1개만 더 죽으면 그룹A 데이터 전체손실 위험 — 더 취약)

[RAID 1+0] 먼저 미러링(1)으로 디스크쌍을 만들고 → 그 미러쌍들을 스트라이핑(0)
   디스크1↔디스크2(미러쌍A), 디스크3↔디스크4(미러쌍B) → A,B를 스트라이핑
   → 디스크1 장애시, 미러쌍A의 디스크2만 살아있으면 데이터유지(다른 미러쌍은 전혀영향없음)
   → 더 많은 디스크장애에도 견딜수있는 구조(더 안정적)
```

**비교**

| 구분 | RAID 0+1 | RAID 1+0(권장) |
|---|---|---|
| 구성순서 | 스트라이핑 먼저, 미러링 나중 | 미러링 먼저, 스트라이핑 나중 |
| 장애내성 | 낮음(한 그룹내 1개고장도 그룹전체위험확대) | **높음**(미러쌍 단위로 격리되어 더많은 동시고장 견딤) |
| 재구성(Rebuild) 시 부담 | 그룹전체를 재동기화해야함(부담큼) | 해당 미러쌍만 재동기화(부담적음) |
| 실무권장 | 비권장 | **권장**(대부분 RAID컨트롤러의 표준선택) |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 메모리인터리빙 | RAID의 스트라이핑과 동일한 "분산저장으로 병렬성능 확보" 사상(메모리시스템 도메인과 연결) |
| 고가용성(HA) / 고장허용시스템(FTS) | RAID 1+0이 실제로 구현하는 디스크레벨 고가용성 사례(경영정보시스템 도메인과 연결) |
| 스토리지가상화 | RAID로 구성된 물리디스크풀을 가상화계층이 다시 추상화하는 상위계층(컴퓨터구조 이전파일과 연결) |

## 3. 플래시메모리 FTL (Flash Translation Layer)

**방식 분류**: SSD 내부에서 "논리주소(OS가 사용)"와 "물리주소(실제 플래시셀 위치)"를 매핑·관리하는 펌웨어계층

**동작원리**
```
[문제] 플래시메모리는 ①덮어쓰기 불가(반드시 지우고(Erase) 다시써야함)
       ②지우기는 블록단위(쓰기는 페이지단위보다 큰 단위로만 가능)
       ③쓰기/지우기 횟수에 마모한계 존재(수천~수만회)

[FTL의 역할]
①주소매핑: 논리주소(LBA)→물리주소(PBA) 매핑테이블 관리(매번 다른 물리위치에 쓰기, Out-of-place Update)
②웨어레벨링(Wear Leveling): 특정셀만 집중적으로 마모되지않도록 쓰기작업을 전체블록에 균등분산
③가비지컬렉션: 더이상 유효하지않은(논리적으로 삭제된) 데이터가 있는 블록을 모아 지우고 재활용
④배드블록관리: 마모로 사용불가해진 블록을 식별해 매핑에서 제외
```

**비교(HDD와 비교)**

| 구분 | HDD | SSD(FTL) |
|---|---|---|
| 데이터수정 | 해당위치 직접덮어쓰기 가능 | 새위치에 쓰고 기존데이터는 무효표시(Out-of-place) |
| 단편화 영향 | 물리적 헤드이동 비효율(디스크조각화 영향큼) | FTL이 내부적으로 처리(TRIM명령으로 효율화) |
| 핵심관리기법 | 디스크최적화(디프래그) | 웨어레벨링, 가비지컬렉션 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 파일슬랙 / 디지털포렌식 | SSD는 TRIM명령으로 슬랙데이터가 빠르게 실제삭제되어, HDD보다 포렌식복구 가능성이 낮은 차이점(보안 도메인과 연결) |
| ROM 종류(Flash) | FTL이 관리하는 Flash메모리 자체의 계층적 발전과정(메모리시스템 도메인과 연결) |
| 단편화(내부/외부) | 가비지컬렉션이 처리하는 "무효데이터로 인한 공간낭비"가 단편화와 유사한 문제의식(이전파일과 연결) |

## 4. 맨체스터 코딩 (Manchester Coding)

**방식 분류**: 디지털데이터(0/1)를 전송할 때, 클럭정보까지 신호자체에 함께 포함시키는 **자기동기화(Self-clocking)** 인코딩 방식

**동작원리**
```
[기본 맨체스터 인코딩 규칙]
0 → 신호가 "하이→로우"로 전환(하강엣지)
1 → 신호가 "로우→하이"로 전환(상승엣지)
(매 비트 중간에 반드시 신호전환이 발생 → 수신측이 이 전환을 보고 클럭을 자동으로 동기화)

[차등 맨체스터 코딩(Differential Manchester)]
비트값을 "전환방향"이 아니라 "비트시작시점에 전환이 있는지 없는지"로 판단
0 → 비트시작시 신호전환 있음
1 → 비트시작시 신호전환 없음
(이전비트값과 무관하게 판단가능, 신호의 극성(+/-)이 반전되어도 정상해독 가능 → 더 강건함)
```

**비교**

| 구분 | 일반 맨체스터 | 차등 맨체스터 |
|---|---|---|
| 비트판별기준 | 신호전환의 "방향"(상승/하강) | 비트시작시 "전환유무"(이전비트 무관) |
| 극성반전 영향 | 영향받음(극성반전시 0/1해석이 뒤바뀜) | **영향없음**(극성에 무관하게 판별가능) |
| 활용 | 이더넷(10BASE-T) | 토큰링(Token Ring) |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| NRZ(Non-Return-to-Zero) | 맨체스터코딩과 대조되는, 클럭정보없이 단순 레벨로만 표현하는 기본 인코딩방식 |
| 샤논정리/채널코딩 | 인코딩방식 선택이 신호의 신뢰성·효율성에 영향을 주는 통신이론적 배경(네트워크 도메인과 연결) |
| 이더넷(IEEE 802.3) | 맨체스터코딩이 실제로 사용되는 표준 프로토콜(네트워크 도메인과 연결) |

## 5. 이진트리 순회 (전위/중위/후위, 계산형 — 126회 기출패턴)

**방식 분류(3가지 순회방식)**

| 방식 | 방문순서 | 활용 |
|---|---|---|
| **전위순회(Preorder)** | 루트→왼쪽서브트리→오른쪽서브트리 | 트리구조 복사·직렬화 |
| **중위순회(Inorder)** | 왼쪽서브트리→루트→오른쪽서브트리 | 이진탐색트리에서 **정렬된순서** 출력 |
| **후위순회(Postorder)** | 왼쪽서브트리→오른쪽서브트리→루트 | 트리삭제, 수식트리의 후위표기변환 |

**동작원리 및 실제 계산(예시 트리)**
```
            A
          /   \
         B     C
        / \      \
       D   E      F
```

**전위순회(루트→좌→우)**: A → (B서브트리: B→D→E) → (C서브트리: C→F)
**→ 결과: A, B, D, E, C, F**

**중위순회(좌→루트→우)**: (D→B→E) → A → (C→F)
**→ 결과: D, B, E, A, C, F**

**후위순회(좌→우→루트)**: (D→E→B) → (F→C) → A
**→ 결과: D, E, B, F, C, A**

**비교**: 전위순회는 항상 "루트가 첫번째"로 출력, 후위순회는 항상 "루트가 마지막"으로 출력, 중위순회는 루트가 가운데 어딘가에 위치(좌측서브트리 노드수만큼 뒤에 등장) — 이 패턴으로 순회결과만 보고도 루트위치를 역추적 가능

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 이진탐색트리(BST) | 중위순회시 항상 정렬된 결과가 나오는 트리구조(라우팅테이블탐색과 연관해 출제됨) |
| 위상정렬(Topological Sort) | 트리가 아닌 일반 방향그래프(DAG)에서의 순서결정 알고리즘(다른 도메인 계산형 문제와 연결) |
| 다차원색인구조(R-Tree 등) | 트리순회 개념이 데이터베이스의 색인탐색에도 동일하게 적용(DB도메인과 연결) |

## 6. Canary Test (배포검증)

**방식 분류**: 신규버전을 **소수의 실제사용자(또는 소수서버)**에게만 먼저 노출시켜 문제유무를 검증한 후, 점진적으로 전체에 확대배포하는 검증·배포전략(탄광에서 위험가스를 가장먼저 감지하는 카나리아새가 명칭의 유래)

**동작원리**
```
[1단계] 신규버전을 전체트래픽의 5%에만 라우팅(나머지95%는 기존버전 유지)
[2단계] 카나리아 그룹의 에러율·응답시간·핵심지표 모니터링
[3단계] 문제없으면 → 트래픽비율을 점진적으로 확대(5%→25%→50%→100%)
        문제발생하면 → 즉시 카나리아 트래픽을 기존버전으로 롤백(피해범위 최소화)
```

**비교(다른 배포전략과 비교)**

| 구분 | Blue-Green | Rolling | Canary |
|---|---|---|---|
| 전환방식 | 전체를 한번에 전환(스위치) | 서버를 순차적으로 하나씩 교체 | **일부(소수)부터 점진확대** |
| 위험노출범위 | 전환즉시 100%(문제시 빠르게되돌림 가능) | 교체중인 일부서버만 | **가장작음**(최소트래픽만 위험노출) |
| 검증목적 | 빠른전환·롤백 | 무중단 순차교체 | **실사용자 데이터로 안전성 검증** |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 무중단배포(Blue-Green/Rolling) | Canary와 함께 비교되는 배포전략 3종(SW방법론 도메인과 연결) |
| A/B테스팅 | Canary가 "안전성검증" 목적인 반면, A/B테스팅은 "성과비교" 목적으로 유사하나 목적이 다름(생성형AI 도메인과 연결) |
| CI/CD파이프라인 | Canary배포가 실제로 자동화되어 실행되는 파이프라인 단계(SW방법론 도메인과 연결) |

## 7. Split Brain 현상 (클러스터)

**방식 분류**: 클러스터(여러서버 묶음)를 구성하는 노드들 간 **네트워크 연결이 끊겨**, 서로 "상대방이 죽었다"고 잘못판단해 **각자 독립적으로 자신이 마스터(주서버)라고 주장**하게 되는 현상

**동작원리**
```
[정상상태] 마스터노드1 ←하트비트(생존신호)→ 슬레이브노드2 (정상적으로 마스터1개만 존재)

[네트워크단절 발생] 마스터1과 슬레이브2 사이의 통신선로(하트비트용)만 끊김
   (둘다 살아있지만 서로의 생존을 확인못함)
   → 슬레이브2: "마스터1이 응답없네? 죽었나보다 → 내가 새 마스터가 되겠다" (승격)
   → 마스터1: 여전히 자신이 마스터라고 생각하며 정상동작계속
   → 결과: 마스터1, 마스터2(구슬레이브) 동시에 "내가마스터다"하며 각자 다른 데이터를 처리
   → 데이터 불일치·정합성 붕괴(Split Brain)
```

**해결기법(비교)**

| 기법 | 방식 |
|---|---|
| **쿼럼(Quorum)** | 과반수 노드의 동의가 있어야만 마스터로 승격 가능(전체노드 절반이하만 응답하면 승격거부) |
| **STONITH(Shoot The Other Node In The Head)** | 마스터승격 전, 기존마스터로 추정되는 노드를 강제로 전원차단·격리시켜 확실히 죽었는지 보장 |
| **펜싱(Fencing)** | 의심노드를 클러스터에서 네트워크적으로 격리(공유스토리지 접근차단 등) |
| **별도 중재자(Witness/Arbitrator)** | 제3의 독립노드를 두어 분쟁시 누가 마스터인지 최종 결정 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| CAP이론 | Split Brain은 분할(Partition) 상황에서 일관성(C)이 깨지는 대표적 실패사례(DB도메인과 연결) |
| 고가용성(HA) 구성 | Split Brain 방지가 HA클러스터 설계의 핵심 고려사항(경영정보시스템 도메인과 연결) |
| 데드락 vs Starvation | "잘못된 판단으로 인한 시스템 이상상태"라는 점에서 분산시스템버전의 유사문제로 비교가능(이전파일과 연결) |
