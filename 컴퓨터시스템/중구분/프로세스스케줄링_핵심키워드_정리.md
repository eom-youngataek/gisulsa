# 프로세스 스케줄링 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 알고리즘 분류 → 동작원리 → 비교(성능지표)

---

## 1. SQMS vs MQMS (멀티프로세서 스케줄링)

**알고리즘 분류**

| 구분 | SQMS(Single Queue Multiprocessor Scheduling) | MQMS(Multi Queue Multiprocessor Scheduling) |
|---|---|---|
| 큐구조 | 모든 CPU가 **하나의 공유 큐**를 바라봄 | CPU마다 **개별 큐**를 보유 |

**동작원리**
```
[SQMS] 작업대기열(공유큐) → 어느 CPU든 비면 큐 맨앞 작업을 가져가 실행
       (자연스러운 부하분산, 단 큐접근시 락(Lock) 경쟁발생)

[MQMS] CPU1-개별큐1, CPU2-개별큐2, CPU3-개별큐3 ...
       (락경쟁 없음, 단 한쪽 큐만 작업이 몰리면 부하불균형 발생 → 작업이전(Migration)으로 보완)
```

**비교(성능지표)**

| 지표 | SQMS | MQMS |
|---|---|---|
| 부하균형(Load Balancing) | 자동으로 균형(공유큐라서) | 불균형 가능(별도 마이그레이션 필요) |
| 캐시지역성(Cache Affinity) | 낮음(매번 다른CPU에 배정될수있어 캐시재사용 어려움) | 높음(같은CPU에서 반복실행되어 캐시활용 우수) |
| 확장성(코어수 증가시) | 락경쟁 심화로 낮음 | 큐가 독립적이라 높음(대규모 멀티코어에 적합) |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 캐시일관성(MESI) | MQMS의 캐시지역성 장점이 멀티코어 캐시일관성 비용과 직결(메모리시스템 도메인과 연결) |
| 작업이전(Work Stealing) | MQMS의 부하불균형을 해소하는 대표기법(한쪽 큐가 비면 다른 큐에서 작업을 가져옴) |
| 로드밸런서(L4/L7) | 동일한 "여러 처리단위에 작업을 분산"하는 개념이 네트워크 계층에서도 동일하게 적용(네트워크 도메인과 연결) |

## 2. RM (Rate Monotonic) 스케줄링

**알고리즘 분류**: 실시간시스템(Real-Time System)의 **정적우선순위(Static Priority)** 스케줄링 알고리즘 — 우선순위가 한번 정해지면 실행중 바뀌지 않음

**동작원리**
```
[우선순위 규칙] 주기(Period)가 짧은 태스크 = 우선순위 높음 (주기와 우선순위가 반비례)
   예: TaskA(주기10ms) > TaskB(주기20ms) > TaskC(주기50ms) — 우선순위 순서

[스케줄가능성 판단(이용률 검사)] 
   U = Σ(Ci/Ti) ≤ n(2^(1/n) - 1)   (Ci=실행시간, Ti=주기, n=태스크수)
   예: n=2일 때 한계값 = 2(2^0.5-1) ≈ 0.828 → 전체 CPU이용률이 82.8% 이내면 스케줄가능 보장
```

**비교(성능지표 — 동적우선순위 EDF와 비교)**

| 구분 | RM(정적) | EDF(Earliest Deadline First, 동적) |
|---|---|---|
| 우선순위 결정 | 고정(주기기준) | 실행중 동적변경(마감시한이 가까울수록 우선) |
| CPU이용률 한계 | 약82.8%(n→∞일때 ln2≈69.3%) | 100%까지 이론적 보장 |
| 구현복잡도 | 단순 | 복잡(매번 재계산) |
| 실무활용 | 항공우주·자동차 임베디드(예측가능성 중시) | 학술/특수환경 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 우선순위역전(PIP/PCP) | RM처럼 우선순위기반 스케줄링에서 반드시 함께 다뤄야 하는 부작용(아래에서 상세) |
| 실시간시스템(Hard/Soft Real-Time) | RM이 적용되는 상위 시스템분류 |
| ISA/IEC 62443 / ISO 26262 | RM이 실제로 적용되는 산업제어·자동차 안전시스템 표준(보안/SW도메인과 연결) |

## 3. MLQ (Multi-Level Queue) 스케줄링

**알고리즘 분류**: 프로세스를 **여러 단계(레벨)의 큐**로 미리 분류해, 큐마다 다른 스케줄링정책을 적용하는 방식

**동작원리**
```
[Level1: 시스템프로세스 큐] - 최우선, RR(Round Robin) 적용
[Level2: 대화형(Interactive) 프로세스 큐] - 중간우선, RR 적용
[Level3: 배치(Batch) 프로세스 큐] - 최하위, FCFS 적용

원칙: 상위레벨 큐가 비어있을 때만 하위레벨 큐의 프로세스가 실행됨(고정우선순위 큐간 관계)
```

**비교(성능지표 — MFQ와 비교)**

| 구분 | MLQ(Multi-Level Queue) | MLFQ(Multi-Level Feedback Queue) |
|---|---|---|
| 큐간 이동 | **불가**(한번 분류된 큐에 고정) | **가능**(실행패턴에 따라 큐를 이동, 피드백 반영) |
| 적응성 | 낮음(고정분류라 환경변화 대응못함) | 높음(CPU 사용패턴 학습해 동적조정) |
| 기아현상위험 | 높음(하위큐는 상위큐가 바쁘면 영원히 대기가능) | 낮음(에이징 등으로 보완) |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 라운드로빈(RR) / FCFS | MLQ의 각 레벨 내부에서 실제로 적용되는 기본 스케줄링기법 |
| 기아현상(Starvation) | MLQ의 핵심 한계점, 에이징(Aging)기법으로 보완 |
| 큐 스케줄링(FIFO/PQ/CQ/WFQ) | 네트워크 패킷처리의 큐잉기법과 동일한 "다단계 우선순위 큐" 철학 공유(네트워크 도메인과 연결) |

## 4. SJF / SRT / SSTF

**알고리즘 분류**

| 알고리즘 | 적용대상 | 선점여부 |
|---|---|---|
| **SJF(Shortest Job First)** | CPU스케줄링 | 비선점(실행시작하면 끝까지) |
| **SRT(Shortest Remaining Time)** | CPU스케줄링 | **선점**(남은시간이 더 짧은 작업이 도착하면 교체) |
| **SSTF(Shortest Seek Time First)** | 디스크스케줄링 | - (탐색시간 최소화 기준) |

**동작원리(SJF vs SRT 비교 — 137회 기출패턴)**
```
[SJF] 대기중인 작업들 중 "예상실행시간이 가장짧은" 작업을 먼저 실행, 한번 시작하면 끝까지 실행
[SRT] 새 작업이 도착할 때마다 "현재실행중 작업의 남은시간"과 "신규작업의 실행시간"을 비교
      → 신규작업이 더 짧으면 즉시 선점(Context Switch 발생)
```

**SSTF 동작원리(디스크헤드 이동)**
```
현재 헤드위치: 50, 대기중인 요청: 10, 30, 70, 90
→ 현재위치(50)에서 가장 가까운 요청부터 처리: 30(거리20) → 10(거리20, 동률시 임의) → 70 → 90
(매번 "가장 가까운" 요청을 선택, 단 한쪽 방향만 계속 선택되면 반대편 요청이 오래 대기하는 기아현상 위험)
```

**비교(성능지표)**

| 지표 | SJF | SRT | SSTF |
|---|---|---|---|
| 평균대기시간 | 짧음(비선점 알고리즘 중 최적) | SJF보다 더짧음(선점으로 즉시반응) | 디스크 평균탐색거리 최소화 |
| 기아현상위험 | 긴작업이 계속 밀릴수있음 | 더 심함(짧은작업이 계속 끼어들면 긴작업 무한대기) | 한쪽방향에 요청집중시 반대편 기아 |
| 예측정확성 의존 | 실행시간 사전예측 필요(부정확시 성능저하) | 동일 | 불필요(현재위치기준만 계산) |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| SLTF(Shortest Latency Time First) | SSTF와 함께 비교출제되는 또다른 디스크스케줄링(회전지연까지 고려, 137회 기출) |
| FCFS / RR | SJF/SRT와 대비되는 가장 단순한 기본 스케줄링기법 |
| 기아현상(Starvation) / 에이징(Aging) | SJF/SRT/SSTF 모두 공통적으로 안고있는 부작용과 그 해결책 |

## 5. 우선순위 역전 (PIP / PCP)

**알고리즘 분류(문제상황 정의)**
> 우선순위기반 스케줄링에서, **낮은우선순위 태스크가 공유자원의 락(Lock)을 점유한 상태**에서 **높은우선순위 태스크가 그 자원을 기다리며 대기**해야 하는 상황 → 결과적으로 높은우선순위 태스크가 낮은우선순위 태스크보다 더 오래 기다리는 역설적 현상

**동작원리(시나리오 — 126회 기출패턴, P연산/V연산 활용)**
```
[T1: 최저우선순위] 자원X의 세마포어 P(X) 획득 → 실행중
[T3: 최고우선순위] 자원X 필요 → P(X) 시도 → T1이 점유중이라 대기(블록)
[T2: 중간우선순위] 자원X와 무관 → CPU선점하고 실행(T1보다 우선순위높아 T1을 선점)
   → T1은 T2에게 밀려 실행을 못하고, 그 결과 T1이 들고있는 자원X를 기다리는 T3도 함께 묶여 대기
   → 결과: 최고우선순위 T3가 중간우선순위 T2보다 더 늦게 실행되는 "역전" 현상 발생
```

**해결기법 2가지 비교(PIP vs PCP)**

| 기법 | 동작원리 |
|---|---|
| **PIP(Priority Inheritance Protocol, 우선순위상속)** | 낮은우선순위 태스크(T1)가 락을 점유한 동안, 더 높은우선순위 태스크(T3)가 대기하게 되면, **T1의 우선순위를 T3수준으로 임시상승** → T2가 T1을 더이상 선점못함 → T1이 빨리 끝나고 락을 풀어줌 |
| **PCP(Priority Ceiling Protocol, 우선순위상한)** | 각 자원에 미리 "그 자원을 사용할 가능성있는 태스크 중 최고우선순위(Ceiling)"를 설정 → 락 획득시 그 우선순위로 즉시 격상(상속보다 선제적) → 연쇄적 블로킹(Chained Blocking)까지 방지 가능 |

**비교(성능지표)**

| 지표 | PIP | PCP |
|---|---|---|
| 구현복잡도 | 비교적단순 | 복잡(사전 Ceiling값 분석필요) |
| 연쇄블로킹 방지 | 부분적(단일자원 역전만 해결) | 완전방지(다중자원 연쇄역전까지) |
| 데드락 방지효과 | 없음 | 있음(우선순위상한 규칙이 부수적으로 데드락도 방지) |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 세마포어 P/V연산 | 우선순위역전 시나리오를 구체적으로 표현하는 동기화 메커니즘 |
| 락기반 병행제어(2PL) | DB의 락경쟁과 동일한 "공유자원 대기" 문제의 OS레벨 버전(DB도메인과 연결) |
| RM스케줄링 | 우선순위역전이 실시간시스템(RM 적용환경)에서 특히 치명적인 이유와 직결 |

## 6. 은행가 알고리즘 (Banker's Algorithm)

**알고리즘 분류**: 데드락 **예방(Avoidance)** 기법 중 하나 — 자원을 할당하기 "전에" 시뮬레이션으로 안전성을 미리 검사

**동작원리**
```
①각 프로세스의 최대요구량(Max), 현재할당량(Allocation), 가용자원(Available)을 관리
②신규 요청이 오면, 그 요청을 일단 할당했다고 가정(시뮬레이션)
③할당후에도 모든 프로세스가 "최대요구량까지 받을 수 있는 안전한 순서(Safe Sequence)"가 
  존재하는지 검사
④안전하면 실제로 할당, 안전하지않으면(데드락 위험) 요청을 보류(대기)
```

**예시(안전성검사 — 간단버전)**
```
프로세스  Max  Allocation  Need(=Max-Allocation)
P1        10      5            5
P2         5      2            3
P3         8      3            5
가용자원: 3

검사: Need가 가용자원(3)보다 작거나같은 프로세스부터 실행가능
→ P2(Need=3) 실행가능 → 완료시 자원반납 → 가용자원 = 3+2 = 5
→ P1(Need=5) 실행가능 → 완료시 가용자원 = 5+5 = 10
→ P3(Need=5) 실행가능 → 완료시 가용자원 = 10+3 = 13
→ 안전순서(P2→P1→P3) 존재 = "안전상태(Safe State)" → 신규요청 할당 승인
```

**비교(성능지표 — 데드락 처리방식 전체비교)**

| 방식 | 시점 | 방법 | 오버헤드 |
|---|---|---|---|
| **예방(Prevention)** | 사전(설계) | 데드락 4조건 중 하나를 원천차단 | 자원활용률 저하 |
| **회피(Avoidance, 은행가알고리즘)** | 할당시점 | 매 요청마다 안전성 시뮬레이션 | 계산오버헤드 큼 |
| **탐지후복구(Detection&Recovery)** | 사후 | 주기적으로 데드락 탐지 후 희생자선정·롤백 | 탐지주기에 따른 지연 |
| **무시(Ostrich)** | - | 데드락이 드물면 그냥 무시(재부팅으로 해결) | 실무에서 흔히 사용 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 데드락 4조건(상호배제/점유대기/비선점/순환대기) | 은행가알고리즘이 막고자하는 데드락의 발생조건 |
| 데드락 vs 기아현상(Starvation) | 132회 기출 비교패턴 — 데드락은 "영원히 대기", 기아현상은 "낮은확률로 계속 밀림"(컴퓨터구조 이전파일과 연결) |
| 락기반 병행제어(2PL) | DB트랜잭션의 데드락 처리도 동일하게 예방/회피/탐지 3가지 전략으로 분류(DB도메인과 연결) |
