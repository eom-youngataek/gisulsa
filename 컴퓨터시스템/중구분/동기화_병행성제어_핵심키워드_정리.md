# 동기화/병행성 제어 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 개념 → 발생조건/원리 → 해결기법(사례 적용)

---

## 1. 데드락 4조건 vs Starvation

**개념**: 데드락(Deadlock)=2개 이상 프로세스가 서로가 가진 자원을 기다리며 **영원히 멈춰버린 상태** / Starvation(기아현상)=특정 프로세스가 자원을 계속 할당받지 못해 **무한정 대기**하지만 시스템 전체는 정상동작 중인 상태

**발생조건(데드락 4조건 — 4가지 모두 동시충족시에만 발생)**

| 조건 | 내용 |
|---|---|
| ①상호배제(Mutual Exclusion) | 자원은 한번에 한 프로세스만 사용 가능 |
| ②점유대기(Hold and Wait) | 자원을 점유한 채로 다른 자원을 추가로 요청·대기 |
| ③비선점(No Preemption) | 다른 프로세스가 점유한 자원을 강제로 빼앗을 수 없음 |
| ④순환대기(Circular Wait) | P1→P2→P3→...→P1 형태로 자원요청이 원형으로 순환 |

**해결기법(사례 적용)**
```
[데드락 사례] P1이 자원A점유+자원B요청, P2가 자원B점유+자원A요청 → 순환대기로 영원히 블록
→ 해결: 4조건 중 하나를 제거 — 자원요청순서를 전역적으로 통일(순환대기 원천차단), 
        또는 은행가알고리즘으로 할당전 안전성검사(회피)

[Starvation 사례] 우선순위 낮은 프로세스가 계속 더 높은 프로세스에 밀려 CPU를 못받음
→ 해결: 에이징(Aging) — 대기시간이 길어질수록 우선순위를 점진적으로 상승시켜 결국 실행기회 보장
```

**비교(132회 기출패턴)**

| 구분 | 데드락 | Starvation |
|---|---|---|
| 시스템상태 | 완전정지(순환대기로 진행불가) | 시스템은 계속 동작(다른 프로세스는 진행) |
| 원인 | 4조건 동시충족 | 스케줄링정책의 불공정성(우선순위 편중) |
| 해결 | 예방/회피/탐지복구 | 에이징, 공정스케줄링(라운드로빈 등) |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 은행가알고리즘 | 데드락 회피의 대표기법(이전파일과 직결) |
| 우선순위역전(PIP/PCP) | Starvation과 유사하게 우선순위 메커니즘에서 파생되는 부작용(이전파일과 연결) |
| 락기반 병행제어(DB) | DB트랜잭션의 데드락도 동일한 4조건으로 발생, 타임아웃/대기그래프로 탐지(DB도메인과 연결) |

## 2. 세마포어 P/V연산

**개념**: 공유자원에 대한 접근을 제어하는 **정수형 카운터** 기반 동기화 도구 — 자원의 "이용가능한 개수"를 표현

**발생조건/원리(P/V연산 동작)**
```
P연산(Proberen, 획득시도) = 자원사용전 호출
   if (S > 0) { S = S-1; 진행 } else { S < 0 상태로 만들고 대기(Block) }

V연산(Verhogen, 반납) = 자원사용후 호출
   S = S+1; 만약 대기중인 프로세스가 있으면 그중 하나를 깨움(Wakeup)

[이진세마포어] S값이 0 또는 1만 가짐(뮤텍스와 유사, 상호배제용)
[계수세마포어] S값이 여러 정수값 가능(자원풀 개수만큼, 예: 주차장 빈자리수)
```

**해결기법(사례 적용 — 생산자/소비자 문제)**
```
공유버퍼 크기N, 세마포어 empty=N(빈자리수), full=0(채워진자리수), mutex=1

[생산자] P(empty) → P(mutex) → 데이터삽입 → V(mutex) → V(full)
[소비자] P(full) → P(mutex) → 데이터추출 → V(mutex) → V(empty)
(empty/full로 버퍼 가득참/비어있음을 제어, mutex로 동시접근시 상호배제)
```

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 우선순위역전(PIP/PCP) | 세마포어P연산으로 자원을 점유한 상태에서 발생하는 대표적 부작용 시나리오 |
| 생산자-소비자 문제 / 식사하는 철학자 문제 | 세마포어로 해결하는 대표적 동기화 고전문제 |
| DB의 락(Lock) | "자원에 대한 배타적 접근권한 획득"이라는 점에서 본질적으로 동일한 개념(DB도메인과 연결) |

## 3. 뮤텍스(Mutex) vs 모니터(Monitor)

**개념**: 뮤텍스=상호배제 전용의 가장 단순한 동기화도구(이진세마포어와 유사하나 "소유권" 개념 있음, 점유한 스레드만 해제가능) / 모니터=공유자원과 그 자원을 다루는 함수(연산)를 하나의 모듈로 캡슐화해, **자동으로 상호배제를 보장**하는 고수준 동기화 구조

**발생조건/원리(비교)**

| 구분 | 세마포어 | 뮤텍스 | 모니터 |
|---|---|---|---|
| 소유권개념 | 없음(누구나 V연산 가능) | **있음**(잠근 스레드만 해제가능) | 있음(언어차원에서 강제) |
| 사용방식 | P/V연산 명시적 호출 | lock()/unlock() 명시적 호출 | 객체의 메서드 호출만으로 자동 동기화(synchronized 등) |
| 오류위험 | 호출순서를 사람이 직접관리(실수위험) | 비교적 안전 | 가장안전(언어가 강제) |
| 대기/신호 | P연산자체가 대기처리 | 별도 조건변수 필요시 추가 | **조건변수(Condition Variable)**가 내장(wait/signal) |

**해결기법(사례 적용)**: Java의 `synchronized` 키워드가 모니터의 대표구현 — 메서드에 synchronized를 붙이면 그 메서드는 한번에 하나의 스레드만 진입가능하도록 컴파일러/JVM이 자동보장(개발자가 직접 P/V를 호출할 필요없음)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 조건변수(Condition Variable) | 모니터 내부에서 "조건이 충족될때까지 대기"를 구현하는 wait/signal 메커니즘 |
| Race Condition | 뮤텍스/모니터가 직접 방지하고자 하는 핵심문제(아래에서 상세) |
| JVM GC | 모니터(synchronized)와 함께 Java런타임의 동시성관리 핵심요소로 자주 비교출제 |

## 4. IPC 3대기법 (Inter Process Communication)

**개념**: 서로 독립된 메모리공간을 가진 프로세스들이 데이터를 교환하기 위한 통신기법(스레드는 메모리를 공유해 IPC가 불필요하나, 프로세스는 격리되어 있어 별도 메커니즘 필요)

**발생조건/원리(3대기법 비교)**

| 기법 | 동작원리 | 특징 |
|---|---|---|
| **공유메모리(Shared Memory)** | 여러 프로세스가 동일한 물리메모리영역을 매핑해 직접 읽기/쓰기 | 가장빠름(커널개입 최소), 단 동시접근시 동기화(세마포어 등) 별도필요 |
| **메시지큐(Message Queue/Pipe)** | 커널이 관리하는 큐에 메시지를 넣고(send) 꺼내는(receive) 방식 | 안전(커널이 동기화 보장), 상대적으로 느림(복사오버헤드) |
| **소켓(Socket)** | 네트워크 프로토콜(TCP/IP 등) 기반 통신 | 같은PC 내부는 물론 **다른 네트워크의 프로세스**와도 통신가능(가장 범용적) |

**해결기법(사례 적용 — 공유자원의 충돌·일관성 문제 해결)**: 공유메모리 방식 IPC를 사용할 때는 여러 프로세스가 동시에 같은 메모리에 쓰기 시도시 데이터충돌 발생 → 세마포어/뮤텍스로 그 메모리영역에 대한 접근을 직렬화(상호배제) 해야 데이터 일관성 보장

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 소켓통신(TCP소켓/Web소켓) | IPC의 소켓기법이 네트워크통신 전체로 확장된 사례(네트워크 도메인과 연결) |
| MSA의 서비스간 통신 | 분산환경의 IPC가 곧 MSA 서비스메시·API호출로 확장된 형태(SW아키텍처 도메인과 연결) |
| 세마포어/뮤텍스 | 공유메모리방식 IPC 사용시 필수적으로 결합되는 동기화도구 |

## 5. Race Condition (경쟁조건)

**개념**: 둘 이상의 프로세스/스레드가 **공유자원에 동시접근**할 때, 실행순서(타이밍)에 따라 결과가 달라지는 비결정적(Non-deterministic) 현상 — 결과의 정확성이 "운"에 좌우됨

**발생조건/원리(전형적 사례)**
```
공유변수 count = 5

[Thread A] count = count + 1 수행과정: 
   1) count값(5) 읽기 → 2) +1 계산(6) → 3) count에 6 저장

[Thread B] 동시에 count = count - 1 수행과정:
   1) count값(5) 읽기 → 2) -1 계산(4) → 3) count에 4 저장

[문제상황] A의 1)→B의 1)→A의 2)3)(count=6 저장)→B의 2)3)(count=4 저장)
   → 최종 count=4 (A의 +1 연산이 그냥 사라짐! 의도한 결과는 count=5였어야함)
   → 실행순서가 겹치는(인터리빙되는) 타이밍에 따라 결과가 달라짐 = Race Condition
```

**해결기법(사례 적용)**: 위 코드(`count = count + 1`)를 **임계영역(Critical Section)**으로 지정 → 세마포어/뮤텍스로 보호해 한번에 한 스레드만 그 영역에 진입하도록 강제(원자성 보장)
```
P(mutex); count = count + 1; V(mutex);  // 이제 중간에 끼어들 수 없음
```

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 임계영역(Critical Section) | Race Condition을 막기 위해 보호해야 할 코드구간 |
| TOCTOU | Race Condition의 보안약점 버전(검사시점과 사용시점 사이의 틈을 노린 공격, 보안 도메인과 연결) |
| DB 동시성제어(락/MVCC) | DB트랜잭션 차원의 Race Condition 방지 메커니즘(DB도메인과 연결) |

## 6. 세그멘테이션 오류 (Segmentation Fault)

**개념**: 프로그램이 자신에게 허용되지 않은 메모리영역에 접근을 시도할 때, OS가 강제로 프로그램을 종료시키는 런타임오류(시그널 SIGSEGV)

**발생조건/원리(대표 발생사례)**
```
①Null포인터 역참조: int *p = NULL; *p = 10;  // NULL이 가리키는 곳에 쓰기시도
②잘못된 포인터 연산: 배열범위를 벗어난 인덱스 접근(Buffer Overflow와 연관)
③해제된 메모리 접근(Use-After-Free): free(p) 이후에도 p를 통해 계속 접근시도
④스택오버플로우: 재귀호출이 너무 깊어져 스택영역을 초과
```

**해결기법(사례 적용)**
- 코드레벨: Null체크 습관화, 배열경계검사, 메모리해제후 포인터를 NULL로 재설정(Dangling Pointer 방지)
- 시스템레벨: ASLR(주소공간배치 임의화)·스택가드(Stack Guard) 등으로 악용(공격)으로의 전이 방지
- 디버깅: 코어덤프(Core Dump) 분석, valgrind 등 메모리분석도구로 발생지점 추적

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| Shellcode / 버퍼오버플로우 | Segmentation Fault가 보안취약점(메모리손상공격)으로 악용되는 경로(보안 도메인과 연결) |
| 가상메모리(페이징) | 세그멘테이션오류가 실제로 발생하는 메커니즘적 배경(페이지테이블에 매핑안된 영역 접근시 트랩발생) |
| 가비지컬렉션(GC) | Use-After-Free류 문제를 언어차원(Java 등)에서 원천적으로 방지하는 메커니즘 |

```
[동시성 문제의 근본원인] Race Condition (실행순서에 따라 결과가 달라짐)
        │
        ▼
[해결도구] 세마포어(P/V) ──→ 뮤텍스(소유권개념 추가) ──→ 모니터(언어차원 자동화)
        │
[다중자원 상호작용 시 위험] 데드락(4조건 동시충족) vs Starvation(불공정스케줄링)
        │
[프로세스간 통신] IPC 3대기법(공유메모리는 동기화 필수 결합)
        │
[메모리 접근오류] 세그멘테이션오류 — Race Condition·동기화실패와는 별개로,
                  잘못된 주소접근 자체에서 발생하는 별도 카테고리 오류
```
