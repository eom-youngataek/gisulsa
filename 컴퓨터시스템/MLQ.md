MLQ는 오늘 다룬 RM(고정우선순위)·SQMS/MQMS(대기열구조)의 아이디어를 \*\*"여러 종류의 작업을 그룹별로 나눠 관리"\*\*하는 방향으로 확장한 개념입니다.

### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (MLQ 정의, 등장배경 - 단일큐의 한계) — 3~4줄
Ⅱ. MLQ 구조 (본론①, 도식 1개 필수)
Ⅲ. MLQ의 한계 및 개선(MLFQ) (본론②, 핵심 배점)
Ⅳ. MLQ vs MLFQ 비교
Ⅴ. 결론
```

포인트: 개요에서 \*\*"모든 프로세스(시스템프로세스/대화형/배치작업)를 하나의 큐에서 똑같은 규칙으로 스케줄링하면 비효율적 → 작업 특성별로 큐를 나눠서 각자 다른 정책을 적용하자"\*\*는 문제의식으로 시작하면, 왜 MLQ가 등장했는지 논리가 섭니다.

### Ⅱ. MLQ 구조 — "분·류·정" (분류→큐배치→정책적용)

| 요소           | 내용                                                             |
| :----------- | :------------------------------------------------------------- |
| **프로세스 분류**  | 작업특성별로 그룹화 — 예: **시스템프로세스 / 대화형(Foreground) / 배치(Background)** |
| **다단계 큐 배치** | 각 그룹이 **독립된 큐**에 들어감 (앞서 다룬 MQMS와 유사구조)                        |
| **큐별 정책**    | 큐마다 **다른 스케줄링 알고리즘**(예: 시스템큐=RR, 배치큐=FCFS) 적용 가능               |
| **큐 간 우선순위** | 상위큐(시스템)가 **완전히 처리될 때까지 하위큐는 대기** (고정우선순위 방식)                  |

→ 암기: **"용도별로 큐를 나누고(분류), 각자 다른 규칙으로 돌리고(정책), 위에 큐가 급하면 아래는 기다린다(우선순위)"** — 앞서 다룬 "MQMS"(서버마다 별도 대기줄)의 아이디어를 "우선순위가 있는 계층"으로 확장한 것입니다.

### 도식화 제안

```
[Queue 0: 시스템프로세스] ──RR── ← 최고우선순위, 항상 먼저 처리
[Queue 1: 대화형프로세스] ──RR──
[Queue 2: 배치프로세스]  ──FCFS── ← 최저우선순위

규칙: Queue0이 비어있어야 Queue1 처리, Queue1도 비어야 Queue2 처리
      (고정된 큐 배정 - 한번 배정되면 다른 큐로 이동 안함)
```

### Ⅲ. MLQ의 한계 및 개선(MLFQ) — 핵심 배점 포인트

**함정 방지: MLQ를 설명만 하면 절반. "무슨 문제가 있어서 MLFQ로 발전했는가"까지 가야 완성됩니다.**

| MLQ의 한계              | 내용                                                                |
| :------------------- | :---------------------------------------------------------------- |
| **기아상태(Starvation)** | 상위큐(시스템/대화형)가 계속 바쁘면, **하위큐(배치)는 영원히 처리 안됨**                      |
| **고정배치의 경직성**        | 프로세스가 **한번 큐에 배정되면 고정** — 상황이 바뀌어도(예: 대화형이 배치처럼 CPU를 오래 씀) 재배치 불가 |

**해결책: MLFQ (Multilevel Feedback Queue)**

| 개선점            | 내용                                                                         |
| :------------- | :------------------------------------------------------------------------- |
| **피드백(이동)**    | 프로세스의 **실제 행동(CPU 사용패턴)에 따라 큐를 이동**시킴 — CPU를 오래 쓰면 하위큐로, I/O대기가 많으면 상위큐 유지 |
| **에이징(Aging)** | 하위큐에서 **오래 기다린 프로세스는 점차 우선순위를 높여줌** — 기아상태 방지                              |
| **큐별 타임퀀텀 차등** | 상위큐(대화형 성향)는 **짧은 타임퀀텀**, 하위큐(배치성향)는 **긴 타임퀀텀**으로 차등부여                     |

→ 암기: **"MLQ는 고정칸막이라 굶어죽는 문제가 있고, MLFQ는 행동을 보고 칸을 옮겨주고(피드백) 너무 오래 기다리면 승진시켜준다(에이징)"** — 앞서 다룬 "페이지교체알고리즘"에서 LRU가 "최근 행동을 관찰해서 판단"하는 것과 같은 원리(과거행동 기반 동적조정)입니다.

### Ⅳ. MLQ vs MLFQ 비교

| 구분          | **MLQ**                  | **MLFQ**                         |
| :---------- | :----------------------- | :------------------------------- |
| **큐 이동**    | **불가**(고정배치)             | **가능**(행동에 따라 이동)                |
| **기아상태 위험** | **높음**                   | 낮음(에이징으로 완화)                     |
| **구현복잡도**   | 단순                       | 복잡(이동규칙, 에이징 관리 필요)              |
| **적합상황**    | 작업유형이 **명확히 사전분류** 가능할 때 | 작업특성을 **미리 알 수 없을 때**(대부분의 범용OS) |

→ 앞서 다룬 "RM(정적우선순위) vs EDF(동적우선순위)"와 정확히 같은 구조: \*\*MLQ=정적(RM류), MLFQ=동적(EDF류)\*\*이라는 유추가 심화 배점 포인트입니다.

### Ⅴ. 결론 포인트 (오늘 스케줄링 시리즈 총연결)

MLQ→MLFQ의 발전은 **"사전에 정한 고정규칙(정적)"에서 "실제 관찰된 행동에 반응하는 규칙(동적)"으로 진화**하는 패턴이며, 이는 오늘 다룬 RM→EDF(정적→동적 우선순위), FIFO→LRU(과거행동 반영), SQMS/MQMS(구조선택)에서 반복된 \*\*"단순함(예측가능하나 경직) vs 적응성(유연하나 복잡)"\*\*이라는 하나의 설계원리가 스케줄링 전반에 걸쳐 재현되는 사례라는 결론으로 마무리하면, 오늘 다룬 OS스케줄링 계열 답안들이 완결됩니다.

### **1. 답안 전개 스토리 (머릿속 핵심 흐름)**

> "운영체제가 프로세스들을 스케줄링할 때 한 줄로만 섞어놓으면 안 된다. 성격이 급한 '시스템 작업'이나 마우스 클릭 같은 '대화형 작업'은 딜레이 없이 빨리 끝내줘야 하고, 묵묵히 뒤에서 돌아가는 '배치(Batch) 작업'은 좀 천천히 해도 된다. 그래서 이들을 성격별로 아예 신분 계급을 나누어 다른 줄(Queue)에 세우는 것이 **'다단계 큐(MLQ)'** 스케줄링이다. MLQ는 VVIP 줄과 일반 줄을 아예 층별로 분리해 놓고, 급한 VVIP 줄(대화형)에는 응답속도가 빠른 '라운드 로빈(RR)' 알고리즘을, 일반 줄(배치)에는 순서대로 처리하는 'FCFS'를 알아서 다르게 적용한다. 아주 체계적이지만 치명적인 단점이 있다. '카스트 제도'처럼 한 번 일반 줄(하위 큐)에 선 프로세스는 VVIP 줄로 절대 신분 상승을 할 수 없다. 따라서 VVIP 줄에 사람이 계속 들어오면 하위 큐에 있는 애들은 영원히 CPU를 못 받고 굶어 죽는 \*\*'기아 현상(Starvation)'\*\*에 빠지게 된다. 이 무자비한 MLQ의 단점을 극복하기 위해, 오래 기다리면 슬쩍 상위 큐로 올려보내 주는(에이징 기법) 자비로운 \*\*'다단계 피드백 큐(MFQ)'\*\*로 진화하게 되었다."

***

### **2. 실제 답안에 쓸 핵심 내용 (암기용)**

#### **I. \[도입] 성격이 다른 프로세스는 다른 줄에, 다단계 큐(MLQ) 개요**

* **정의:** 준비 큐(Ready Queue)를 한 개만 쓰는 것이 아니라 프로세스의 우선순위나 성격(유형)에 따라 **여러 개의 독립적인 큐로 분할하고, 각 큐마다 고유한 스케줄링 알고리즘을 적용**하는 방식.
* **목적:** 대화형(Interactive) 프로세스와 백그라운드 배치(Batch) 프로세스의 성격이 완전히 다르므로, 이를 분리하여 시스템 응답 시간 최소화 및 처리량 효율을 동시에 잡기 위함.

#### **II. \[본론 1] MLQ의 핵심 동작 메커니즘과 큐별 알고리즘 (카스트 제도)**

MLQ의 가장 큰 특징은 \*\*'한 번 들어간 큐에서 절대 벗어날 수 없다'\*\*는 엄격성입니다.

* **큐의 계층적 분리 (예시):**
  * **1순위 (시스템 프로세스 큐):** OS 시스템 작업 등 초고속 처리가 필요함.
  * **2순위 (대화형 프로세스 큐):** 사용자 입력 응답이 중요하므로 짧은 할당 시간을 갖는 **'라운드 로빈(Round Robin)' 알고리즘** 적용.
  * **3순위 (배치 프로세스 큐):** 사용자 개입 없이 오래 도는 작업이므로 오버헤드를 줄이기 위해 순차적인 **'FCFS(선입선출)' 알고리즘** 적용.
* **큐 간의 스케줄링 통제:** 상위 우선순위 큐가 완전히 비어(Empty) 있어야만 비로소 하위 큐의 프로세스가 CPU를 할당받아 실행됨. 만약 하위 큐 실행 중에 상위 큐로 새 프로세스가 들어오면 **즉각 CPU를 뺏김(선점형).**

#### **III. \[본론 2] MLQ의 치명적 한계: 큐 간 이동 불가에 따른 기아 현상(Starvation)**

* **원인:** 프로세스가 실행을 마칠 때까지 자신이 처음 배정된 큐를 절대 변경할 수 없는(No Migration) 엄격한 고립 정책.
* **문제점 발생:** 우선순위가 높은 1, 2순위 큐에 프로세스가 끊임없이 생성되어 들어올 경우, 최하위 큐(배치 작업 등)에 있는 프로세스는 수 시간, 수일 동안 단 한 번도 CPU 제어권을 얻지 못하고 대기 상태에서 방치되는 \*\*무한 대기 및 기아 현상(Starvation)\*\*이 치명적으로 발생함.

#### **IV. \[결론/제언] MLQ의 궁극적 진화: 다단계 피드백 큐(MFQ)와 에이징(Aging) 융합**

* **(키워드 위주 2줄 마무리)** "MLQ의 '기아 현상'이라는 태생적 한계를 극복하기 위해, 현대의 운영체제(Windows, Unix)는 프로세스의 \*\*'큐 간 이동'\*\*을 전면 허용하는 \*\*'다단계 피드백 큐(MFQ, Multi-Level Feedback Queue)'\*\*로 진화했습니다. MFQ는 하위 큐에서 너무 오래 기다린 프로세스의 우선순위를 강제로 높여 상위 큐로 구제해 주는 \*\*'에이징(Aging) 기법'\*\*을 융합하여 기아 현상을 완벽히 타파한 현존 최고의 CPU 스케줄링 기법입니다."
