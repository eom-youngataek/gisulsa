### Ⅱ. 세그멘테이션 구조 — "세·베·한·보" (4대 구성요소)

| 구성요소              | 내용                                                          |
| :---------------- | :---------------------------------------------------------- |
| **세그먼트(Segment)** | 논리적 의미단위(코드/데이터/스택/힙 등) — **가변크기**                          |
| **세그먼트테이블**       | 세그먼트번호별 **베이스(Base)주소 + 한계(Limit)** 저장                      |
| **베이스(Base)**     | 해당 세그먼트가 물리메모리에서 시작하는 주소                                    |
| **한계(Limit)**     | 해당 세그먼트의 **크기**(길이) — 이 범위를 벗어나면 **보호오류(Protection Fault)** |

→ 암기: **"세그먼트마다 어디서 시작하고(Base) 얼마나 큰지(Limit)를 표에 적어두고, 넘어가면 막는다(보호)"** — 앞서 다룬 페이징의 "Page#→Frame#" 단순매핑과 달리, 세그멘테이션은 \*\*"주소가 그 범위 안에 있는지 검증"\*\*하는 과정이 추가된다는 게 핵심 차이입니다.

### 도식화 제안

```
[논리주소] Segment# | Offset
     ↓ (세그먼트테이블 조회)
[세그먼트테이블] Seg0: Base=1000,Limit=400
                Seg1: Base=2000,Limit=150...
     ↓ (Offset < Limit 검증)
[물리주소] = Base + Offset
     ↓
[물리메모리] (세그먼트별로 가변크기 배치)

┌────────┬──────┬────────────┬────┐
│ Seg0(코드)│Seg2(빈공간)│ Seg1(데이터) │... │
└────────┴──────┴────────────┴────┘
        (가변크기로 여기저기 배치 → 외부단편화 발생)
```

### Ⅲ. 페이징 vs 세그멘테이션 비교 — 핵심 변별력

**함정 방지: "페이징=고정, 세그멘테이션=가변"만 답하면 절반. 단편화·보호·공유 관점까지 대비해야 완성.**

| 구분                 | **페이징**                      | **세그멘테이션**                                 |
| :----------------- | :--------------------------- | :----------------------------------------- |
| **분할단위**           | **고정크기**(물리적 편의)             | **가변크기**(논리적 의미)                           |
| **분할기준**           | 프로그램 내용과 무관                  | 코드/데이터/스택 등 **의미단위**                       |
| **단편화**            | **내부단편화**(마지막 페이지의 남는 공간 낭비) | **외부단편화**(가변크기라 빈틈이 여기저기 생김)               |
| **보호(Protection)** | 페이지단위 권한설정(읽기/쓰기)            | **세그먼트단위**로 자연스러운 보호(코드=읽기전용, 스택=읽기/쓰기 등)  |
| **공유(Sharing)**    | 공유 시 페이지단위로 애매하게 쪼개짐         | **의미단위 그대로 공유**(예: 라이브러리 코드세그먼트 통째로 공유) 유리 |
| **주소구조**           | Page# + Offset               | Segment# + Offset (+ Limit검증)              |

→ 암기: **"페이징은 관리는 쉽지만(고정) 의미가 없고, 세그멘테이션은 의미는 있지만(가변) 관리가 어렵다(단편화)"** — 앞서 다룬 "직접매핑↔완전연관매핑"의 트레이드오프와 동일한 구조: **단순함 vs 유연함**.

### Ⅳ. 세그멘테이션의 문제점 — 외부단편화 및 해결

세그먼트가 가변크기라서, 할당·해제를 반복하면 메모리에 \*\*사용 안하는 작은 빈틈들(Hole)\*\*이 여기저기 생기는 \*\*외부단편화(External Fragmentation)\*\*가 발생합니다.

| 해결방안                               | 내용                                           |
| :--------------------------------- | :------------------------------------------- |
| **압축(Compaction)**                 | 빈틈을 없애기 위해 세그먼트들을 **한쪽으로 밀어 재배치** — 오버헤드 큼   |
| **최적적합/최초적합** (Best-fit/First-fit) | 빈 공간 중 어디에 새 세그먼트를 넣을지 배치전략                  |
| **세그멘테이션-페이징 혼합**                  | 각 세그먼트를 다시 **페이지로 나눠** 물리메모리에 배치 — 아래 Ⅴ에서 정리 |

### Ⅴ. 결론 포인트 — 실무는 "혼합방식"으로 절충

**함정 방지: 페이징과 세그멘테이션을 양자택일로 답하면 미완성. 실제 현대 OS(x86 등)는 두 개를 혼합해서 씁니다.**

**세그멘테이션+페이징 혼합방식**: 논리주소를 먼저 **세그먼트단위**(의미)로 나누고, 각 세그먼트 내부는 다시 **페이지단위**(물리적 관리편의)로 쪼갭니다.

```
[논리주소] Segment# | Page# | Offset
     ↓ 세그먼트테이블 조회 → 해당 세그먼트의 페이지테이블 위치 확인
     ↓ 페이지테이블 조회 → Frame# 획득
[물리주소] Frame# | Offset
```

→ **"세그멘테이션의 의미보호+공유 장점"과 "페이징의 고정크기 관리편의(단편화 없음) 장점"을 절충**한 것 — 이는 앞서 다룬 "집합연관매핑(직접매핑+완전연관매핑의 절충)"과 정확히 같은 논리구조의 반복입니다.

**최종 결론**: 페이징(물리적 효율성)과 세그멘테이션(논리적 의미)은 서로 다른 목표를 가진 기법이며, 실무는 둘을 배타적으로 택하지 않고 **각자의 장점만 취해 계층적으로 결합**한다는 점 — 이는 오늘 다룬 "캐시매핑의 N-way 절충", "CoE의 연합형 모델" 등에서 반복된 \*\*"양극단의 장점만 취하는 하이브리드 설계철학"\*\*이 OS 메모리관리에도 그대로 나타난다는 결론으로 마무리하면 좋습니다.

### **1. 답안 전개 스토리 (머릿속 핵심 흐름)**

> "이전의 '페이징'은 메모리 낭비(외부 단편화)를 막기 위해 프로그램을 '같은 크기(페이지)'로 무식하게 토막 내버렸다. 기계 입장에선 관리하기 편하지만, 코드 영역과 데이터 영역이 한 조각에 짬뽕으로 섞여 버려 다른 프로그램과 코드를 '공유'하거나 '보안(접근제어)'을 걸기가 너무 까다로웠다. 그래서 사람(개발자)이 생각하는 논리적인 단위대로 '코드(Code)', '데이터(Data)', '스택(Stack)'이라는 의미 있는 덩어리로 예쁘게 자르는 \*\*'세그멘테이션(Segmentation)'\*\*이 등장했다. 의미 단위로 잘랐으니 조각들의 크기가 다 제각각이다. 딱 필요한 만큼 잘렸으니 내부 단편화는 사라지고 프로그램 보호와 공유가 아주 쉬워졌지만, 크기가 들쭉날쭉하다 보니 빈 공간에 끼워 넣기가 다시 까다로워져 끔찍한 \*\*'외부 단편화'\*\*가 또다시 부활하는 치명적 단점을 낳았다. 결국 현대의 OS는 이 둘의 장점만 취합하여, 먼저 의미 단위(세그먼트)로 자른 다음 그걸 다시 잘게 동일한 크기(페이지)로 다져서 넣는 \*\*'페이징된 세그먼테이션'\*\*이라는 하이브리드 혼합 기법을 완성했다."

***

### **2. 실제 답안에 쓸 핵심 내용 (암기용)**

#### **I. \[도입] 기계 중심에서 논리적 의미 단위 중심으로, 세그멘테이션 개요**

* **정의:** 가상 메모리를 관리할 때, 프로세스를 동일한 크기로 자르는 것이 아니라 **코드(Code), 데이터(Data), 스택(Stack) 등 '서로 크기가 다른 논리적인 의미 단위(Segment)'로 분할**하여 메모리에 할당하는 기법.
* **목적:** 프로그램의 논리적 구조를 보존하여 세그먼트별로 읽기/쓰기/실행 권한을 다르게 부여하는 **기억장치 보호(Protection)** 및 타 프로세스와의 **공유(Sharing)** 효율성을 극대화하기 위함.

#### **II. \[본론 1] 세그먼트 주소 변환 메커니즘과 안전장치 (Base와 Limit)**

크기가 제각각이기 때문에 페이징에는 없는 \*\*'길이 제한(Limit)'\*\*이라는 특별한 방어막이 필요합니다.

* **주소의 구조:** CPU의 논리 주소는 **`[ s (세그먼트 번호) | d (오프셋/거리) ]`** 로 구성됨.
* **세그먼트 테이블의 핵심 2가지 값:**
  1. **Base (기준 주소):** 해당 세그먼트가 물리 메모리 어디에서 시작하는지 알려주는 번지수.
  2. **Limit (한계 주소/길이):** ⚠️ **(중요)** 해당 세그먼트의 전체 길이.
* **변환 및 트랩(Trap) 발생:** CPU가 요구한 오프셋 'd'가 세그먼트의 전체 길이인 'Limit'보다 크면, **남의 메모리 영역을 침범한 것으로 간주하여 운영체제가 즉시 인터럽트(Segmentation Fault)를 걸어 프로그램을 강제 종료**시킵니다. (강력한 보안 메커니즘)

#### **III. \[본론 2] 페이징(Paging) vs 세그멘테이션(Segmentation) 전격 비교 (출제 1순위)**

운영체제 메모리 파트에서 가장 중요하게 다루어지는 앙숙 관계의 비교표입니다.

| **비교 항목**   | **✂️ 페이징 (Paging) 기법**                       | **🧩 세그멘테이션 (Segmentation) 기법**                     |
| :---------- | :------------------------------------------- | :-------------------------------------------------- |
| **분할의 기준**  | 물리적인 **동일한 크기**로 분할 (Page)                   | 논리적인 **의미 단위, 서로 다른 크기**로 분할                        |
| **단편화 문제**  | **내부 단편화 발생** (마지막 페이지에 빈 공간 남음)             | **외부 단편화 발생** (들쭉날쭉한 조각들 사이의 자투리 공간 낭비)             |
| **보호 및 공유** | 한 페이지에 코드와 데이터가 섞일 수 있어 **권한 부여와 공유가 까다로움.** | 의미 단위로 쪼개져 있어 **읽기/쓰기 권한 제어와 모듈 공유가 매우 직관적이고 우수함.** |
| **테이블 정보**  | 프레임 시작 주소만 필요                                | 시작 주소(Base) + **길이(Limit) 필수**                      |

#### **IV. \[결론/제언] 두 기법의 진화적 융합, '페이징된 세그멘테이션(Paged Segmentation)'**

* **(키워드 위주 2줄 마무리)** "페이징은 단편화 관점에서 유리하고, 세그멘테이션은 보호와 공유 관점에서 강력합니다. 현대의 운영체제(Linux 등)는 이 두 가지의 치명적 단점을 상호 보완하기 위해, **프로세스를 먼저 의미 단위의 '세그먼트'로 자른 뒤, 그 세그먼트를 다시 동일한 크기의 '페이지'로 잘게 쪼개어 메모리에 적재하는 '페이징된 세그멘테이션' 기법을 표준으로 채택**하여 메모리 관리의 효율성을 극대화하고 있습니다."
