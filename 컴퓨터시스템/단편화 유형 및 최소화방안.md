단편화는 바로 앞서 다룬 "페이징 vs 세그멘테이션" 답안에서 이미 씨앗이 뿌려진 주제입니다. 오늘은 이걸 독립 주제로 정면 승부하되, \*\*"왜 두 종류(내부/외부)가 정확히 페이징/세그멘테이션에 대응하는가"\*\*를 명확히 잡고 가겠습니다.

### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (단편화 정의, 발생원인) — 3~4줄
Ⅱ. 내부단편화 vs 외부단편화 (본론①, 도식 1개 필수)
Ⅲ. 유형별 최소화방안 (본론②, 핵심 배점)
Ⅳ. 결론
```

포인트: 개요에서 \*\*"단편화는 메모리를 나눠서 쓰다 보면 필연적으로 '쓰지 못하는 빈 공간'이 생기는 문제이며, 어떻게 나누느냐(고정 vs 가변)에 따라 단편화의 종류가 결정된다"\*\*는 한 줄로 시작하면, 앞서 다룬 페이징(고정크기)-세그멘테이션(가변크기) 답안과 정확히 이어집니다.

### Ⅱ. 내부단편화 vs 외부단편화 — "고·가" (고정할당 vs 가변할당의 결과)

| 구분       | **내부단편화** (Internal Fragmentation)                     | **외부단편화** (External Fragmentation)                           |
| :------- | :----------------------------------------------------- | :----------------------------------------------------------- |
| **발생원인** | **고정크기** 블록(페이지/파티션)을 할당했는데, 실제 필요량이 그보다 **작아서** 남는 부분 | **가변크기**로 할당·해제를 반복하며, 사용가능한 공간이 \*\*여기저기 조각(Hole)\*\*으로 흩어짐 |
| **발생위치** | 할당된 블록 **내부**(그 블록을 다 못 채워서 낭비)                        | 블록들 **사이사이**(공간은 충분한데 연속되지 않아 못 씀)                           |
| **대응기법** | **페이징**(고정크기 프레임)                                      | **세그멘테이션**, 가변파티션 할당                                         |
| **예시**   | 4KB 페이지에 1KB만 쓰면 3KB 낭비                                | 10KB+20KB 빈틈이 떨어져있어 25KB 프로세스를 못 넣음                          |

→ 암기: **"내부단편화는 '박스가 커서 안이 남는 것', 외부단편화는 '박스들 사이 틈이 흩어져 있는 것'"** — 앞서 다룬 페이징/세그멘테이션 답안의 단편화 항목이 여기서 정확히 재활용됩니다.

### 도식화 제안

```
[내부단편화 - 고정크기 할당]           [외부단편화 - 가변크기 할당]
┌──────┬──────┬──────┐          ┌────┬──┬─────┬───┬────┐
│사용1KB│빈3KB │      │         │Seg0│빈│ Seg1 │빈 │Seg2│
(4KB블록)│(낭비)│    │          │     │  │      │  │    │
└──────┴──────┴──────┘          └────┴──┴─────┴───┴────┘
블록 "안"에서 낭비                    블록들 "사이"에서 낭비
(총량은 충분해도 조각나서 못 씀)
```

### Ⅲ. 유형별 최소화방안 — 핵심 배점 포인트

**함정 방지: "페이징 쓰면 됨/세그멘테이션 쓰면 됨"이라고 rocketing만 답하면 절반. 각 기법 내에서도 구체적 완화방안이 있다는 걸 보여줘야 완성.**

#### 내부단편화 최소화

| 방안                         | 내용                                                          |
| :------------------------- | :---------------------------------------------------------- |
| **작은 페이지크기 채택**            | 페이지가 작을수록 마지막 페이지의 낭비분도 작아짐 (단, 페이지테이블 크기↑, 오버헤드 trade-off) |
| **버디시스템(Buddy System)**    | 필요한 크기에 **가장 근접한 2^n 블록**을 할당해 낭비 최소화                       |
| **슬랩 할당자(Slab Allocator)** | 자주 쓰는 **고정크기 객체 전용 캐시풀**을 만들어 낭비 없이 재사용(커널 메모리 관리에서 사용)     |

#### 외부단편화 최소화

| 방안                 | 내용                                                                                                                |
| :----------------- | :---------------------------------------------------------------------------------------------------------------- |
| **압축(Compaction)** | 사용중인 블록들을 **한쪽으로 밀어** 흩어진 빈틈을 하나로 합침 — 오버헤드 크지만 확실                                                                |
| **배치전략 최적화**       | **Best-fit**(가장 딱맞는 곳), **First-fit**(처음 맞는 곳), **Worst-fit**(가장 큰 곳)의 선택 — 실무에선 First-fit이 속도, Best-fit이 공간효율 유리 |
| **페이징 도입(근본해결)**   | 가변크기 할당 자체를 없애고 **고정크기 페이지로 전환** → 외부단편화를 내부단편화로 "치환"(트레이드)                                                       |

→ 암기: **"내부단편화는 크기를 정교하게 나누거나(버디/슬랩) 캐시해서 줄이고, 외부단편화는 밀어서 합치거나(압축) 아예 페이징으로 바꿔서 없앤다"**

**+ 트레이드오프 핵심 통찰 (심화, 차별화 포인트)**: 외부단편화의 근본해결책인 "페이징 전환"은 사실 외부단편화를 없애는 대신 **내부단편화를 발생시키는 것**입니다 — 즉, **단편화를 완전히 없애는 방법은 없고, 어느 종류의 단편화를 감당할지 선택하는 문제**라는 게 핵심 통찰입니다.

### Ⅳ. 결론 포인트 (차별화 한 줄)

단편화는 "제거"의 대상이 아니라 \*\*"어느 종류를, 얼마나 감당할 것인가를 설계 초기에 선택하는 트레이드오프"\*\*입니다 — 이는 오늘 다룬 "페이징(내부단편화 감당) vs 세그멘테이션(외부단편화 감당)"의 선택과 정확히 같은 문제이며, 더 거슬러 올라가면 "캐시매핑(직접↔완전연관)", "쓰기정책(Through↔Back)"에서도 반복된 \*\*"완벽한 해법은 없고, 어떤 비효율을 감수할지를 고르는 것"\*\*이라는 오늘 시리즈 전체를 관통하는 설계원리의 또 다른 사례라는 결론으로 마무리하면 좋습니다.

### **1. 답안 전개 스토리 (머릿속 핵심 흐름)**

> "호텔 방을 배정할 때, 모든 방을 똑같은 '4인실(페이징 기법)'로만 만들어 놨더니, 3명인 가족이 들어가면 빈 침대 1개가 덩그러니 남아서 아깝게 낭비된다. 이것이 바로 방 안에서 잉여 공간이 생기는 \*\*'내부 단편화'\*\*다. 반대로 손님이 올 때마다 '인원수에 맞춰서 방 크기를 요리조리 잘라서(세그먼테이션 기법)' 내줬더니, 손님들이 체크아웃하고 난 뒤에 복도 여기저기에 1인용, 2인용 빈자리들이 흩어지게 된다. 정작 10인 단체 손님이 왔을 때, 전체 빈자리의 합은 15인분인데 연속된 큰 방이 없어서 손님을 받지 못하는 끔찍한 사태가 발생한다. 이것이 방 밖에서 공간이 찢어지는 \*\*'외부 단편화'\*\*다. 운영체제는 이 두 가지 테트리스의 딜레마를 해결하기 위해, 조각난 방들을 불도저로 한쪽으로 몰아버리는 **'압축(Compaction)'**, 2의 배수로 방을 쪼개는 **'버디 시스템'**, 그리고 객체 크기를 미리 맞춰놓는 **'슬랩(Slab) 할당자'** 같은 고도의 기술을 총동원한다."

***

### **2. 실제 답안에 쓸 핵심 내용 (암기용)**

#### **I. \[도입] 끝없는 메모리 낭비와의 전쟁, 단편화 현상 개요**

* **정의:** 주기억장치(RAM)에 프로세스(프로그램)를 적재하고 회수하는 과정이 반복되면서, **메모리 공간이 여러 개의 좁은 조각으로 나뉘어 할당할 수 없는 잉여 공간이 발생하여 낭비되는 현상**.
* **문제점:** 메모리의 가용 공간(Free Space) 총합은 충분함에도 불구하고 프로세스를 실행하지 못해 시스템의 성능과 다중 프로그래밍의 효율성을 극도로 저하시킴.

#### **II. \[본론 1] 내부 단편화 vs 외부 단편화 발생 원리와 차이점 (전격 비교)**

| **구분**       | **🛏️ 내부 단편화 (Internal Fragmentation)**                                                          | **🏢 외부 단편화 (External Fragmentation)**                                                          |
| :----------- | :----------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
| **현상 요약**    | 할당된 공간 **'안에서'** 자리가 남음                                                                          | 메모리 공간 **'밖에서'** 쪼가리들이 흩어짐                                                                      |
| **발생 메커니즘**  | 메모리를 \*\*'고정된 크기'\*\*의 블록으로 나눌 때, 프로세스가 요구하는 메모리 크기가 블록 크기의 배수가 아니어서 **마지막 블록 내부에 남게 되는 잉여 공간**. | 메모리를 \*\*'프로세스 크기에 맞춰 가변적'\*\*으로 할당할 때, 프로세스가 들어왔다 빠지기를 반복하며 **연속되지 않은 작은 빈 공간들이 산발적으로 남는 현상**. |
| **발생 원인 기술** | **페이징(Paging) 기법**, 고정 분할 방식                                                                     | **세그멘테이션(Segmentation) 기법**, 동적 분할 방식                                                           |
| **치명도**      | 낭비되는 양이 제한적이라 상대적으로 감수할 만함. (최대 1페이지 미만 낭비)                                                      | 남은 쪼가리를 합치면 충분한데도 프로세스를 아예 올릴 수가 없어서 **매우 치명적임.**                                               |

#### **III. \[본론 2] 단편화 유형별 낭비 최소화 방안 (출제 핵심 포인트)**

단편화를 없애는 운영체제의 핵심 전략들입니다.

**1. 외부 단편화 해결 방안 (흩어진 쪼가리 극복)**

* 🚜 **압축 (Compaction / Garbage Collection):** 실행 중인 프로세스들을 한쪽으로 싹 다 몰아서, 흩어져 있던 **조각난 빈 공간들을 하나의 큰 연속된 공간으로 만드는 작업.** (단점: 옮기는 동안 시스템이 멈춰야 해서 오버헤드가 극심함).
* 🧩 **통합 (Coalescing):** 프로세스가 종료되어 메모리를 반환할 때, 그 옆에 있는 빈 공간과 즉시 하나로 묶어(병합) 조금이라도 큰 공간을 확보하는 기법.
* ✂️ **페이징(Paging) 기법 전면 도입:** 연속된 공간을 버리고 무조건 동일한 크기로 프로세스를 썰어 흩뿌림으로써 외부 단편화를 근본적으로 100% 제거.

**2. 내부 단편화 해결 방안 (블록 내부의 낭비 극복)**

* 🍰 **슬랩 할당자 (Slab Allocator - 리눅스/유닉스 핵심):** 커널 내부에서 자주 쓰이는 특정 객체(예: 파일 디스크립터 등)의 **크기를 미리 알고, 그 크기에 딱 맞는 틀(Slab)을 미리 여러 개 짜놓고 캐싱**하여 할당해 줌으로써 내부 단편화를 최소화하는 최적화 기법.

**3. 양측 단편화의 절충 및 최소화 방안**

* 👯 **버디 시스템 (Buddy System):** 메모리 요청이 들어오면 큰 메모리 블록을 **절반(1/2)씩 계속 쪼개어(Buddy 생성)**, 요구 크기를 담을 수 있는 가장 작은 2의 제곱수(2^n) 크기로 맞춤 할당하는 기법. 내부와 외부 단편화의 밸런스를 잡은 혁신적 기법.

#### **IV. \[결론/제언] 단편화 최소화를 위한 현대 운영체제의 하이브리드 메모리 관리 동향**

* **(키워드 위주 2줄 마무리)** "현대의 운영체제는 단일 기법만으로는 단편화를 완벽히 막을 수 없습니다. 따라서 프로세스의 의미 단위 분할을 통한 보안성(세그멘테이션)을 확보하면서도 외부 단편화를 근절하기 위해 이를 다시 동일한 크기의 페이지로 자르는 **'페이징된 세그멘테이션(Paged Segmentation)'** 기법과 커널의 \*\*'슬랩 할당자'\*\*를 융합한 하이브리드 구조를 채택하고 있습니다."
