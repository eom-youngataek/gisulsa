SJF/SRT는 CPU스케줄링, SSTF는 디스크스케줄링으로 **분야가 다른데 이름이 비슷해서 헷갈리기 쉬운 조합**입니다. 오늘은 이 구분을 명확히 하면서, \*\*"가장 짧은 것부터 처리한다"\*\*는 공통원리로 스토리를 짜겠습니다.

### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (공통원리 - Shortest-First 전략, 적용분야 구분) — 3~4줄
Ⅱ. SJF vs SRT (CPU스케줄링, 본론①, 도식 1개)
Ⅲ. SSTF (디스크스케줄링, 본론②, 도식 1개)
Ⅳ. 공통의 함정 - 기아상태(Starvation)
Ⅴ. 결론
```

포인트: 개요에서 \*\*"셋 다 '가장 짧은/가까운 것부터 처리한다'는 그리디(Greedy) 전략을 쓰지만, SJF/SRT는 CPU작업시간에, SSTF는 디스크헤드이동거리에 적용된다"\*\*는 한 줄로 구분하면, 왜 이름이 비슷한지 그리고 왜 다른 분야인지 동시에 설명됩니다.

### Ⅱ. SJF vs SRT — CPU스케줄링, "비선점 vs 선점"

**함정 방지: SJF와 SRT를 별개로 외우지 말고, "SRT = 선점형 SJF"라는 관계로 봐야 합니다.**

| 구분      | 원어                      | 방식                                                                  |
| :------ | :---------------------- | :------------------------------------------------------------------ |
| **SJF** | Shortest Job First      | **비선점형** — 실행시작하면 끝날 때까지 안 뺏김, 대기중인 작업 중 **총실행시간이 가장 짧은 것**을 다음에 선택 |
| **SRT** | Shortest Remaining Time | **선점형** — 새 작업이 도착할 때마다 **남은시간**을 비교해서, 더 짧으면 즉시 **선점(교체)**         |

→ 암기: **"SJF는 한번 시작하면 안 바꾸고, SRT는 더 급한(짧은) 게 오면 바로 바꾼다"** — 앞서 다룬 "RM(정적)"이 SJF와 유사한 경직성, "SRT는 매순간 재평가"한다는 점에서 EDF의 동적속성과 유사합니다.

### 도식화 제안

```
[SJF - 비선점]
작업A(5) 실행중 → 작업B(2) 도착해도 A가 끝날때까지 계속 A실행
████████████ (A끝) → ████ (B실행)

[SRT - 선점]
작업A(5) 실행중 → 작업B(2) 도착 → 남은시간(A:3 vs B:2) 비교
────A── (중단!) ████ (B실행, 더 짧아서 선점) ─── (A재개)
```

→ "SJF는 한번 정하면 끝, SRT는 매번 다시 계산해서 바꿀 수 있다"는 게 시각적 차이입니다.

**공통특성**: 둘 다 **평균대기시간을 최소화하는 최적기법**(이론상)이지만, **미래 실행시간을 미리 알아야 한다**는 현실적 한계가 있습니다(추정치로 근사).

### Ⅲ. SSTF — 디스크스케줄링, "탐색시간 최소화"

| 개념                                  | 내용                                         |
| :---------------------------------- | :----------------------------------------- |
| **SSTF** (Shortest Seek Time First) | 디스크헤드의 **현재위치에서 가장 가까운(탐색거리가 짧은) 요청**부터 처리 |

→ "CPU의 '짧은 실행시간'을 디스크의 '짧은 이동거리'로 바꾼 것"이라는 게 SSTF와 SJF의 관계입니다 — **이름의 유사성이 우연이 아니라 같은 그리디 전략을 다른 자원(CPU시간→헤드이동거리)에 적용한 것**입니다.

### 도식화 제안

```
현재 헤드위치: 50
요청 대기열: 10, 90, 30, 70, 60

FCFS라면: 50→10(40)→90(80)→30(60)→70(40)→60(10) = 총 230
SSTF라면: 50→60(10)→70(10)→90(20)→30(60)→10(20) = 총 120

(현재위치에서 가장 가까운 요청부터 순서대로 선택)
```

→ 앞서 다룬 "SQMS/MQMS"의 성능비교처럼, \*\*"탐색시간 총합을 줄인다"\*\*는 게 SSTF의 목표라는 걸 숫자로 보여주면 실전감각이 생깁니다.

### Ⅳ. 공통의 함정 — 기아상태(Starvation), 앞서 다룬 MLQ와 동일한 문제

**함정 방지: 세 기법 모두 "짧은 것 우선"이라는 그리디 전략의 공통된 부작용을 갖고 있다는 걸 놓치면 감점.**

| 기법          | 기아상태 발생 시나리오                              |
| :---------- | :---------------------------------------- |
| **SJF/SRT** | 계속 **짧은 작업들이 새로 들어오면**, 긴 작업은 영원히 뒤로 밀림   |
| **SSTF**    | 헤드 근처로 요청이 계속 몰리면, **먼 곳의 요청**은 영원히 처리 안됨 |

→ 해결책: SJF/SRT는 **에이징(Aging)**(앞서 다룬 MLFQ와 동일기법)으로 대기시간에 따라 우선순위를 보정, SSTF는 **SCAN/LOOK 계열**(헤드가 한 방향으로 쓸고 지나가며 방향전환)로 개선합니다.

→ 암기: **"짧은 것/가까운 것만 계속 우선하면, 긴 것/먼 것은 영원히 기다린다"** — 앞서 다룬 MLQ의 기아상태 문제와 정확히 동일한 구조적 결함입니다.

### Ⅴ. 결론 포인트 (오늘 스케줄링 시리즈 대단원)

SJF/SRT/SSTF는 \*\*"당장 가장 효율적인 선택을 그리디하게 반복"\*\*하는 전략으로, 평균성능은 최적화되지만 **"운이 나쁜 소수(긴 작업/먼 요청)를 계속 희생시키는" 공정성 문제**를 필연적으로 동반합니다 — 이는 오늘 다룬 RM/EDF/MLQ/MLFQ 전체를 관통한 \*\*"평균효율(그리디) vs 공정성(기아상태 방지)"\*\*이라는 근본적 트레이드오프의 또 다른 사례이며, 결국 모든 스케줄링 알고리즘 설계는 이 두 목표 사이 어딘가에서 균형점을 찾는 작업이라는 결론으로, 오늘 하루 다룬 스케줄링 시리즈(RM→MLQ→SJF/SRT/SSTF) 전체를 마무리할 수 있습니다.

### **1. 답안 전개 스토리 (머릿속 핵심 흐름)**

> "식당에서 주문을 처리할 때나 택배 기사가 배송 루트를 짤 때, 효율을 높이기 위해 가장 본능적으로 선택하는 전략은 바로 '가장 빨리 끝나는 일, 가장 가까운 곳부터 먼저 치워버리자!'는 것이다. 이것이 컴퓨터 OS 스케줄링의 근원이자 양날의 검인 \*\*'Shortest(최단/최소) 우선 전략'\*\*이다. CPU 스케줄링에서는 전체 작업의 평균 대기시간을 최소화하기 위해 총 실행 시간이 가장 짧은 놈부터 묵묵히 끝내는 \*\*'SJF(비선점형)'\*\*가 있고, 거기에 한술 더 떠 일하는 도중이라도 남은 시간이 더 짧은 놈이 나타나면 즉시 CPU를 뺏어버리는 독한 \*\*'SRT(선점형)'\*\*가 있다. 한편 하드디스크 스케줄링에서는 현재 디스크 헤드 위치에서 물리적으로 가장 가까운 트랙부터 먼저 읽어 이동 낭비를 없애는 \*\*'SSTF'\*\*가 있다. 이 3가지의 공통점은 '수학적으로는 최적의 효율'을 보장한다는 것이다. 하지만 치명적인 교집합이 있다. 얌체같이 짧은 놈들만 계속 챙기다 보니, 실행 시간이 길거나 위치가 구석에 박힌 불쌍한 작업들은 평생 서비스를 받지 못해 굶어 죽는 \*\*'기아 현상(Starvation)'\*\*에 빠진다는 것이다. 결국 이들은 최적화의 딜레마를 남긴 채, '공평성'을 가미한 HRN이나 SCAN 알고리즘으로 진화하게 된다."

***

### **2. 실제 답안에 쓸 핵심 내용 (암기용)**

#### **I. \[도입] 시스템 최적화의 양날의 검, "Shortest(최단/최소)" 우선 스케줄링 철학**

* **공통 철학:** CPU 연산 시간이나 디스크 헤드의 이동 거리 등 \*\*'비용(시간, 거리)이 가장 적게 드는 작업'\*\*을 무조건 1순위로 처리하여 시스템의 전체적인 평균 대기시간(Average Waiting Time)을 최소화하는 효율성 극대화 스케줄링 기법.
* **공통 한계:** 효율성만 극단적으로 쫓다 보니 \*\*형평성(Fairness)\*\*이 심각하게 파괴됨.

#### **II. \[본론 1] CPU 자원의 낭비 최소화: SJF (비선점형) vs SRT (선점형) 전격 비교**

CPU 스케줄링 분야의 두 형제입니다. 한 번 뺏길 수 있느냐 없느냐의 차이가 핵심입니다.

| **비교 항목**   | **⏱️ SJF (Shortest Job First)**                                 | **⚡ SRT (Shortest Remaining Time First)**                              |
| :---------- | :-------------------------------------------------------------- | :--------------------------------------------------------------------- |
| **선점 여부**   | 🛑 **비선점형 (Non-Preemptive)**                                    | 🚀 **선점형 (Preemptive)**                                                |
| **우선순위 기준** | 준비 큐에 있는 프로세스 중, \*\*'총 CPU 버스트(실행) 예상 시간이 가장 짧은 것'\*\*을 먼저 처리. | 현재 실행 중인 프로세스의 \*\*'남은(Remaining) 시간'\*\*보다 더 짧은 작업이 들어오면 즉시 CPU를 빼앗음. |
| **특징 및 장점** | 일단 CPU를 잡으면 끝날 때까지 안 뺏김. 수학적으로 **평균 대기시간을 가장 줄여주는 최적의 알고리즘.**   | 짧은 작업에 대해 SJF보다 더 즉각적이고 우수한 응답시간(Response Time) 보장.                    |
| **단점 (한계)** | 현실적으로 프로세스가 앞으로 얼마나 실행될지 정확한 시간 예측이 불가능함(비현실적).                 | 잦은 뺏기기(Context Switching)로 인한 오버헤드 과다 발생. 남은 시간 계산의 부하.                |

#### **III. \[본론 2] 디스크 탐색 거리 최소화: SSTF 스케줄링 메커니즘**

SSTF는 디스크 헤드(바늘)를 어떻게 움직일 것인가의 문제입니다.

* **SSTF (Shortest Seek Time First) 개요:** 현재 디스크 헤드의 위치에서 **탐색 거리(Seek Time)가 가장 짧은(가장 가까운) 트랙의 입출력 요청을 먼저 서비스**하는 디스크 스케줄링 기법. (FCFS의 이동 거리 낭비를 개선)
* **작동 예시:** 헤드가 50번 트랙에 있고 대기열에 \[100, 52, 10]이 있다면, 가장 가까운 52번으로 먼저 이동한 뒤, 52번에서 가까운 100번이 아닌 10번으로 역주행하여 이동함.
* **문제점:** 디스크 중간 트랙에 요청이 몰리면 헤드가 중간에서만 왔다 갔다 함. 가장자리(안쪽 끝, 바깥쪽 끝) 트랙의 요청들은 무한정 무시당해 **응답시간의 편차가 극도로 심해짐(불공평).**

#### **IV. \[결론/제언] 'Shortest' 철학의 치명적 결함(기아 현상)과 공평성 보완 전략**

* **(키워드 위주 2줄 마무리)** "이 세 가지 'Shortest 기반' 알고리즘들은 모두 무겁고 멀리 있는 작업이 영원히 서비스를 받지 못하는 치명적인 \*\*'기아 현상(Starvation)'\*\*을 발생시킵니다. 이를 해결하기 위해 CPU 스케줄링에서는 오래 대기한 작업에 가중치를 부여하는 \*\*'에이징(Aging) 기반의 HRN 스케줄링'\*\*으로 진화하였고, 디스크 스케줄링은 엘리베이터처럼 한 방향으로 끝까지 쓸고 지나가며 공평성을 보장하는 \*\*'SCAN (엘리베이터 알고리즘)'\*\*으로 패러다임이 전환되었습니다."
