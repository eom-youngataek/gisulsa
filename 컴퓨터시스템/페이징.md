페이징은 오늘 다룬 하드웨어(캐시·DRAM 등) 답안에서 **소프트웨어(OS) 레벨**로 넘어가는 주제입니다. \*\*"물리메모리가 부족한 문제를 어떻게 속이는가"\*\*라는 하나의 문제의식으로 스토리를 짜겠습니다.

### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (페이징 필요성 - 가상메모리와의 관계) — 3~4줄
Ⅱ. 페이징 구조 및 원리 (본론①, 도식 1개 필수)
Ⅲ. 페이지 부재(Page Fault) 처리 (본론②)
Ⅳ. 페이지 교체알고리즘 (본론③)
Ⅴ. 결론
```

포인트: 개요에서 \*\*"프로세스가 필요로 하는 메모리(논리주소공간)가 실제 물리메모리보다 클 수 있다 → 전체를 다 올리지 않고, 필요한 부분(페이지)만 나눠서 올리는 기법이 페이징"\*\*이라는 인과관계로 시작하면, 왜 페이징이 존재하는지 논리가 섭니다.

### Ⅱ. 페이징 구조 — "논·페·물·프" (4대 구성요소)

| 구성요소                             | 내용                                                   |
| :------------------------------- | :--------------------------------------------------- |
| **논리주소공간**                       | 프로세스가 보는 가상의 메모리공간, 고정크기 **페이지(Page)** 단위로 분할        |
| **물리주소공간**                       | 실제 RAM, 동일크기 **프레임(Frame)** 단위로 분할 (페이지와 프레임 크기는 같음) |
| **페이지테이블**                       | 페이지번호→프레임번호 매핑정보 저장 (프로세스마다 별도 유지)                   |
| **MMU** (Memory Management Unit) | 논리주소를 물리주소로 **실시간 변환**하는 하드웨어                        |

→ 암기: **"논리는 페이지로 쪼개고, 물리는 프레임으로 쪼개고, 페이지테이블이 둘을 연결하고, MMU가 실시간 변환한다"** — 앞서 다룬 "캐시매핑(주소를 Tag+Line+Offset로 쪼갬)"과 정확히 같은 원리(주소를 나눠서 매핑)가 여기서도 반복됩니다.

### 도식화 제안

```
[논리주소] Page# | Offset
     ↓ (페이지테이블 조회)
[페이지테이블] Page0→Frame3, Page1→Frame7...
     ↓
[물리주소] Frame# | Offset
     ↓
[실제 물리메모리(RAM)]
```

→ "논리주소의 Offset은 그대로 유지되고, Page#만 Frame#으로 바뀐다"는 게 핵심 — 앞서 다룬 캐시의 "Tag+Line+Offset" 구조에서 Offset이 그대로 유지되는 원리와 동일합니다.

**+ 페이지테이블 접근 가속화 (심화)**: 페이지테이블도 메모리에 있어서 매번 조회하면 느림 → **TLB**(Translation Lookaside Buffer, 페이지테이블 항목의 **캐시**)를 두어 최근 변환결과를 저장 — 오늘 다룬 "캐시" 개념이 페이지테이블 조회에도 그대로 응용되는 지점입니다.

### Ⅲ. 페이지 부재(Page Fault) 처리 — "탐·확·적·재·복" (5단계)

| 단계       | 내용                                                |
| :------- | :------------------------------------------------ |
| ① **탐지** | 페이지테이블에 유효비트(Valid bit)=0 → 해당 페이지가 물리메모리에 없음을 확인 |
| ② **확보** | 빈 프레임 탐색, 없으면 **페이지교체알고리즘**으로 희생페이지 선정            |
| ③ **적재** | 보조기억장치(디스크)에서 필요한 페이지를 해당 프레임으로 로드                |
| ④ **갱신** | 페이지테이블 업데이트(유효비트=1, 프레임번호 기록)                     |
| ⑤ **복귀** | 페이지폴트를 발생시켰던 명령어 **재실행**                          |

→ 암기: **"없다는 걸 알고, 자리를 찾고, 가져와서, 표시하고, 다시 실행한다"** — 앞서 다룬 "EVM"이나 "WBS 지연대책"처럼, **문제감지→조치→재개**라는 공통 패턴입니다.

### Ⅳ. 페이지 교체알고리즘 — "F·O·L·C" (4대 알고리즘, 배점 핵심)

| 알고리즘                          | 원리                                 | 특징                                                  |
| :---------------------------- | :--------------------------------- | :-------------------------------------------------- |
| **FIFO**                      | 가장 **먼저 들어온** 페이지를 교체              | 구현단순, **Belady's Anomaly**(프레임 늘려도 폴트 증가하는 역설) 발생가능 |
| **OPT** (Optimal)             | **미래에 가장 안 쓸** 페이지를 교체             | 이론상 최적, **실제구현 불가**(미래를 알 수 없음) — 비교기준용             |
| **LRU** (Least Recently Used) | **가장 오래전에 사용**된 페이지를 교체            | OPT에 근접, 실무에서 널리 사용                                 |
| **Clock** (LRU 근사)            | 참조비트(Reference bit)로 **LRU를 근사**구현 | LRU보다 구현 간단, 오버헤드 적음                                |

→ 암기: **"먼저 온 놈(FIFO), 미래를 아는 놈(OPT, 이상적), 최근 안 쓴 놈(LRU), LRU를 대충 흉내내는 놈(Clock)"** — 앞서 다룬 "캐시의 3C 미스모델"에서 **충돌미스를 줄이는 방법**과 같은 문제의식(누구를 내보낼지)이 여기서 재현됩니다.

### Ⅴ. 결론 포인트 (오늘 하드웨어→OS 답안의 연결)

페이징의 본질은 \*\*"물리적 한계를 논리적 추상화로 감춘다"\*\*는 점입니다 — 오늘 다룬 하드웨어 답안들(캐시매핑, CXL, HBM)이 \*\*"물리적 메모리를 어떻게 배치·연결할까"\*\*의 문제였다면, 페이징은 \*\*"그 물리적 한계 자체를 프로세스에게 안 보이게 만드는 소프트웨어적 해법"\*\*이라는 점에서, 하드웨어 최적화와 소프트웨어 추상화가 메모리 시스템을 함께 완성한다는 결론으로 마무리하면 좋습니다.

### **1. 답안 전개 스토리 (머릿속 핵심 흐름)**

> "프로그램을 통째로 메모리에 올리려다 보면, 쪼개진 빈 공간을 다 합치면 용량이 충분한데도 연속된 큰 빈자리가 없어서 프로그램을 못 올리는 '외부 단편화'라는 끔찍한 메모리 낭비가 발생한다. 이를 해결하기 위해 등장한 혁신이 \*\*'페이징(Paging)'\*\*이다. 페이징은 프로그램을 덩어리째 넣는 대신, 똑같은 크기의 일정한 조각(**페이지, Page**)으로 무자비하게 잘게 썰고, 메모리 공간도 그와 똑같은 크기의 빈 액자(**프레임, Frame**)로 나누어, 남는 액자가 보일 때마다 조각을 흩뿌려 끼워 넣는 방식이다. 이렇게 하면 연속된 공간이 필요 없으니 외부 단편화는 완벽히 사라진다. 단, 무조건 똑같은 크기로 자르다 보니 프로그램의 마지막 조각이 액자 크기보다 작아서 액자 안에 남는 빈 공간, 즉 \*\*'내부 단편화'\*\*가 생긴다는 단점이 있다. 또한 조각이 어느 액자에 들어있는지 적어둔 장부(페이지 테이블)를 뒤져보느라 속도가 느려지는데, 이를 극복하기 위해 CPU 안에 \*\*'TLB'\*\*라는 초고속 컨닝 페이퍼(캐시)를 두어 메모리 변환 속도를 극대화한다."

***

### **2. 실제 답안에 쓸 핵심 내용 (암기용)**

#### **I. \[도입] 외부 단편화 해결의 마법, 가상 메모리 페이징 기법 개요**

* **정의:** 프로세스의 논리적 주소 공간을 \*\*'동일한 크기'의 블록인 페이지(Page)\*\*로 나누고, 물리적 주소(RAM) 공간을 같은 크기의 \*\*프레임(Frame)\*\*으로 나누어, 페이지를 빈 프레임에 흩어서 할당하는 불연속 메모리 관리 기법.
* **도입 목적:** 연속 할당 방식에서 발생하는 치명적인 메모리 낭비 현상인 **'외부 단편화(External Fragmentation)'를 근본적으로 해결**하여 다중 프로그래밍의 효율성을 극대화하기 위함.

#### **II. \[본론 1] 페이징 기법의 핵심 동작 메커니즘과 주소 변환 (페이지 테이블)**

CPU는 가상 주소만 알고 있으므로, 이를 실제 RAM의 물리 주소로 바꿔주는 과정이 필수적입니다.

* **주소의 구조 (쪼개기):** CPU가 발행하는 논리 주소는 **`[ p (페이지 번호) | d (오프셋/거리) ]`** 로 나뉩니다.
* **변환 메커니즘 흐름:**
  1. CPU가 논리 주소(p, d)를 요구함.
  2. 메모리에 저장된 \*\*'페이지 테이블(Page Table)'\*\*로 찾아가서, 가상 페이지 번호 'p'가 물리 메모리의 몇 번 프레임 'f'에 들어 있는지 장부를 뒤져서 찾음.
  3. 프레임 번호 'f'에 원래의 오프셋 'd'를 결합하여, \*\*실제 물리 주소 `[ f | d ]`\*\*를 완성하고 메모리 데이터를 읽어옴.

#### **III. \[본론 2] 페이징 기법의 장점과 한계점 (단편화 관점 출제 1순위)**

| **구분** | **핵심 특징 (수험용 키워드)**                      | **상세 설명**                                                                                             |
| :----- | :--------------------------------------- | :---------------------------------------------------------------------------------------------------- |
| **장점** | 🛑 **외부 단편화 완전 해결**                      | - 페이지와 프레임 크기가 완벽히 동일하므로, 비어 있는 어떤 프레임에라도 페이지를 쏙쏙 넣을 수 있어 불연속적 할당이 가능해짐.                              |
| **장점** | 🔄 **메모리 배치 유연성**                        | - 페이지 블록들이 메모리 이곳저곳에 흩어져(Scatter) 존재해도 페이지 테이블만 거치면 모두 찾을 수 있어 빈 공간 활용도 극대화.                          |
| **단점** | ⚠️ **내부 단편화(Internal Fragmentation) 발생** | - 프로그램을 페이지 크기(예: 4KB)로 무조건 나누다 보면, **프로세스의 마지막 페이지는 4KB를 꽉 채우지 못하고 빈 공간이 남게 됨.** (어쩔 수 없는 메모리 낭비 발생) |
| **단점** | 🐌 **성능 저하 및 오버헤드**                      | - 주소를 변환하기 위해 **① 페이지 테이블 읽기, ② 실제 데이터 읽기 등 총 2번의 메모리 접근**이 발생하여 처리 속도가 느려짐.                          |

#### **IV. \[결론/제언] 페이징의 속도 한계 극복을 위한 특수 하드웨어 캐시: TLB**

* **(키워드 위주 2줄 마무리)** "페이징 기법은 메모리를 2번이나 읽어야 하는 속도 저하의 단점이 있습니다. 현대의 운영체제는 이 주소 변환 병목 현상을 타파하기 위해, 가장 최근에 참조된 페이지 테이블의 매핑 정보를 CPU 내부에 임시로 복사해 두는 \*\*연관 메모리 기반의 초고속 하드웨어 캐시인 TLB(Translation Lookaside Buffer)\*\*를 도입하여, 한 번의 접근만으로 주소 변환을 획기적으로 가속화하고 있습니다."
