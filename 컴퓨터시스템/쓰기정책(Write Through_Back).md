쓰기정책은 바로 앞서 다룬 "캐시 주소매핑"과 세트로 자주 출제됩니다. 매핑은 "어디에 저장하는가"였고, 오늘은 \*\*"쓸 때 언제 메모리에도 반영하는가"\*\*의 문제라는 위치관계를 먼저 잡겠습니다.

### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (쓰기정책의 필요성 - 캐시 vs 메모리 데이터 불일치 문제) — 3~4줄
Ⅱ. 2대 쓰기정책 (본론①, 도식 1개 필수)
Ⅲ. 쓰기 미스(Write Miss) 처리방식 (본론②)
Ⅳ. 비교 및 실무 적용
Ⅴ. 결론
```

포인트: 개요에서 \*\*"CPU가 캐시에 값을 쓸 때, 그 순간 메모리에도 똑같이 쓸 것인가(즉시반영) 아니면 나중에 몰아서 쓸 것인가(지연반영)"\*\*라는 질문 하나로 시작하면, 두 정책이 왜 존재하는지 논리가 섭니다.

### Ⅱ. 2대 쓰기정책 — "즉·지" (Write Through/Write Back)

| 정책                       | 원리                                   | 특징                                |
| :----------------------- | :----------------------------------- | :-------------------------------- |
| **Write Through** (즉시쓰기) | 캐시에 쓸 때 **메모리에도 동시에** 씀              | 항상 최신상태 일치, 하지만 매번 메모리 접근(느림)     |
| **Write Back** (지연쓰기)    | 캐시에만 쓰고, **교체(Eviction)될 때** 메모리에 반영 | 빠름, 하지만 **Dirty Bit**로 변경여부 추적 필요 |

→ 암기: **"Write Through는 그때그때 메모리도 갱신(정직), Write Back은 캐시에만 써두고 나갈 때 한꺼번에 정리(효율)"** — 앞서 다룬 "쓰기정책=지출관리"로 비유하면, Write Through는 "카드 긁을 때마다 바로 통장에서 빠짐", Write Back은 "일단 카드로 쓰고 월말에 한번에 정산"과 같은 감각입니다.

### 도식화 제안

```
[CPU 쓰기]
   ↓
[캐시에 기록]
   ├─ Write Through ──→ [메모리도 즉시 기록] (매번)
   │
   └─ Write Back ──→ [Dirty Bit=1 설정] → 캐시에만 유지
                          ↓ (교체(Eviction) 시점에만)
                     [메모리에 반영] (한번에)
```

### Ⅲ. Write Miss 처리방식 — 쓰기정책과 짝을 이루는 개념 (자주 놓치는 포인트)

**함정 방지: 쓰기정책(Through/Back)만 답하면 절반. "캐시에 없는 데이터에 쓸 때는 어떻게 하는가"까지 가야 완성됩니다.**

| 방식                                   | 내용                             | 주로 짝을 이루는 쓰기정책           |
| :----------------------------------- | :----------------------------- | :----------------------- |
| **Write Allocate** (Fetch on Write)  | 쓰기 미스 시 **해당 블록을 캐시로 가져온 후** 씀 | **Write Back**과 주로 결합    |
| **No-Write Allocate** (Write Around) | 캐시로 안 가져오고 **메모리에 직접** 씀       | **Write Through**와 주로 결합 |

→ 암기: **"Write Back은 캐시에 자주 다시 쓸 거니 가져와서 쓰고(Allocate), Write Through는 어차피 메모리에도 쓰니 그냥 메모리에 바로 쓴다(No-Allocate)"** — 이 조합 논리를 이해하면 4가지 조합 중 왜 이 2개가 대표조합인지 설명이 가능해집니다.

### Ⅳ. 비교 및 실무 적용 — "일·속·복" (일관성/속도/구현복잡도)

| 구분             | Write Through      | Write Back                      |
| :------------- | :----------------- | :------------------------------ |
| **데이터일관성**     | **높음**(항상 메모리=캐시)  | 낮음(Dirty 상태 동안 불일치)             |
| **속도**         | 느림(매번 메모리 접근)      | **빠름**(캐시 접근만)                  |
| **구현복잡도**      | 단순                 | **Dirty Bit 관리, 교체시 쓰기 필요**(복잡) |
| **멀티코어 캐시일관성** | 유리(항상 최신)          | 별도 **캐시코히런시 프로토콜**(MESI 등) 필요   |
| **실무사례**       | 신뢰성 중요(금융/저장장치 일부) | **대부분의 CPU 캐시**(L1/L2/L3)       |

→ "왜 대부분 CPU가 Write Back을 쓰는가"의 답: **CPU-메모리 속도차가 워낙 커서, 매번 메모리에 쓰면 캐시의 존재의미가 없어지기 때문**입니다. 반면 멀티코어 환경에서는 여러 캐시 간 데이터 불일치 문제(캐시 코히런시)가 생겨 MESI 프로토콜 같은 별도 해결기법이 필요하다는 심화 연결을 넣으면 좋습니다.

### Ⅴ. 결론 포인트 (차별화 한 줄)

쓰기정책 선택은 \*\*"일관성(Consistency) vs 성능(Performance)"\*\*의 트레이드오프이며, 이는 앞서 다룬 "캐시매핑방식"의 트레이드오프(충돌율 vs 구현복잡도)와 같은 축에 있는 문제입니다 — 결국 컴퓨터구조의 캐시설계 전체가 \*\*"완벽한 정합성과 최고속도를 동시에 가질 수 없다"는 근본적 제약을 어떻게 절충하는가"\*\*의 반복이라는 결론으로 마무리하면, 두 답안이 하나의 큰 원리로 연결됩니다.

**1. 답안 전개 스토리 (머릿속 핵심 흐름)**

> "CPU가 계산한 결과를 장부에 적을 때, CPU 바로 옆의 캐시(임시 수첩)에만 적을지, 아니면 저 멀리 있는 주기억장치(큰 원장)에도 똑같이 적을지 결정해야 하는데 이것이 \*\*'캐시 쓰기 정책'\*\*이다. \*\*① 'Write Through(즉시 쓰기)'\*\*는 수첩에 적을 때마다 원장에도 꼬박꼬박 가서 똑같이 적어두는 바른생활 방식이다. 데이터는 절대 틀릴 일이 없지만, 느린 원장까지 매번 다녀와야 해서 시스템이 굼벵이가 된다. 반면 \*\*② 'Write Back(나중에 쓰기)'\*\*은 일단 빠른 수첩에만 휘갈겨 적어놓고, 나중에 수첩 공간이 모자라 그 페이지를 찢어 버릴 때쯤(교체될 때) 원장에 한꺼번에 몰아서 적어두는 벼락치기 방식이다. 속도는 엄청나게 빠르지만, 중간에 누군가 원장을 들춰보면 옛날 데이터를 읽어가게 되는 치명적인 '데이터 불일치'가 발생한다. 현대 컴퓨터는 속도가 생명이므로, 이 불일치를 해결하는 복잡한 기술을 붙여서라도 대부분 Write Back 방식을 쓴다."

***

### **2. 실제 답안에 쓸 핵심 내용 (암기용)**

#### **I. \[도입] 데이터 일관성(Consistency)과 속도의 딜레마, 캐시 쓰기 정책 개요**

* **정의:** CPU가 연산을 수행하고 그 결과를 캐시 메모리에 기록(Write)할 때, **어느 시점에 하위 계층인 주기억장치(Main Memory)에 데이터를 업데이트할 것인지**를 결정하는 정책.
* **목적:** 캐시와 메인 메모리 간의 \*\*데이터 일관성(Data Consistency)\*\*을 보장할 것인지, 아니면 느린 메인 메모리 접근을 줄여 **시스템 처리 성능**을 극대화할 것인지의 트레이드오프(Trade-off) 조율.

#### **II. \[본론 1] 캐시 쓰기 정책의 양대 산맥: Write Through vs Write Back 전격 비교**

답안지의 가장 큰 면적을 차지해야 하는 핵심 비교표입니다.

| **비교 항목**   | **📝 Write Through (즉시 쓰기)**                                     | **⚡ Write Back (지연 쓰기 / 나중에 쓰기)**                                             |
| :---------- | :--------------------------------------------------------------- | :---------------------------------------------------------------------------- |
| **동작 메커니즘** | CPU가 데이터를 캐시에 기록할 때, **항상 메인 메모리에도 동시에 기록**하는 방식                 | CPU가 데이터를 **캐시에만 기록**해 두었다가, 해당 캐시 블록이 **메모리로 쫓겨날 때(교체될 때) 비로소 한꺼번에 기록**하는 방식 |
| **데이터 일관성** | **\[장점] 완벽 보장 (100% 일치)** - 갑작스런 전원 차단에도 메모리 데이터가 안전하게 보존됨       | **\[단점] 일시적 불일치 발생** - 캐시에는 최신 값이, 메모리에는 옛날 값이 존재하는 타이밍(Inconsistency) 발생     |
| **시스템 성능**  | **\[단점] 속도 저하 및 병목 현상** - 쓰기 연산마다 느린 메인 메모리에 접근해야 하므로 버스 트래픽이 심함 | **\[장점] 시스템 전체 속도 획기적 향상** - 메인 메모리 접근 횟수를 최소화하여 시스템 성능 극대화                   |
| **적용 환경**   | 데이터의 **안정성/신뢰성**이 극도로 중요한 금융/항공 시스템 등에 일부 적용                     | 속도가 생명인 **현대 대부분의 고성능 멀티코어 CPU**에서 표준으로 채택                                    |

#### **III. \[본론 2] Write Back 방식의 성능을 뒷받침하는 핵심 무기: Dirty Bit (수정 비트)**

Write Back 방식을 설명할 때 \*\*'Dirty Bit'\*\*라는 단어가 안 들어가면 점수가 깎입니다.

* **Dirty Bit의 역할:** Write Back 방식에서는 캐시의 데이터가 쫓겨날 때 메모리에 쓸지 말지를 결정해야 합니다. 만약 CPU가 데이터를 한 번이라도 수정했다면 해당 블록의 꼬리표인 **Dirty Bit를 '1'로 세팅**합니다. (이때의 상태를 '더러워졌다(Dirty)'고 표현함)
* **동작 원리:** 캐시 공간이 꽉 차서 특정 블록을 버려야 할 때, **Dirty Bit가 '1'인 놈만 메인 메모리에 덮어쓰기(업데이트)를 수행**하고, '0'인 놈(수정된 적 없는 놈)은 그냥 쓰레기통에 바로 버림으로써 불필요한 메모리 접근을 완벽히 차단합니다.

#### **IV. \[결론/제언] 다중 코어(Multi-Core) 환경에서의 캐시 일관성(Cache Coherence) 문제 해결 제언**

* **(키워드 위주 2줄 마무리)** "현재 대부분의 CPU는 성능을 위해 Write Back 방식을 사용하지만, 멀티코어 환경에서는 Core 1이 캐시에만 업데이트한 최신 데이터를 Core 2가 메인 메모리에서 옛날 데이터로 잘못 읽어가는 \*\*'캐시 일관성(Cache Coherence) 문제'\*\*가 치명적으로 발생합니다. 이를 해결하기 위해, 각 캐시의 상태를 M(수정), E(배타), S(공유), I(무효) 4가지로 관리하는 \*\*하드웨어 기반의 MESI 프로토콜(스누핑 방식)\*\*이 반드시 병행 적용되어야 합니다."
