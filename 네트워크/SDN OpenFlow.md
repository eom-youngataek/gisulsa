포인트: 개요에서 **"앞서 다룬 VXLAN·SRv6가 'SDN 위에서 실제로 트래픽을 어떻게 나를 것인가'를 다루는 데이터 평면 기술이었다면, SDN(Software Defined Networking) 자체는 그 모든 것의 전제가 되는 더 근본적인 아키텍처 혁명 — '전통 네트워크 장비에서 제어 평면(경로를 결정하는 두뇌)과 데이터 평면(패킷을 실제로 나르는 손발)이 하나의 하드웨어 안에 고정 결합되어 있던 구조를 물리적으로 분리'하는 패러다임이다 — 기존 라우터·스위치는 각자 독립적으로 자신만의 라우팅 알고리즘을 실행해 네트워크 전체를 조율하려면 장비 수백 대를 CLI로 일일이 설정해야 했는데, 2008년 스탠퍼드 연구진이 제안한 OpenFlow는 이 제어 로직을 중앙 컨트롤러 소프트웨어로 뽑아내고 장비는 그 지시를 받아 단순히 패킷을 전달만 하는 '멍청한 스위치(Dumb Switch)'로 만듦으로써, 네트워크를 마치 하나의 프로그래밍 가능한 컴퓨터처럼 다룰 수 있게 한 SDN의 최초이자 가장 대표적인 구현 프로토콜"**이라는 한 줄로 시작하면 전체 맥락이 드러납니다.

#### Ⅱ. SDN 핵심 원리 및 OpenFlow 동작 방식

**가. 전통 네트워크 vs SDN 아키텍처 비교**

```
[전통 네트워크: 제어 평면과 데이터 평면이 장비마다 결합]

스위치A(제어+데이터)  스위치B(제어+데이터)  스위치C(제어+데이터)
  각자 STP·라우팅 알고리즘을 독립적으로 실행
  → 네트워크 전체 정책 적용 시 장비마다 개별 설정 필요 🚨
  → 장애·정책 변경 시 전체 재구성에 많은 시간 소요

[SDN: 제어 평면을 중앙으로 분리]

         ┌──────────────────┐
         │   SDN 컨트롤러      │  ← 제어 평면(중앙 집중)
         │  (네트워크 전체 지도  │
         │   보유, 정책 결정)   │
         └─────────┬────────┘
                    │ OpenFlow(Southbound API)
      ┌─────────────┼─────────────┐
      ↓             ↓             ↓
  스위치A         스위치B         스위치C   ← 데이터 평면(단순 전달만)
  (플로우테이블만  (플로우테이블만  (플로우테이블만
   보유·전달)      보유·전달)      보유·전달)

→ 네트워크 전체를 하나의 소프트웨어 프로그램처럼 중앙에서 제어
```

**나. OpenFlow 핵심 동작 원리**

```
[OpenFlow 플로우 처리 흐름]

새로운 패킷이 스위치에 도착
       ↓
스위치: 자신의 플로우 테이블(Flow Table)에서 일치하는 규칙 검색
       ↓
  ①일치하는 규칙 있음(Table Hit)
    → 규칙에 정의된 액션 즉시 실행(전달·삭제·수정 등)
       ↓
  ②일치하는 규칙 없음(Table Miss)
    → 패킷을 SDN 컨트롤러에 문의(Packet-In 메시지)
    → 컨트롤러가 새 규칙을 계산해 스위치에 설치(Flow-Mod 메시지)
    → 이후 동일 패턴의 패킷은 스위치가 직접 처리(Table Hit)

[플로우 테이블 엔트리 구조]

Match Fields(매칭 조건) + Actions(처리 동작) + 통계(카운터)
  예: 출발지IP=10.0.0.1, 목적지포트=80 → Action: 포트2로 전달
     앞서 다룬 LPM(최장 프리픽스 매칭)과 유사하게
     더 구체적인 매칭 규칙이 우선 적용됨
```

**다. SDN 3계층 구조**

|계층|구성요소|역할|
|---|---|---|
|**애플리케이션 계층**|로드밸런서·방화벽 앱·오케스트레이터|네트워크 정책·비즈니스 로직 정의|
|**제어 계층**|SDN 컨트롤러(OpenDaylight·ONOS 등)|네트워크 전체 상태 파악, 플로우 규칙 계산·배포|
|**데이터(인프라) 계층**|OpenFlow 지원 스위치|컨트롤러 지시에 따라 패킷 전달만 수행|

#### Ⅲ. 비교 및 적용 체계

**가. 전통 네트워크 vs SDN 전면 비교**

|비교 항목|전통 네트워크|SDN|
|---|---|---|
|**제어·데이터 평면**|장비마다 결합(분산)|**중앙 분리**(제어는 컨트롤러, 데이터는 스위치) ✅|
|**설정 방식**|장비별 개별 CLI 설정|**중앙에서 프로그래밍 가능**(API 기반) ✅|
|**네트워크 가시성**|장비별 파편화된 정보|**컨트롤러가 전체 토폴로지 통합 보유** ✅|
|**정책 변경 속도**|느림(장비 수만큼 반복 작업)|**빠름**(중앙에서 일괄 배포) ✅|
|**장비 지능**|높음(자체 판단)|낮음(컨트롤러 지시 따름)|
|**단일 장애점 위험**|분산되어 상대적으로 낮음|**컨트롤러 장애 시 영향 범위 큼** 🚨(이중화 필수)|

**나. OpenFlow 버전별 발전**

|버전|주요 개선|
|---|---|
|**OpenFlow 1.0(2009)**|최초 표준, 단일 플로우 테이블|
|**OpenFlow 1.3(2012)**|다중 플로우 테이블(파이프라인), 실무 채택 확산|
|**OpenFlow 1.5(2015)**|확장 매치 필드, 세밀한 통계 지원|

**다. SDN 컨트롤러 비교**

|컨트롤러|특징|
|---|---|
|**OpenDaylight(ODL)**|Linux Foundation 주도, 다수 Southbound 프로토콜 지원(범용성)|
|**ONOS**|통신사업자(Telco) 환경 특화, 고가용성·확장성 강조|
|**Ryu**|Python 기반, 경량·연구/교육 환경에서 널리 활용|

**라. SDN vs 전통 네트워크 자동화(스크립트 기반) 비교**

|비교 항목|전통 자동화(Ansible 등 스크립트)|SDN|
|---|---|---|
|**제어 방식**|장비별 CLI 명령을 스크립트로 대량 실행|**실시간 중앙 제어**(Reactive/Proactive)|
|**실시간 대응**|배치성(스크립트 재실행 필요)|**Packet-In 이벤트 기반 즉각 대응** ✅|
|**네트워크 상태 인지**|제한적(스크립트가 상태를 직접 파악 안 함)|**컨트롤러가 전체 상태를 실시간 파악** ✅|
|**적합 상황**|정적·반복적 설정 배포|동적·실시간 트래픽 엔지니어링|

**마. 실무 적용 시 고려사항**

|고려사항|내용|
|---|---|
|**컨트롤러 이중화**|단일 장애점 위험을 낮추기 위해 다중 컨트롤러 구성(앞서 다룬 Raft류 합의 알고리즘으로 컨트롤러 간 상태 동기화)|
|**Reactive vs Proactive**|Table Miss마다 컨트롤러에 문의(Reactive)하면 지연 발생 → 자주 쓰이는 규칙은 사전에 미리 설치(Proactive)하는 하이브리드 설계|
|**확장성 한계**|대규모 데이터센터에서는 모든 Table Miss를 중앙 컨트롤러가 처리하면 병목 발생 가능 → 앞서 다룬 VXLAN 등 오버레이와 조합해 부담 분산|
|**레거시 장비 공존**|전면적 OpenFlow 전환이 어려운 환경에서는 하이브리드(전통+SDN) 네트워크 설계 필요|

---

**(제언)** "SDN과 OpenFlow의 핵심 통찰은 네트워크 장비의 '지능'을 개별 하드웨어에서 떼어내 소프트웨어로 중앙화함으로써, 네트워크를 마치 애플리케이션처럼 코드로 정의하고 버전 관리하며 배포할 수 있게 만들었다는 데 있으며, 이는 서버 인프라가 물리 서버에서 가상화·클라우드로 진화한 것과 정확히 같은 궤적을 네트워크 영역에서 뒤늦게 밟은 것으로 볼 수 있습니다. 다만 모든 패킷 처리 결정을 중앙 컨트롤러에 의존하는 순수 Reactive 방식은 대규모 환경에서 컨트롤러 자체가 병목이자 단일 장애점이 될 수 있으므로, 실무에서는 자주 발생하는 트래픽 패턴에 대한 규칙을 미리 설치해두는 Proactive 방식과 결합하고 컨트롤러 자체도 다중화해 가용성을 확보하는 것이 필수적이며, 오늘날 클라우드 데이터센터에서는 순수 OpenFlow보다 앞서 다룬 VXLAN 오버레이와 결합된 형태로 SDN 원리가 더 널리 실현되고 있다는 점에서, OpenFlow는 최초의 상징적 구현체이자 이후 등장한 다양한 Southbound 프로토콜(P4·NETCONF 등)의 개념적 토대로 이해하는 것이 정확합니다.
