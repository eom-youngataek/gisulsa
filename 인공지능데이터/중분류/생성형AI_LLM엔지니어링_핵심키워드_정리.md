# 생성형AI/LLM 엔지니어링 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 등장배경 → 아키텍처 구조도 → 기존기술과 비교표 → 적용 시 고려사항/한계

---

## 1. Advanced RAG vs Modular RAG

**등장배경**
> 기존(Naive) RAG는 "질문→검색→생성" 단순 1회 파이프라인이라 검색 품질이 나쁘면 답변도 나빠지는 한계가 있음. 검색·생성 단계 각각을 개선하기 위해 발전

**아키텍처 구조도**
```
[Naive RAG]   질문 → 검색(1회) → 프롬프트결합 → LLM생성 → 답변

[Advanced RAG] 질문 → 질의 재작성(Query Rewriting) → 검색 → 재순위화(Re-ranking) 
              → 압축(Compression) → LLM생성 → 답변
              (검색 전/후 단계를 보강한 "선형 개선형")

[Modular RAG]  질문 → [라우팅모듈] → (검색모듈/캐시모듈/도구호출모듈 등 중 선택)
              → 여러 모듈을 자유롭게 조합·반복(Pipeline이 아닌 "레고블록형")
```

**비교표**

| 구분 | Naive RAG | Advanced RAG | Modular RAG |
|---|---|---|---|
| 구조 | 단일 선형 | 선형+전후처리 보강 | 모듈 조합(비선형) |
| 유연성 | 낮음 | 중간 | 높음(라우팅·반복 가능) |
| 예시기법 | 단순 벡터검색 | Query Rewriting, Re-ranking | Self-RAG, Routing, Fusion |

**적용 시 고려사항/한계**
> 모듈이 많아질수록 응답 지연(Latency)과 운영 복잡도가 증가 → 실시간성이 중요한 서비스에는 Advanced RAG가 더 적합할 수 있음

## 2. 파인튜닝 vs RAG

**등장배경**
> LLM에 "최신정보"나 "기업 내부지식"을 반영하는 방법으로, 모델 자체를 재학습(파인튜닝)할지, 검색으로 외부지식을 주입(RAG)할지 선택이 필요해짐

**아키텍처 구조도**
```
[파인튜닝]  사전학습LLM + 기업데이터(학습) → 가중치 업데이트 → 전용모델 생성

[RAG]      사전학습LLM(고정) + 외부DB(실시간검색) → 프롬프트에 검색결과 삽입 → 답변생성
           (모델 가중치는 변경하지 않음)
```

**비교표**

| 구분 | 파인튜닝 | RAG |
|---|---|---|
| 지식갱신 | 재학습 필요(느림, 비용↑) | DB만 갱신(빠름) |
| 정보 출처 | 모델 내부에 암묵적으로 내재 | 명시적 문서 인용 가능(출처 추적 용이) |
| 적합한 경우 | 말투·형식·전문용어 등 "스타일" 학습 | 최신정보·사실기반 답변이 필요할 때 |

**적용 시 고려사항/한계**
> 파인튜닝은 GPU·데이터 구축비용이 크고 잦은 정보갱신에 부적합. RAG는 검색 품질이 낮으면 환각(Hallucination)이 그대로 노출됨 → 실무에서는 두 가지를 병행(RAFT처럼)하는 경우가 많음

---

## 3. RLHF vs RAFT 파이프라인

**등장배경**
> 단순히 다음 단어를 잘 맞히도록 학습된 LLM은 "사람이 선호하는 답변"을 못 줄 수 있음 → 인간 피드백으로 정렬(Align)하는 기법이 필요해짐

**아키텍처 구조도**
```
[RLHF] ①사전학습LLM → ②SFT(지도학습 미세조정) 
       → ③사람이 답변 여러개에 순위 매김(보상모델 학습) 
       → ④강화학습(PPO)으로 보상이 높은 답변을 하도록 LLM 업데이트

[RAFT] ①질문+검색된 문서(관련문서+방해문서 혼합) 입력 
       → ②"관련 문서만 인용해 답하도록" 파인튜닝 
       → ③RAG 환경에 특화된 모델 생성(검색결과를 잘 활용하는 능력 학습)
```

**비교표**

| 구분 | RLHF | RAFT |
|---|---|---|
| 목적 | 사람의 선호/가치에 맞게 정렬 | RAG 환경에서 검색결과를 잘 활용하도록 학습 |
| 핵심기법 | 보상모델 + 강화학습(PPO) | 지도학습 파인튜닝(SFT 변형) |
| 학습난이도 | 높음(보상모델 별도 필요, 불안정) | 상대적으로 낮음(SFT 기반) |

**적용 시 고려사항/한계**
> RLHF는 보상모델 설계가 까다롭고 비용이 큼(최근 DPO 등 대안 등장). RAFT는 RAG 특화이므로 일반 대화능력 향상에는 한계

## 4. MCP (Model Context Protocol)

**등장배경**
> LLM이 외부 도구(DB, API, 파일시스템 등)와 연동하려면 각 도구마다 별도의 연결코드를 만들어야 했음(N×M 문제) → 표준화된 연결 규약이 필요해짐

**아키텍처 구조도**
```
[LLM 애플리케이션] ←(MCP 표준 프로토콜)→ [MCP 서버1: DB조회]
                                        [MCP 서버2: 파일시스템]
                                        [MCP 서버3: 외부API]
(USB처럼 "표준 커넥터"로 어떤 도구든 꽂아서 사용 가능)
```

**비교표**

| 구분 | 기존 방식(개별 연동) | MCP |
|---|---|---|
| 연동방식 | 도구마다 커스텀 코드 작성 | 표준 프로토콜로 통일 |
| 확장성 | 도구 추가 시마다 개발 필요 | 신규 MCP서버만 등록하면 즉시 사용 |
| 비유 | 기기마다 다른 충전케이블 | USB-C(범용 표준) |

**적용 시 고려사항/한계**
> 표준이 정착 중이라 보안 통제(악성 MCP서버 연결 시 데이터 유출 위험)가 중요 — OWASP LLM 보안위협과 직결되며, 신뢰된 MCP서버만 화이트리스트로 관리해야 함

## 5. Text2SQL

**등장배경**
> 비개발자(현업)도 자연어로 데이터를 조회하고 싶은 수요 증가 → SQL을 몰라도 LLM이 자연어를 SQL로 번역

**아키텍처 구조도**
```
자연어 질문("지난달 매출 1위 제품은?") → LLM(+DB스키마 정보 제공) 
→ SQL문 생성("SELECT product, SUM(sales)... ORDER BY ... LIMIT 1") 
→ DB실행 → 결과 자연어로 재변환 → 답변
```

**비교표**

| 구분 | 기존 BI 도구 | Text2SQL |
|---|---|---|
| 사용방법 | 정해진 대시보드/필터 클릭 | 자유로운 자연어 질문 |
| 유연성 | 사전 정의된 질문만 가능 | 새로운 질문도 즉석 대응 |
| 위험 | 낮음(고정쿼리) | SQL 인젝션·잘못된 쿼리 생성 위험 |

**적용 시 고려사항/한계**
> 복잡한 조인·서브쿼리에서 정확도 저하, 잘못된 SQL이 운영DB에 실행되지 않도록 읽기전용(Read-only) 권한 제한 및 쿼리 검증 단계 필수

---

## 6. sLLM vs LLM

**등장배경**
> 거대 LLM(GPT급)은 비용·응답지연이 크고 온프레미스 구축이 어려움 → 특정 업무에 경량화된 모델(sLLM)로 비용·보안 문제를 해결하려는 수요 발생

**아키텍처 구조도**
```
[LLM]  수백억~수조 파라미터, 클라우드API 호출, 범용 지식 보유

[sLLM] 수억~백억 파라미터, 온프레미스/엣지 탑재 가능, 
       특정 도메인(예: 의료상담)에 특화 파인튜닝
```

**비교표**

| 구분 | LLM | sLLM |
|---|---|---|
| 파라미터 규모 | 매우 큼 | 작음(경량화) |
| 구축환경 | 주로 클라우드 API | 온프레미스/엣지(온디바이스) 가능 |
| 비용/속도 | 높은 비용, 응답 지연 | 저비용, 빠른 응답 |
| 범용성 | 다양한 작업 모두 가능 | 특정 도메인 특화 |

**적용 시 고려사항/한계**
> sLLM은 일반지식이나 복잡한 추론에서 LLM보다 성능이 떨어짐 → 보안이 중요한 폐쇄망 환경(공공기관, 금융사)에서는 sLLM이 적합, 범용 챗봇은 LLM이 적합

---

## 7. 멀티에이전트시스템(MAS, Multi-Agent System)

**등장배경**
> 단일 AI 에이전트로는 복잡한 업무(기획→실행→검증)를 한번에 처리하기 어려움 → 역할을 나눈 여러 에이전트가 협업하도록 분업화

**아키텍처 구조도**
```
[사용자 요청] → [관리자(Orchestrator) 에이전트]
               ├─→ [기획 에이전트] 
               ├─→ [코딩 에이전트]
               ├─→ [검증 에이전트]
               └─→ (결과 통합) → 최종 출력
```

**비교표**

| 구분 | 단일 에이전트 | 멀티 에이전트(MAS) |
|---|---|---|
| 처리방식 | 한 모델이 모든 일 처리 | 역할별 전문 에이전트가 분업 |
| 복잡업무 대응 | 한계 있음 | 단계별 분업으로 정교한 처리 가능 |
| 단점 | - | 에이전트 간 통신 오버헤드, 무한루프·비용 폭증 위험 |

**적용 시 고려사항/한계**
> 에이전트 수가 늘수록 비용·지연 증가, 에이전트 간 책임 소재/오류 전파 관리(거버넌스)가 중요 — 기업 업무프로세스(RPA+AI) 자동화에 적용 시 모니터링 체계 필수

---

## 8. 프롬프트 엔지니어링

**등장배경**
> LLM은 입력(프롬프트)에 따라 답변 품질이 크게 달라짐 → 모델 재학습 없이 "질문을 잘 설계"해서 원하는 답을 끌어내는 기법 발전

**아키텍처 구조도**
```
[프롬프트 구성요소] 역할지정(System) + 맥락(Context) + 예시(Few-shot) + 출력형식 지정
→ LLM → 원하는 형태의 답변
```

**비교표**

| 기법 | 방식 | 효과 |
|---|---|---|
| Zero-shot | 예시 없이 바로 질문 | 간단하지만 정확도 낮을 수 있음 |
| Few-shot | 예시 1~2개 제시 후 질문 | 패턴 학습 효과로 정확도 향상 |
| Chain-of-Thought(CoT) | "단계별로 생각해봐" 유도 | 복잡한 추론문제 정답률 향상 |

**적용 시 고려사항/한계**
> 같은 모델도 프롬프트에 따라 결과가 들쭉날쭉(재현성 문제), 프롬프트 인젝션(악의적 지시 주입) 보안 위협에 노출 — 가드레일과 함께 설계 필요

---

## 9. A/B 테스팅 (모델 검증)

**등장배경**
> 새로운 AI 모델/프롬프트를 실제 서비스에 적용하기 전, "기존 모델보다 정말 더 나은지"를 객관적으로 검증할 필요

**아키텍처 구조도**
```
사용자 트래픽 → [무작위 분할]
              ├─→ A그룹(기존 모델) → 결과 측정
              └─→ B그룹(신규 모델) → 결과 측정
              → 통계적 검증(t검정 등)으로 우열 판정
```

**비교표**

| 구분 | 오프라인 검증(벤치마크) | A/B 테스팅 |
|---|---|---|
| 환경 | 정적 테스트셋 | 실제 사용자 트래픽 |
| 신뢰성 | 실제 사용 패턴과 차이 가능 | 실서비스 반응을 직접 반영 |
| 비용/위험 | 낮음 | 신규모델 결함 시 일부 사용자 영향 |

**적용 시 고려사항/한계**
> 충분한 표본 크기와 검증기간 확보 필요(너무 짧으면 통계적으로 유의하지 않음), 신규모델이 나쁠 경우를 대비한 신속한 롤백(이전 키워드: Blue-Green/Canary 배포)체계 연계 필요

---

## 📌 키워드 간 연결 요약

```
파인튜닝 vs RAG ──┬──→ RLHF(파인튜닝의 정렬기법) 
                  └──→ RAFT(RAG+파인튜닝의 결합형)

Advanced/Modular RAG ──→ Text2SQL (RAG의 응용 — DB를 외부지식으로 활용)
                      └──→ MCP (RAG가 호출하는 외부도구 연결 표준)

LLM vs sLLM ──→ 멀티에이전트시스템(MAS) (여러 sLLM/LLM이 역할분담해 협업)

프롬프트엔지니어링 ──→ A/B테스팅 (프롬프트/모델 변경의 효과를 실증적으로 검증)
```
