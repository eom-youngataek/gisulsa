### **분산 데이터베이스 무결성 보장: 2단계 커밋 (2PC)**

#### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (왜 분산 환경에서 단순 커밋으로는 무결성이 깨지는가)
Ⅱ. 2PC 핵심 동작 원리 (2단계 상세)
Ⅲ. 한계점 및 대안 비교
Ⅳ. 결론
```

포인트: 개요에서 \*\*"물리적으로 쪼개져 서로 멀리 떨어진 분산 데이터베이스 환경에서 '모든 DB 노드가 죽어도 같이 죽고(Rollback) 살아도 같이 사는(Commit)' 완벽한 분산 무결성(ACID) 보장 프로토콜이다 — 돈을 송금할 때 출금 은행 DB와 입금 은행 DB가 쪼개져 있다면, 출금만 성공하고 입금이 실패하는 무결성 대참사를 막아야 한다. 앞서 다룬 ARIES 회복 알고리즘이 단일 노드 장애 복구의 황금 열쇠라면, 2PC는 분산 노드 전체의 원자성 보장 프로토콜이며, Raft가 합의로 단 하나의 진실을 정하는 구조라면 2PC는 합의로 단 하나의 커밋 결과를 정하는 구조"\*\*라는 한 줄로 시작하면 전체 맥락이 드러납니다.

***

#### Ⅱ. 2PC 핵심 동작 원리

**가. 참여자 구성**

| 역할                    | 내용                 | 핵심 키워드                      |
| :-------------------- | :----------------- | :-------------------------- |
| **조정자 (Coordinator)** | 2PC 전체 진행 주관·결정권자  | 트랜잭션 관리자(TM) / 단일 장애점(SPOF) |
| **참여자 (Participant)** | 실제 데이터 처리·투표·실행 노드 | 자원 관리자(RM) / 복수 DB 노드       |

***

**나. 2단계 상세 동작**

```
[2PC 전체 흐름]

클라이언트: "출금 1만원·입금 1만원 처리해줘"
       ↓
조정자: 트랜잭션 시작·참여자 목록 확정

━━━━━━━━━━━━━━━━━━━━━━━
1단계: 준비 단계 (Prepare Phase)
━━━━━━━━━━━━━━━━━━━━━━━
조정자 → 전체 참여자: "Prepare!" 메시지 전송
       ↓
각 참여자:
  WAL 로그 기록 (앞서 다룬 WAL 프로토콜)
  데이터 임시 잠금(Lock) 설정
  커밋 가능 여부 판단
       ↓
  가능: "Vote Yes" 응답 + 준비 상태 유지
  불가: "Vote No" 응답 + 즉시 롤백

━━━━━━━━━━━━━━━━━━━━━━━
2단계: 결정 단계 (Commit Phase)
━━━━━━━━━━━━━━━━━━━━━━━
조정자: 모든 투표 수집·결정

[만장일치 Yes]
  조정자 → 전체 참여자: "Commit!" 명령
  참여자: 실제 커밋 실행·잠금 해제
  조정자: 트랜잭션 완료 기록

[단 하나라도 No 또는 타임아웃]
  조정자 → 전체 참여자: "Rollback!" 명령
  참여자: 전체 롤백·잠금 해제
  조정자: 트랜잭션 실패 기록
```

***

#### 핵심 내용 (암기용)

| **핵심 척도**    | **📊 1단계: 준비 단계 (Prepare Phase) 🚨**                                     | **🔑 2단계: 결정 단계 (Commit Phase) 🚨**                                             | **🏁 2PC의 치명적 한계 (Blocking) 💯**                                                           |
| :----------- | :----------------------------------------------------------------------- | :------------------------------------------------------------------------------ | :----------------------------------------------------------------------------------------- |
| **프로토콜 액션**  | 조정자가 참여 노드들에게 데이터 임시 잠금(Lock) 및 트랜잭션 준비 가능 여부를 묻고 응답을 대기함                | 모든 노드의 응답 결과를 취합하여 최종 성공(Commit) 혹은 전체 철회(Rollback) 명령을 동보 전송함                  | 통신 장애 발생 시 노드들의 트랜잭션 잠금이 영원히 풀리지 않아 시스템 전체가 마비되는 문제                                        |
| **상태 전이 🚨** | **\[질의·응답 🚨]** 참가자는 준비가 되면 WAL 로그에 상태를 기록하고 **'Vote Yes'** 응답 송신 후 락 유지 | **\[만장일치 원칙 💯]** 단 하나의 노드라도 **'Vote No'** 를 보내거나 타임아웃이 발생하면 **전체 Rollback** 강제 | **\[동기식 블로킹(Blocking) 💯]** 조정자가 Phase 2 명령을 보내기 직전 장애로 죽어버리면 참여 노드들은 락을 쥔 채 영원히 대기 상태에 갇힘 |

***

#### Ⅲ. 한계점 및 대안 비교

**가. 2PC 3대 한계**

```
[한계 1: 블로킹(Blocking)]
조정자 장애 → 참여자 전체 락 보유 채 무한 대기
→ 앞서 다룬 Raft의 리더 자동 재선출과 달리
  2PC는 조정자 복구 전까지 전체 시스템 중단 🚨

[한계 2: 성능 병목]
동기식 2라운드 통신 → 네트워크 지연 × 2 비용
참여자 수 증가 → 응답 대기 시간 선형 증가
→ 앞서 다룬 BASE의 결과적 일관성과 정반대의 성능 트레이드오프

[한계 3: 단일 장애점(SPOF)]
조정자 1개가 전체 트랜잭션 제어
→ 조정자 장애 = 전체 분산 트랜잭션 마비
```

| :---------- | :---------- | :----- | :------ |

| **일관성**     | 강한 일관성 ✅    | 강한 일관성 | 결과적 일관성 |
| **성능**      | 낮음          | 더 낮음   | 높음 ✅    |
| **MSA 적합성** | 낮음 🚨       | 낮음     | 높음 ✅    |

| **적합 환경**   | 단일 기관 분산 DB | 이론적 개선 | 마이크로서비스 |

#### Ⅳ. 결론

**(제언)** "2PC는 데이터 정합성을 철저히 지키나 병목이 매우 심합니다. **최신 분산 마이크로서비스 아키텍처(MSA)에서는 성능 저하를 일으키는 2PC 대신, 각 로컬 트랜잭션을 순차 실행하고 실패 시 역순으로 보상 트랜잭션을 실행해 결과적 일관성을 맞추는 'Saga 패턴' 아키텍처 도입을 적극 우선해야 합니다.** 앞서 다룬 Raft 합의가 '단 하나의 리더가 과반 동의로 진실을 정하는 강한 합의'라면, Saga는 '각 서비스가 자율적으로 로컬 커밋하고 실패 시 보상으로 결과적 일관성을 맞추는 약한 합의'로서, 강한 일관성이 필수인 금융·결제는 2PC, 최종 일관성으로 충분한 커머스·물류·예약은 Saga 패턴을 도메인 특성에 따라 선택하는 것이 현대 분산 시스템 설계의 핵심 원칙입니다."
