### **NoSQL 스키마 디자인: 임베딩 (Embedding) vs 참조 (Referencing)**

#### **MongoDB 데이터 모델링 핵심: 임베딩(Embedding) vs 참조(Referencing)**

***

#### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (왜 NoSQL에서 데이터 모델링 전략이 성능을 결정하는가)
Ⅱ. 임베딩 vs 참조 핵심 비교
Ⅲ. 선택 기준 및 적용 패턴
Ⅳ. 결론
```

포인트: 개요에서 \*\*"앞서 다룬 5NF·정규화가 'RDBMS에서 중복 제거·무결성 보장을 위해 데이터를 분리'하는 원칙이라면, MongoDB 등 문서형 NoSQL에서는 반대로 '관련 데이터를 하나의 문서에 내장(임베딩)하느냐, 별도 컬렉션에 분리하고 참조(Referencing)하느냐'가 쿼리 성능·데이터 일관성·확장성을 결정하는 핵심 설계 의사결정이다 — RDBMS의 JOIN이 없는 NoSQL에서 임베딩은 단일 쿼리로 연관 데이터를 모두 조회하는 성능 최적화 수단이고, 참조는 데이터 중복을 줄이고 독립적 갱신을 가능하게 하는 유연성 수단이며, 앞서 다룬 CAP 이론·BASE의 AP 선택 환경에서 어느 전략을 선택하느냐가 앞서 다룬 데이터 계약의 스키마 설계와 직결"\*\*이라는 한 줄로 시작하면 전체 맥락이 드러납니다.

***

#### Ⅱ. 임베딩 vs 참조 핵심 비교

**가. 개념 및 구조**

```
[임베딩 (Embedding) 구조]
{
  "_id": "order_001",
  "customer": "홍길동",
  "items": [                    ← 주문 항목을 문서 내 내장
    {"product": "노트북", "qty": 1, "price": 150},
    {"product": "마우스",  "qty": 2, "price": 3}
  ],
  "address": {                  ← 배송지도 내장
    "city": "서울",
    "zip": "04524"
  }
}
→ 단일 도큐먼트 조회로 모든 정보 획득 ✅

[참조 (Referencing) 구조]
// 주문 컬렉션
{
  "_id": "order_001",
  "customer_id": "cust_100",    ← 고객 컬렉션 참조
  "item_ids": ["item_1","item_2"] ← 상품 컬렉션 참조
}
// 고객 컬렉션 (별도)
{ "_id": "cust_100", "name": "홍길동", ... }
→ 2번 이상 쿼리 또는 $lookup 필요
```

***

**나. 핵심 비교**

| **핵심 척도** | **📊 임베딩 (Embedding) 🚨**                                                             | **🔑 참조 (Referencing) 🚨**                                                                 | **🏁 선택 기준 💯**                                           |
| :-------- | :------------------------------------------------------------------------------------ | :----------------------------------------------------------------------------------------- | :-------------------------------------------------------- |
| **핵심 장점** | **단일 쿼리 완결**: 연관 데이터 한 번에 조회 / JOIN 없음·네트워크 왕복 감소 / 읽기 성능 최고 ✅ / 원자적 쓰기(문서 단위 트랜잭션)   | **데이터 독립성**: 참조 대상 독립 갱신·재사용 / 중복 최소화 / 무제한 크기 확장 / 다대다 관계 자연스러운 표현 ✅                      | **임베딩 선택**: 함께 읽히는 데이터 / 1:1·1:少 관계 / 하위 데이터가 독립 존재 불필요   |
| **핵심 단점** | **문서 크기 한계**: MongoDB 16MB 제한 🚨 / 배열 무한 증가 위험 / 중복 데이터 발생 / 내장 데이터 단독 갱신 시 전체 문서 재기록 | **다중 쿼리 필요**: $lookup(LEFT JOIN) 또는 애플리케이션 레벨 조인 / 읽기 성능 저하 🚨 / 원자성 보장 어려움(다중 문서 트랜잭션 필요) | **참조 선택**: 독립적으로 접근하는 데이터 / 1:多·多:多 관계 / 자주 변경되는 공유 데이터   |
| **적합 관계** | **1:1**: 사용자-프로필 / **1:少(1:N, N 소규모)**: 주문-주문항목 / 블로그-댓글(적은 경우)                       | **1:多(N 대규모)**: 게시물-댓글(수천 개) / **多:多**: 학생-수강과목 / **공유 참조**: 상품 카탈로그 여러 주문에서 참조            | **하이브리드**: 자주 읽는 데이터 임베딩 + 드물게 접근하는 데이터 참조 / 실무 대부분 혼합 사용 |

#### Ⅲ. 선택 기준 및 적용 패턴

**가. 의사결정 흐름**

```
[임베딩 vs 참조 선택 의사결정]

데이터가 항상 함께 조회되는가?
  Yes → 임베딩 강력 권장
  No  ↓
데이터가 독립적으로 접근/수정되는가?
  Yes → 참조 권장
  No  ↓
관계의 N 규모는?
  N < 수십 → 임베딩 가능
  N > 수백 → 참조 (16MB 한계)
       ↓
중복 허용 vs 일관성 중요?
  중복 허용·읽기 성능 → 임베딩
  일관성·갱신 빈도↑  → 참조
```

**나. 실무 적용 패턴**

| 패턴         | 내용                    | 예시                 |
| :--------- | :-------------------- | :----------------- |
| **완전 임베딩** | 모든 관련 데이터 내장          | 주문+주문항목+배송지        |
| **부분 임베딩** | 자주 쓰는 필드만 내장·나머지 참조   | 상품명·가격만 내장·상세정보 참조 |
| **완전 참조**  | 모든 관련 데이터 참조          | 소셜네트워크 팔로워·팔로잉     |
| **양방향 참조** | 양쪽 컬렉션에 서로의 ID 보관     | 영화-배우 다대다 관계       |
| **버킷 패턴**  | 시계열 데이터 시간 단위 버킷에 임베딩 | IoT 센서 데이터·로그      |

***

**다. 앞서 다룬 개념과의 연결**

```
[RDBMS 정규화 vs MongoDB 모델링 비교]

RDBMS (5NF·정규화):
  중복 제거·무결성 → 분리(테이블)
  JOIN으로 재결합
  앞서 다룬 CBO가 최적 JOIN 계획 수립

MongoDB (임베딩·참조):
  읽기 패턴 중심 → 함께 쓰이면 내장
  $lookup으로 필요 시 참조 조인
  JOIN 최소화가 성능 핵심

연계:
  앞서 다룬 CAP·BASE(AP 선택)
  → 참조 시 다중 문서 원자성 보장 어려움
  → 임베딩으로 단일 문서 원자성 활용

  앞서 다룬 데이터 계약
  → MongoDB 스키마 설계를 계약으로 명시
  → 임베딩 구조 변경 = Breaking Change
```

***

**(제언)** "임베딩과 참조는 '데이터를 어떻게 읽을 것인가'에서 출발하는 NoSQL 모델링의 핵심 의사결정입니다. **MongoDB의 황금 원칙은 '함께 접근하는 데이터는 함께 저장하라(Data that is accessed together should be stored together)'이며, 앞서 다룬 5NF 정규화처럼 이론적 완벽함보다 실제 쿼리 패턴·갱신 빈도·관계 규모를 기준으로 임베딩·참조·하이브리드를 선택하고, 앞서 다룬 데이터 계약으로 스키마 구조를 문서화해 임베딩 구조 변경 시 Breaking Change로 관리하는 것이 MongoDB 데이터 모델링 거버넌스의 핵심입니다.**"
