좋은 원자료를 확보했습니다. 이 가이드라인은 \*\*"공통기준(모든 클라우드) + SaaS 추가기준"\*\*이라는 확장구조가 핵심입니다. 앞서 다룬 클라우드SLA·CSAP 답안과 이어지는 흐름이라, 그 연결성도 살려서 짜겠습니다.

### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (가이드라인 배경 - 국가클라우드보안가이드라인의 SaaS 확장) — 3~4줄
Ⅱ. 클라우드서비스 위험관리 원칙 (본론①, 도식 1개)
Ⅲ. 위험관리 기준 (7대 분류)
Ⅳ. 보안성검토 및 SLA 연계
Ⅴ. 결론
```

포인트: 개요에서 \*\*"기존 국가클라우드보안가이드라인(IaaS 중심)에, SaaS 특유의 위험요소(개발환경·애플리케이션 계층)를 추가 확장한 것"\*\*이라는 한 줄을 잡으면, 왜 별도 가이드라인이 필요한지 논리가 섭니다. 앞서 다룬 CSAP(IaaS/SaaS/DaaS 인증)와도 자연스럽게 연결됩니다.

### Ⅱ. 위험관리 원칙 — "정책×기술" 2축, 각각 "공통+SaaS추가" 구조

**함정 방지: 원칙을 그냥 나열하지 말고 "공통기준에 SaaS가 무엇을 더 요구하는가"로 대비**

| 축         | 공통 기본원칙                                                                                 | SaaS 환경 추가원칙                                               |
| :-------- | :-------------------------------------------------------------------------------------- | :--------------------------------------------------------- |
| **정책 측면** | 국가클라우드보안가이드라인 준수, 도입 정보보호시스템 안전성 확인, **인터넷·업무망 분리**, 공급망 관리                             | **개발단계부터 보안취약점 원인(보안약점) 배제** — Secure Coding 개념의 정책화       |
| **기술 측면** | 인프라·개발운영환경의 **물리적 위치·보안성 확인**, 허가받은 외부연동 서비스 연계, 영역분리, 이중화·백업체계, 접근통제, 중요업무자료 암호화, 보안관제 | **외부공개용 SaaS ↔ 내부업무용 SaaS 영역 분리**, SaaS 애플리케이션 보안성 강화방안 마련 |

→ 암기: **"공통은 인프라를 어떻게 지키나(IaaS 관점), SaaS 추가는 애플리케이션/개발단계를 어떻게 지키나(App 관점)"** — 이 대비 하나로 원칙 전체가 정리됩니다.

### 도식화 제안

```
        [국가클라우드컴퓨팅 보안가이드라인] (공통기반)
                    ↓ 확장
        [공공부문 SaaS 이용 가이드라인]
   ┌────────┴────────┐
[정책측면]              [기술측면]
공통: 망분리/공급망관리    공통: 암호화/접근통제/이중화
 +SaaS: 개발단계 보안약점   +SaaS: 영역분리(외부↔내부)
      배제                  애플리케이션 보안강화
```

### Ⅲ. 위험관리 기준 — "정·인·가·데·접·사" (7대 분류, 표로 압축)

| 분류          | 세부기준                                       | 적용범위        |
| :---------- | :----------------------------------------- | :---------- |
| **정책**      | 시스템보호, 인적관리, 보안검사                          | 공통/IaaS     |
| **인프라**     | 가상화인프라, 보안관리                               | 공통/IaaS     |
| **가상환경보안**  | SaaS App개발 보안관리, 개발운영환경 보안관리, 악성코드방지, 접근통제 | **SaaS 특화** |
| **데이터**     | 관리, 암호화                                    | 공통          |
| **인증/권한**   | 인증, 권한                                     | 공통          |
| **사고/장애대응** | 사고대응, 장애대응                                 | 공통          |

→ 암기: **"정책-인프라"는 IaaS 색채가 강하고, "가상환경보안"이 SaaS 고유영역이라는 것**만 구분해서 기억하면, 나머지(데이터/인증/사고대응)는 일반적인 정보보안 원칙과 동일해서 새로 외울 게 없습니다.

### Ⅳ. 보안성검토 및 SLA (본론 마무리)

**보안성검토**: 국가클라우드컴퓨팅보안가이드라인·국가정보보안기본지침에 따라 **시스템 규모·중요도에 비례**하여 검토를 직접 실행하거나 위임 — 앞서 다룬 CSAP(제3자 인증)와의 차이는, 보안성검토는 **기관 자체 또는 위임기관이 개별 도입 시점마다 수행하는 심사**라는 점입니다.

**서비스수준협약(SLA) 연계**: 앞서 다룬 클라우드SLA 답안의 "가·성·안·지" 지표와 정확히 대응됩니다.

| SLA 구분  | 기준                        |
| :------ | :------------------------ |
| 시스템 안정성 | 가용성, 신뢰성(회복시간·백업), 서비스지속성 |
| 성능관리    | 응답성, 확장성                  |
| 고객지원    | 서비스지원, 고객대응               |

→ "이 가이드라인의 SLA 요구사항이 앞서 배운 클라우드SLA 지표체계와 동일하다"는 한 줄을 넣으면 답안 간 연결성이 드러나 고득점에 유리합니다.

### Ⅴ. 결론 포인트 (차별화 한 줄)

이 가이드라인의 본질은 \*\*"IaaS 중심 보안모델에서 SaaS 중심(애플리케이션·개발단계) 보안모델로의 확장"\*\*이며, 이는 앞서 다룬 CSAP 등급제(상·중·하) 및 공동책임모델(Shared Responsibility)과 함께 \*\*"클라우드 계층이 올라갈수록 이용기관의 애플리케이션·데이터 책임이 커진다"\*\*는 큰 흐름 속에 있다는 논리로 마무리하면, 클라우드 관련 여러 답안(SLA·CSAP·본 가이드라인)이 하나의 큰 그림으로 연결됩니다.

### **1. 답안 전개 스토리 (머릿속 핵심 흐름)**

> "공공기관이 민간 SaaS(소프트웨어 클라우드)를 도입할 때 가장 크게 착각하는 것이 '벤더(CSP)가 CSAP 인증을 받았으니 보안은 벤더가 다 책임지겠지'라는 생각이다. 하지만 가이드라인이 강조하는 최우선 \*\*'위험관리 원칙'\*\*은 철저한 \*\*'공동 책임 모델(Shared Responsibility)'\*\*이다. 껍데기(인프라/앱)의 보안은 벤더가 책임지더라도, 그 안에 들어가는 데이터 보호와 계정(접근) 관리는 여전히 도입 기관의 몫이다. 따라서 CSAP 인증만 믿지 말고, 사전에 기관 자체의 꼼꼼한 \*\*'보안성 검토'\*\*를 통해 데이터 암호화와 망분리 완화에 따른 추가 보안 대책을 세워야 한다."

***

### **2. 실제 답안에 쓸 핵심 내용 (암기용)**

#### **I. \[도입] 공공 SaaS 도입의 엑셀이자 브레이크, 이용 가이드라인 개요**

* **배경:** 정부의 '디지털 플랫폼 정부(DPG)' 정책에 따라 공공기관의 민간 SaaS 이용이 급증함에 따라, 무분별한 도입에 따른 데이터 유출 리스크를 막기 위한 국가정보원 및 관련 기관의 보안 지침.
* **목적:** 업무 편의성과 비용 절감이라는 엑셀(활성화)을 밟으면서도, 국가 주요 데이터 유출 방지라는 브레이크(보안 통제)를 동시에 작동시키기 위한 표준 기준 제공.

#### **II. \[본론 1] 공공 SaaS 도입 시 핵심 위험관리 원칙 (가장 중요)**

공공 SaaS 가이드라인에서 요구하는 리스크 관리의 본질은 **책임의 분배**와 **데이터 주권 확보**입니다.

1. 🤝 **공동 책임 모델 (Shared Responsibility) 원칙**
   * **CSP(클라우드 제공자) 책임:** 물리적 인프라 보안, 네트워크 및 애플리케이션 플랫폼 자체의 보안 취약점 관리.
   * **공공기관(이용자) 책임:** 해당 SaaS에 올리는 **데이터 자체의 보호, 계정(ID/PW) 및 권한 관리**, 내부 직원의 단말기 보안 등은 전적으로 기관이 책임져야 함.
2. 🔐 **데이터 주권 및 통제권 확보 원칙**
   * SaaS 장애 시나 계약 종료 시 데이터(Lock-in 방지)를 즉각적이고 온전하게 회수할 수 있는 방안 사전 확보 의무화.
3. 🛡️ **최소 권한 부여 원칙 (Zero Trust 기반)**
   * 인가된 사용자라 하더라도 업무에 꼭 필요한 최소한의 접근 권한만 부여하여 내부자 유출 리스크 최소화.

#### **III. \[본론 2] 안전한 SaaS 이용을 위한 사전 '보안성 검토' 핵심 항목**

단순히 CSAP 인증서만 확인하고 끝나는 것이 아니라, 국정원 정보보안지침에 따른 구체적인 점검을 수행해야 합니다. (답안지에 표 형태로 정리하면 좋습니다)

| **보안성 검토 영역**                     | **필수 확인 및 점검 조치 사항 (수험용 키워드)**                                                               |
| :-------------------------------- | :------------------------------------------------------------------------------------------- |
| **1. 인증 및 계약 요건** (제도적 요건 확인)     | - 해당 SaaS가 KISA의 **CSAP(클라우드 보안인증) 유효 상태**인지 확인 - 클라우드 서비스 수준 협약(**SLA**) 상의 보안 페널티 조항 명시 여부 |
| **2. 접근 및 계정 통제** (사용자 통제)        | - 관리자 및 사용자 로그인 시 **2FA / MFA(다중 인증)** 적용 여부 확인 - IP 접속 통제(지정된 공공기관 망에서만 접속 허용 등) 설정         |
| **3. 데이터 보호 및 암호화** (핵심 정보 자산 보호) | - 전송 구간 암호화(TLS 적용) 및 저장 데이터 암호화 적용 여부 - 특히, **암호화 키(Key)의 관리 주체가 누구인지** 점검 (BYOK 권장)        |
| **4. 망분리 완화 보완 대책** (네트워크 통제)     | - CSAP '하' 등급 허용으로 논리적 망분리가 적용된 경우, 공공 망과 외부 인터넷 망 간의 불법적 데이터 우회 통신 방지 대책 수립 여부              |
| **5. 감사 및 모니터링** (사후 대응 체계)       | - 접속 기록 및 관리자 행위 로그의 최소 6개월 이상 보존 보장 - 이상 행위 탐지 시 공공기관 보안 관제 센터와 즉시 연동되는 체계                  |

#### **IV. \[결론/제언] 완벽한 공공 SaaS 정착을 위한 CASB 도입 제언**

* **(키워드 위주 2줄 마무리)** "민간 SaaS의 무분별한 사용(섀도우 IT)은 공공기관의 치명적인 데이터 유출로 직결될 수 있습니다. 이를 근본적으로 차단하기 위해, 관리자가 인가하지 않은 SaaS 접근을 통제하고 클라우드로 이동하는 데이터를 실시간으로 모니터링/암호화하는 **클라우드 접근 보안 브로커(CASB, Cloud Access Security Broker)** 솔루션의 도입이 공공 부문에서도 적극적으로 논의되어야 합니다."
