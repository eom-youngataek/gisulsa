좋은 자료입니다. 오픈뱅킹은 KIPRIS Plus의 Open API 전략과도 구조적으로 닮아있어서, 답안 뒤에 자연스러운 확장이 가능합니다. **"플랫폼 구조(누가 무엇을 하나) → 보안모델 → 최근 확장(마이데이터/기업용)"** 순서로 짜겠습니다.

### 답안 전체 스토리 흐름 (목차)

```
Ⅰ. 개요 (오픈뱅킹 정의, 도입배경 - PSD2와 비교) — 3~4줄
Ⅱ. 플랫폼 구조 (본론①, 도식 1개 필수)
Ⅲ. 보안모델 (본론②)
Ⅳ. 최신 확장동향 (본론③)
Ⅴ. 결론
```

포인트: 개요에서 \*\*"한국형 오픈뱅킹은 유럽 PSD2(분산형-은행별 개별API)와 달리, 금융결제원이라는 단일 중앙허브를 통해 표준API를 제공하는 중앙집중형 모델"\*\*이라는 한 줄 대비를 던지면, "왜 한국 모델이 독특한가"의 논리가 섭니다.

### Ⅱ. 플랫폼 구조 — "허·참·이·용" (4대 주체, 앞서 다룬 CSAP 위계패턴과 유사)

| 주체             | 역할                              |
| :------------- | :------------------------------ |
| **허브(금융결제원)**  | 단일 API 게이트웨이 운영, 참가기관 간 **중계**  |
| **참가기관(은행 등)** | 계좌정보·이체 등 금융서비스를 **표준API로 개방**  |
| **이용기관(핀테크사)** | 오픈API로 **신규서비스 개발** (등록·승인 필요)  |
| **사용자(고객)**    | 본인인증 후 여러 계좌를 **한 앱에서 통합조회·이체** |

→ 암기: **"허브가 중계하고, 참가기관이 열어주고, 이용기관이 만들고, 사용자가 편하게 쓴다"** — 앞서 다룬 CSAP의 "정·인·위·기·신" 5대주체 구조와 같은 패턴이라는 걸 인지하면 새로 외울 부담이 줄어듭니다.

**오픈API 구성 (기술요소)**: **7개 서비스API**(잔액조회/거래내역조회/입출금이체 등) + **인증/관리API**, 그리고 실제 서비스 전 검증하는 **테스트베드**로 구성됩니다.

### 도식화 제안

```
        [금융결제원] (중앙허브, 단일게이트웨이)
   ┌────────┼────────┐
[참가기관]           [이용기관]
은행/저축은행/증권사     핀테크기업(토스/카카오페이 등)
(API 개방)              (API 소비→신규서비스)
   └────────┼────────┘
        [사용자] 통합조회/이체(1억2천만건 등록, 일 1,500만건 호출)
```

→ "유럽(분산형: 은행마다 API) vs 한국(중앙집중형: 결제원이 허브)"을 이 그림 옆에 대비로 넣으면 심화 배점입니다.

### Ⅲ. 보안모델 — "인·위·표" (3대 보안기술)

| 기술                             | 역할                                       |
| :----------------------------- | :--------------------------------------- |
| **OAuth2**                     | 사용자 권한을 제3자(이용기관)에 **안전하게 위임**           |
| **OpenID Connect**             | 신원확인(본인인증) 표준                            |
| **FAPI** (Financial-grade API) | 금융특화 API보안표준 — 일반 OAuth보다 **강화된 암호화·검증** |

→ 암기: **"권한은 넘기고(OAuth2), 신원은 확인하고(OpenID), 금융이라 더 세게 검증한다(FAPI)"** — 은행 비밀번호 자체는 절대 제3자와 공유되지 않고, 토큰 기반으로만 접근한다는 점이 핵심 보안원칙입니다.

### Ⅳ. 최신 확장동향 (2025\~2026, 최신성 어필 핵심)

| 확장             | 내용                                                              |
| :------------- | :-------------------------------------------------------------- |
| **법인 이용확대**    | 기존 개인전용 → **2025년부터 법인도 오픈뱅킹 이용가능**하게 확대                        |
| **오프라인 확대**    | 모바일 앱 전용에서 **영업점 오프라인에서도 이용 가능**하도록 계획                          |
| **마이데이터 2.0**  | 2026년 마이데이터 2.0 추진 — 앞서 다룬 "데이터3법"의 신용정보법 마이데이터 조항과 직결          |
| **오픈파이낸스로 진화** | 은행 중심 오픈뱅킹 → 보험·증권 등 전 금융권 포괄하는 **오픈파이낸스**로 로드맵 확장(2028\~2029년) |

→ "오픈뱅킹(은행중심) → 마이데이터(개인정보 전송권 확장) → 오픈파이낸스(전 금융권)"로 이어지는 확장궤적을 한 줄로 정리하면, 앞서 다룬 "데이터산업법 제15조(데이터이동)" 답안과도 연결됩니다.

### Ⅴ. 결론 포인트 (차별화 한 줄)

한국형 오픈뱅킹의 성공요인은 기술(API)이 아니라 \*\*"중앙허브(금융결제원)가 표준을 강제함으로써, 개별은행이 각자 API를 만들 필요 없이 동일한 규격으로 빠르게 참여할 수 있게 한 거버넌스 설계"\*\*에 있습니다 — 이는 앞서 다룬 "CoE(연합형)"의 "표준은 중앙이, 실행은 각자가" 논리와 정확히 같은 구조이며, \*\*"공공API(KIPRIS Plus 등)도 이런 중앙허브형 표준화 모델을 참고할 수 있다"\*\*는 결론으로 마무리하면 실무 확장성이 큽니다.

### **1. 답안 전개 스토리 (머릿속 핵심 흐름)**

> "과거엔 A은행 돈을 B은행으로 보내려면 무조건 A은행 앱을 켜야만 했다. 은행들이 자기들의 결제망을 철옹성처럼 잠가두었기 때문이다. 초기 토스나 뱅크샐러드 같은 핀테크 기업들은 고객의 아이디/비번을 받아 대신 로그인해서 정보를 몰래 긁어오는 불안정한 '스크래핑' 꼼수를 써야만 했다. 하지만 **'오픈뱅킹'** 제도가 도입되면서 이 철벽이 무너졌다. 은행들은 자신들의 핵심 기능(조회, 이체)을 \*\*'표준 오픈API'\*\*로 전면 개방했고, 이제 고객은 앱 하나만 깔면 모든 은행의 돈을 굴릴 수 있게 되었다. 핀테크 기업들은 이 안전한 API를 바탕으로 초거대 종합 금융 플랫폼으로 성장했으며, 이는 향후 전 국민의 금융/의료 데이터를 한곳으로 모으는 '마이데이터' 생태계의 심장이 되었다."

***

### **2. 실제 답안에 쓸 핵심 내용 (암기용)**

#### **I. \[도입] 은행의 철옹성을 부순 거대한 금융 혁신, 오픈뱅킹 개요**

* **오픈뱅킹 (Open Banking):** 고객이 여러 은행의 앱을 설치할 필요 없이, **하나의 은행 앱이나 핀테크 앱만으로 자신의 모든 은행 계좌를 조회하고 자금을 이체할 수 있는 서비스**.
* **오픈API (Open API):** 오픈뱅킹을 기술적으로 구현하는 핵심 수단. 은행이 폐쇄적으로 가지고 있던 금융 인프라(잔액조회, 출금이체 등)를 제3자(핀테크 기업)가 쉽게 가져다 쓸 수 있도록 **공개된 표준 프로그램 인터페이스(API) 형태로 제공**하는 것.

#### **II. \[본론 1] 핀테크 정보 수집 기술의 진화: 스크래핑 vs 오픈API 비교**

핀테크 앱이 내 계좌 정보를 가져오는 기술이 과거의 해킹과 다름없던 스크래핑에서, 공식적이고 안전한 API 방식으로 진화했음을 명확히 보여주어야 합니다.

| **비교 항목** | **과거: 스크린 스크래핑 (Screen Scraping)**                                | **🚀 현재: 오픈 API (Open API) 방식**                        |
| :-------- | :---------------------------------------------------------------- | :----------------------------------------------------- |
| **작동 원리** | 핀테크 앱이 **고객의 ID/PW를 대신 입력해 은행 사이트에 로그인**한 뒤 화면의 글자를 긁어옴 (Parsing) | 은행이 공식적으로 열어준 **API 게이트웨이를 통해 정형화된 JSON 데이터**를 호출하여 받음 |
| **보안성**   | ❌ **매우 취약** (고객의 인증정보를 핀테크 업체가 저장해야 하므로 유출 위험 극대화)                | 🛡️ **매우 우수** (**OAuth 2.0 기반의 토큰 인증**으로 ID/PW 노출 없음)  |
| **안정성**   | 은행 홈페이지 UI가 살짝만 바뀌어도 크롤링 에러 발생 (유지보수 극상)                          | 국제 표준 규격 준수로 트래픽이 몰려도 안정적이고 즉각적인 응답                    |

#### **III. \[본론 2] 오픈뱅킹 시스템 생태계의 3대 핵심 아키텍처 구조**

한국형 오픈뱅킹 생태계는 '금융결제원'을 중심 허브망으로 하는 아키텍처를 가집니다.

1. **핀테크 기업 / 이용기관 (API Consumer):**
   * 토스, 뱅크샐러드 또는 타 은행의 뱅킹 앱.
   * 사용자의 동의(OAuth 2.0)를 얻어 오픈뱅킹 공동망에 '잔액 조회', '출금 이체' 등의 API 호출 요청.
2. **오픈뱅킹 공동망 센터 (API Gateway - 금융결제원 주도):**
   * 수십 개의 핀테크 앱과 수십 개의 은행이 일일이 1:1로 통신(그물망 구조)하는 복잡도를 줄이기 위해, 중간에서 **중계 허브(Hub) 역할** 수행.
   * 표준 API 라우팅, 실시간 트래픽 제어, \*\*FDS(이상거래탐지시스템)\*\*를 통한 사기 이체 모니터링 수행.
3. **참여 금융기관 (API Provider):**
   * 시중 은행 및 증권사 등.
   * 공동망에서 들어온 API 요청을 받아 실제 원장(Core Banking)의 잔액을 깎고 돈을 이체시킨 후 결과를 반환.

#### **IV. \[결론/제언] 오픈뱅킹과 마이데이터(MyData)의 결합에 따른 빅블러(Big Blur) 시대 제언**

* **(키워드 위주 2줄 마무리)** "오픈뱅킹이 '결제망의 개방'이라면, 마이데이터는 '데이터의 개방'입니다. 이 두 가지가 강력한 오픈API를 매개체로 결합되면서, 은행·증권·보험·통신의 경계가 붕괴되는 **'빅블러(Big Blur)' 현상**이 가속화되고 있습니다. 기존 금융권이 거대한 핀테크 플랫폼의 단순 인프라 공급자(Dumb Pipe)로 전락하지 않기 위해서는, 뱅킹 자체를 서비스형 플랫폼으로 제공하는 **BaaS(Banking as a Service) 중심의 클라우드 네이티브 아키텍처 전환**이 시급합니다."
