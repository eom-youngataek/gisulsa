# 인증/접근제어 모델 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 정책별 비교표 → 융합 필요성 → 운영방안

---

## 1. ISMS vs ISMS-P (차이/의무대상)

**정책별 비교표**

| 구분 | ISMS | ISMS-P |
|---|---|---|
| 정식명칭 | 정보보호 관리체계 인증 | 정보보호 및 개인정보보호 관리체계 인증 |
| 인증범위 | 정보보호 영역만(80개 항목) | 정보보호(80개)+개인정보보호 생애주기 전체(22개 항목) 추가 |
| 의무대상 | ISP, 클라우드사업자, 매출/이용자수 기준 충족 정보통신서비스제공자 등(정보통신망법 기준) | ISMS 의무대상 중 개인정보처리가 많은 기업이 선택 또는 별도 의무화 대상 |
| 법적근거 | 정보통신망법 제47조 | 개인정보보호법 + 정보통신망법 동시 근거 |

**융합 필요성**
> 단순 정보보호(ISMS)만으로는 개인정보의 수집·이용·제공·파기 전체 생애주기의 위험을 다루지 못함 → 개인정보 유출사고 예방을 위해 개인정보 처리흐름까지 포괄하는 ISMS-P 통합인증 필요성 증가(최근 ISMS-P 간편인증 제도 도입으로 중소기업 부담 완화)

**운영방안**
- 인증범위(ISMS vs ISMS-P) 결정 시 자사의 개인정보처리 비중을 먼저 진단
- 관리과정(PDCA: 정책수립→위험관리→대책구현→사후관리)을 연중 상시 운영체계로 정착

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| PIMS(개인정보보호 관리체계) | ISMS-P의 전신 제도(현재는 ISMS-P로 통합됨) |
| PIA(개인정보 영향평가) | ISMS-P 인증과 별개로 개인정보 처리시스템 신규구축 시 수행하는 사전 위험평가 |
| 개인정보 안전성확보조치 기준 | ISMS-P 인증항목 중 기술적 보호조치의 구체적 기준 |

## 2. MAC / DAC / RBAC / ABAC

**정책별 비교표**

| 모델 | 권한부여 기준 | 특징 |
|---|---|---|
| **MAC(강제적 접근제어)** | 시스템(관리자)이 보안등급(Label)을 강제 부여 | 사용자가 권한 변경 불가, 군사·정부기관 등 고보안환경 |
| **DAC(임의적 접근제어)** | 데이터 소유자가 자율적으로 권한 부여 | 유연하지만 권한관리가 분산되어 보안 일관성 낮음(일반 파일시스템) |
| **RBAC(역할기반 접근제어)** | 사용자에게 직접 권한을 주지 않고 "역할(Role)"에 권한 부여, 사용자는 역할에 배정 | 인사이동 시 역할만 재배정하면 됨(관리효율 높음, 기업 표준) |
| **ABAC(속성기반 접근제어)** | 사용자속성+자원속성+환경속성(시간,위치 등)을 조합해 동적 판단 | 가장 정교하고 유연, 제로트러스트의 핵심 접근제어 방식 |

**융합 필요성**
> RBAC는 역할이 고정적이라 "원격근무 중인 직원이 새벽시간에 접속"같은 동적 상황 통제가 어려움 → **MAC(고정등급 보안)+ABAC(동적 컨텍스트)** 융합으로 "민감정보는 절대불가(MAC) + 상황에 따라 추가검증(ABAC)"의 다층 통제 구현

**운영방안**
- 일반 업무시스템은 RBAC로 기본 골격 구성 → 민감정보(개인정보·기밀)에는 MAC 등급 추가 → 원격/이상접속 등 동적 상황은 ABAC로 실시간 정책 적용(정책엔진, PDP/PEP 구조)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 제로트러스트 | ABAC를 핵심 메커니즘으로 사용하는 차세대 보안모델(아래 키워드와 직결) |
| BLP/BIBA/Clark-Wilson | MAC을 학문적으로 구체화한 보안모델들(다음 섹션과 연계) |
| LDAP | RBAC의 "역할-사용자" 매핑 정보를 실제로 저장·관리하는 디렉토리서비스 |

## 3. BLP / BIBA / Clark-Wilson / 만리장성 모델

**정책별 비교표**

| 모델 | 핵심목표 | 핵심규칙 |
|---|---|---|
| **BLP(Bell-LaPadula)** | **기밀성** 보장 | No Read Up(상위등급 못읽음), No Write Down(하위등급에 못씀) — 정보가 위로만 흐름 |
| **BIBA** | **무결성** 보장 | No Read Down(하위등급 못읽음), No Write Up(상위등급에 못씀) — BLP와 반대방향, 정보가 아래로만 흐름 |
| **Clark-Wilson** | **무결성**(상업환경) | 잘 짜인 트랜잭션(Well-formed Transaction)+직무분리(SoD)로 데이터 일관성 보장 |
| **만리장성모델(Chinese Wall, Brewer-Nash)** | **이익충돌 방지** | 경쟁관계 고객정보를 다루는 부서 간 접근을 동적으로 차단(금융투자업 컴플라이언스) |

**융합 필요성**
> BLP만 적용하면 기밀성은 확보되나 데이터 위변조(무결성) 위험은 못막음 → 군사·정부기관처럼 기밀성이 최우선인 환경은 BLP, 금융권처럼 데이터 정확성이 핵심인 환경은 BIBA/Clark-Wilson을 같이 고려해야 균형있는 모델 설계 가능

**운영방안**
- 기밀성 중심 조직(국방·정보기관): BLP 우선 적용
- 무결성 중심 조직(금융·회계시스템): Clark-Wilson의 직무분리 원칙 적용
- 증권사·자산운용사의 고객정보 격리: 만리장성모델로 부서간 정보교류 통제

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| MAC(강제적접근제어) | BLP/BIBA는 MAC을 구체적으로 구현한 수학적 모델 |
| 직무분리(SoD, Segregation of Duties) | Clark-Wilson의 핵심원칙, 내부통제(회계감사)에서도 동일하게 강조 |
| 만리장성모델 vs 정보장벽(Information Barrier) | 금융권 실무에서는 만리장성모델을 "정보장벽"이라는 실무용어로도 부름 |

## 4. 식별(Identification) vs 인증(Authentication)

**정책별 비교표**

| 구분 | 식별 | 인증 |
|---|---|---|
| 질문 | "당신은 누구입니까?" | "정말 그 사람이 맞습니까?" |
| 수단 | ID, 사용자명(주장만 함) | 비밀번호, 생체정보, OTP 등(증명) |
| 보안수준 | 단독으로는 보안기능 없음 | 인증요소(아래 4유형)로 신뢰성 부여 |

**인증방식 4가지 유형**: ①Something you know(비밀번호) ②Something you have(OTP·보안카드) ③Something you are(생체인식) ④Something you do(행동패턴, 키보드 입력습관 등)

**융합 필요성**
> 1가지 인증요소(비밀번호)만으로는 유출·탈취 시 무력화 → **다중인증(MFA)**으로 여러 유형을 결합해야 안전(예: 비밀번호+OTP=지식+소지)

**운영방안**
- 중요시스템은 최소 2가지 이상 인증요소 결합(MFA) 의무화
- 생체인증(안면인식 결제 등) 도입 시 라이브니스 검사로 위변조(사진·딥페이크) 방지 병행

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 안면인식 결제서비스(생체인식AI) | "Something you are" 인증요소의 실제 응용사례 |
| 제로트러스트 | "한번 인증했다고 끝이 아니라 지속적으로 재인증·검증"하는 철학으로 식별/인증 개념을 확장 |
| LDAP | 사용자 식별정보(계정)를 저장·검색하는 인프라(다음 키워드) |

## 5. LDAP (Lightweight Directory Access Protocol)

**정책별 비교표(LDAP vs RDBMS, 용도 비교)**

| 구분 | LDAP(디렉토리서비스) | RDBMS |
|---|---|---|
| 데이터구조 | 트리(계층) 구조(예: 조직도 형태) | 테이블(행/열) 구조 |
| 용도 | 사용자·그룹·권한 등 **자주 조회, 가끔 수정**되는 정보 | 빈번한 트랜잭션(입출금 등) 처리 |
| 조회성능 | 매우 빠름(읽기 최적화) | 쓰기/조회 균형 |

**인증흐름(Bind 절차)**
```
[클라이언트] → Bind 요청(사용자DN + 비밀번호) → [LDAP서버]
[LDAP서버] 저장된 정보와 대조 → 일치하면 인증성공(Bind 성공) → 이후 권한범위 내 조회/수정 허용
```

**융합 필요성**: 기업 내 수많은 시스템(이메일·VPN·사내포털)이 각자 계정을 관리하면 비효율·보안취약 → LDAP을 중앙 계정저장소로 통합해 SSO(Single Sign-On)와 결합 필요

**운영방안**: Active Directory(MS의 LDAP기반 구현체) 등으로 중앙집중 계정관리, RBAC의 역할정보도 LDAP 그룹으로 매핑해 운영

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| SSO(Single Sign-On) | LDAP 기반 중앙인증의 대표 활용사례 |
| RBAC | LDAP의 그룹(Group) 구조가 RBAC의 역할을 실제로 구현하는 저장소 역할 |

## 6. 제로트러스트 성숙도 4단계

**정책별 비교표(성숙도 단계)**

| 단계 | 특징 |
|---|---|
| **1단계(전통적)** | 경계기반 보안, 내부망은 기본신뢰(VPN 접속 후 전체 접근 허용) |
| **2단계(초기)** | 일부 자원에 ID기반 인증 도입, 정책이 정적(고정규칙) |
| **3단계(고도화)** | 동적(ABAC) 정책 적용 확대, 마이크로세그멘테이션(자원단위 최소권한) 시작 |
| **4단계(최적화)** | 모든 접근을 실시간·지속적으로 검증(Continuous Verification), AI기반 이상탐지와 자동대응 결합 |

**핵심원칙**: "절대 신뢰하지 말고, 항상 검증하라(Never Trust, Always Verify)" — 내부망이라도 무조건 신뢰하지 않음

**융합 필요성**
> 전통적 경계기반 보안(망분리·VPN)은 "한번 내부에 들어오면 자유롭게 이동(Lateral Movement)" 가능한 한계 → 제로트러스트는 ABAC+MFA+마이크로세그멘테이션을 결합해 매 접근마다 재검증

**운영방안**: 성숙도 진단 후 단계적 로드맵 수립(전 영역을 한번에 4단계로 도약 불가) → 핵심자산부터 마이크로세그멘테이션 우선 적용 → 점진적으로 전사 확대

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 망분리 / VPN | 제로트러스트가 대체하고자 하는 전통적 경계기반 보안모델 |
| ABAC | 제로트러스트의 동적 정책판단을 실제로 구현하는 접근제어 모델 |
| ZTNA(Zero Trust Network Access) | VPN을 대체하는 제로트러스트 기반 원격접속 솔루션 |
| 측면이동(Lateral Movement) | 제로트러스트가 마이크로세그멘테이션으로 차단하고자 하는 공격기법 |

## 7. CC (Common Criteria, 공통평가기준)

**정책별 비교표(평가등급 EAL)**

| 등급 | 보증수준 |
|---|---|
| EAL1~2 | 기능 시험 수준(낮은 보증) |
| EAL3~4 | 체계적 설계·검토(일반 상용제품 표준, 대부분 EAL4 획득) |
| EAL5~7 | 정형적 검증 수준(국방·고보안 요구환경) |

**핵심구성**: PP(Protection Profile, 보호프로파일=요구사항 정의서), ST(Security Target, 보안목표명세서=제품이 PP를 어떻게 만족하는지), TOE(Target of Evaluation, 평가대상제품)

**융합 필요성**: 국가마다 다른 보안제품 평가기준이 있으면 국제 조달·수출이 어려움 → CC는 국제공통기준(ISO/IEC 15408)으로 상호인정(CCRA)을 통해 한 나라에서 받은 인증을 여러 나라가 인정

**운영방안**: 공공기관 보안제품(방화벽·IPS 등) 도입 시 CC인증(국정원 검증필 제품) 의무 확인, 제품개발 초기부터 PP에 맞춰 설계해 인증획득 기간 단축

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| ISA/IEC 62443 | CC가 일반 IT제품 대상인 것과 달리 산업제어시스템(OT) 특화 보안표준 |
| FIPS 140-2 | CC와 유사한 목적(보안제품 검증)이나 암호모듈에 특화된 미국 표준 |
| TPM(Trusted Platform Module) | TPM 칩 자체도 CC인증(EAL4+ 등)을 받는 대표적 평가대상(TOE) 사례 |

## 8. TPM (Trusted Platform Module)

**정책별 비교표(TPM 기능 vs 일반 소프트웨어 보안)**

| 구분 | 일반 소프트웨어 키저장 | TPM(하드웨어) |
|---|---|---|
| 키 보관위치 | 디스크/메모리(OS레벨에서 접근가능) | 별도 보안칩 내부(OS조차 직접 접근 불가) |
| 변조 저항성 | 낮음(악성코드로 탈취 가능) | 높음(물리적 보안칩으로 추출 차단) |

**핵심기능**: 암호화키 생성·저장, **무결성 측정(PCR, Platform Configuration Register)**으로 부팅과정의 변조여부 검증(Secure Boot), 디스크 암호화 키 보호(BitLocker 등)

**융합 필요성**: 소프트웨어만으로 키를 보관하면 루트킷·악성코드에 의해 탈취 위험이 상존 → 하드웨어 기반 신뢰의 뿌리(Root of Trust)인 TPM과 결합해야 진정한 무결성 보장 가능

**운영방안**: 기업 노트북·서버 전체에 TPM 칩 기본탑재 의무화, 부팅 시 TPM 기반 무결성 검증을 통과해야만 OS가 정상기동되도록 정책 설정

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| Secure Boot | TPM의 PCR값 검증으로 구현되는 부팅단계 보안기능 |
| CC(Common Criteria) | TPM 칩 자체가 받는 보안인증 체계 |
| 제로트러스트 | TPM이 디바이스 신뢰성을 보장하는 "디바이스 검증" 요소로 제로트러스트 정책판단에 활용 |

## 종합 흐름도

```
[관리체계 인증] ISMS → ISMS-P (개인정보보호 영역 확장)
        │
[접근제어 모델 설계]
  DAC(자율) → RBAC(역할기반, 기업표준) → ABAC(속성기반, 동적) → 제로트러스트(ABAC 핵심활용)
        │                                              │
  학문적 모델: BLP(기밀성)/BIBA(무결성)/Clark-Wilson(상업무결성)/만리장성(이익충돌방지)
        │
[인증 기반체계]
  식별(누구) → 인증(증명, MFA) → LDAP(중앙 계정저장소)
        │
[하드웨어/평가 신뢰체계]
  TPM(하드웨어 신뢰뿌리) ← CC(국제공통 보안평가기준)
```
