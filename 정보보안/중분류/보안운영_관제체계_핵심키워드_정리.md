# 보안 운영 및 관제체계 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 기존체계 한계 → 신체계 구성요소 → 도입효과/적용 시나리오

---

## 1. SOAR (Security Orchestration, Automation and Response)

**기존체계 한계**
> 전통적 SIEM은 수많은 보안이벤트를 **탐지·수집**하는 데는 강하지만, 그 이후 "실제 대응(차단·격리·조치)"은 여전히 보안담당자가 수작업으로 처리해야 해 대응속도가 느리고 인력의존도가 높음(알림 과부하, Alert Fatigue)

**3대 구성요소**

| 구성요소 | 내용 |
|---|---|
| **오케스트레이션(Orchestration)** | 방화벽·EDR·SIEM 등 여러 보안솔루션을 하나의 워크플로우로 통합 연계 |
| **플레이북(Playbook)** | "이런 유형의 위협이 탐지되면 이런 순서로 대응한다"는 사전 정의된 대응절차(자동화 시나리오) |
| **자동화(Automation)** | 플레이북에 따라 IP차단, 계정잠금, 격리 등을 인간개입 없이(또는 최소개입으로) 자동실행 |

**도입효과/적용 시나리오**
- 시나리오: 피싱메일 탐지 → SOAR가 자동으로 발신자IP 차단 + 동일메일 수신한 다른 직원 메일함에서 자동삭제 + 담당자에게는 결과보고만 전달(사람은 최종 검토만)
- 효과: 평균 대응시간(MTTR) 대폭 단축, 반복적 단순대응 업무의 인력부담 경감, 야간·휴일에도 무인 자동대응 가능

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| SIEM | SOAR가 입력데이터(탐지결과)를 받아오는 전제 시스템(다음 키워드) |
| EDR/NDR | SOAR의 플레이북이 실제 차단·격리 명령을 내리는 실행 대상 솔루션 |
| 측면이동(Lateral Movement) | SOAR의 자동대응이 막아야 하는 대표적인 빠른 확산위협 |

## 2. SIEM (Security Information and Event Management)

**기존체계 한계**
> 방화벽·서버·IDS 등 장비마다 **로그가 따로 흩어져 있어**, 하나의 침해사고가 여러 시스템에 걸쳐 발생해도 전체 그림을 보지 못하고 개별 로그만으로는 공격을 놓치기 쉬움

**구성요소**
```
[각종 장비 로그(방화벽/서버/IDS/엔드포인트)] → [SIEM: 로그수집·정규화·통합저장]
   → [상관분석(Correlation)] 여러 로그를 연관지어 단일 공격을 재구성
   → [대시보드/경보] 탐지된 위협을 시각화하고 보안관제요원에게 알림
```

**SOAR와의 비교(역할 분담)**

| 구분 | SIEM | SOAR |
|---|---|---|
| 핵심역할 | 로그수집·통합·탐지(가시성) | 탐지 이후 대응 자동화(행동) |
| 출력 | 경보(Alert) | 실제 조치(차단/격리) |

**도입효과/적용 시나리오**: 여러 시스템에 분산된 로그를 한곳에서 분석해 "내부 PC1대 감염→여러 서버 동시 비정상접속"같은 패턴을 발견(개별로그만으로는 놓칠 위협을 상관분석으로 포착)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| ELK 스택 | SIEM을 오픈소스로 구축할 때 사용되는 대표적 로그수집·분석 플랫폼 |
| 데이터 관측가능성(Data Observability) | SIEM의 "여러 소스의 데이터를 모아 이상을 탐지"하는 철학과 유사한 데이터 도메인 개념 |
| TTPs / MITRE ATT&CK | SIEM의 상관분석 규칙을 설계할 때 활용하는 공격패턴 분류체계 |

## 3. CTEM (Continuous Threat Exposure Management) 5단계

**기존체계 한계**
> 전통적 취약점관리는 "연 1~2회 정기점검"처럼 **주기적·일회성**으로 이뤄져, 점검 사이 기간에 새로 발생한 취약점·공격표면 변화에 대응하지 못함

**5단계 프로세스**

| 단계 | 내용 |
|---|---|
| **① 범위설정(Scoping)** | 보호해야 할 핵심 비즈니스 자산·공격표면 범위 정의 |
| **② 발견(Discovery)** | 자산·취약점·잘못된 설정을 지속적으로 스캐닝해 식별 |
| **③ 우선순위화(Prioritization)** | 단순 CVSS점수가 아닌 실제 악용가능성·비즈니스영향을 고려해 우선순위 산정 |
| **④ 검증(Validation)** | 실제 공격이 통할지 모의공격(레드팀 등)으로 검증 |
| **⑤ 동원(Mobilization)** | 검증된 위협에 대해 실제 조치(패치·정책변경)를 신속히 실행하도록 조직 동원 |

**도입효과/적용 시나리오**: 클라우드 환경처럼 자산이 실시간으로 변하는 상황에서, 매달 정기점검만으로는 새로 열린 포트·신규 클라우드자원의 노출을 놓치는 문제를 "지속적" 프로세스로 해결

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 네트워크 스캐닝 / ASM(Attack Surface Management) | CTEM의 ②발견 단계에서 실제로 사용되는 기술 |
| 레드티밍(Red Teaming) | CTEM ④검증 단계의 핵심 실행방법 |
| 제로트러스트 | "지속적으로 검증한다"는 CTEM의 철학이 제로트러스트의 Continuous Verification과 동일선상 |

## 4. N2SF (National Network Security Framework, 국가 망보안체계)

**기존체계 한계**
> 기존 망분리 정책은 물리적 분리에 의존해 클라우드·원격근무 등 디지털전환 환경에 적용하기 어렵고, 일률적인 "분리 여부"만 규정해 데이터 중요도별 차등보안이 부족했음

**구성요소(적용 절차)**
```
[데이터/시스템 중요도 분류] → [등급별 보안수준(zone) 결정]
   → [망분리/클라우드 등 다양한 구현방식 중 등급에 맞는 방식 선택]
   → [모니터링/감사체계로 지속 검증]
```
- 기존의 경직된 "물리적 망분리 일괄적용" 대신, 데이터 중요도에 따라 **클라우드 기반 망분리 등 유연한 구현방식**을 등급별로 허용

**보안고려사항(고려사항)**: 기관별 데이터 중요도 분류기준의 일관성 확보, 클라우드 전환 시에도 기존 망분리 수준 이상의 보안성 입증 필요

**도입효과/적용 시나리오**: 공공기관이 일률적 물리적 망분리 대신 등급에 따라 일부 업무는 안전성이 검증된 클라우드 환경에서 처리할 수 있게 되어 디지털전환 속도와 보안성을 동시에 확보

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 망분리(원칙/유형/장단점) | N2SF가 기존 망분리 정책을 보완·고도화한 차세대 버전 |
| 데이터안심구역 / 개인정보안심구역 | 데이터 중요도별 차등 보안환경이라는 점에서 N2SF와 유사한 철학 공유 |
| 제로트러스트 | N2SF도 경계기반(망분리)에서 보다 유연한 모델로 전환하는 흐름의 일환 |

## 5. 융합보안관제

**기존체계 한계**
> 물리보안(CCTV·출입통제)과 정보보안(IT 네트워크)이 **별도 시스템·별도 운영조직**으로 분리되어 있어, "출입카드 도용 후 내부망 접속"같은 물리+사이버 결합공격을 놓치기 쉬움

**구성요소(시스템 구성요소)**
```
[물리보안 솔루션: CCTV/출입통제/생체인증]   [정보보안 솔루션: 방화벽/IPS/SIEM]
              └─────────── 통합관제플랫폼 ───────────┘
              (이벤트를 한 화면에서 융합분석, 연계 대응)
```

**구축 시 고려사항과 활용기술**: 물리·IT 보안솔루션 간 API 연동표준화, 이벤트 연관분석(예: "출입기록 없는 사람이 사내망 접속" 탐지) 룰 설계

**도입효과/적용 시나리오**: 퇴사자의 출입카드가 비활성화되었는데 그 시간에 VPN 접속시도가 발생하면 즉시 융합관제센터에서 동시탐지·차단(물리보안 단독, IT보안 단독으로는 놓칠 수 있는 패턴)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| SIEM/SOAR | 융합보안관제의 정보보안 측 이벤트를 처리하는 기반 시스템 |
| TPM / 생체인증 | 융합보안관제에서 물리적 신원확인의 신뢰성을 보강하는 기술 |

## 6. 리버스 프록시 (Reverse Proxy)

**기존체계 한계**
> 내부 웹서버가 외부에 직접 노출되면, 서버의 실제 IP·구조가 그대로 공격자에게 알려져 직접 공격(DDoS·취약점스캔)에 취약하고, 여러 서버를 운영할 때 트래픽 분산이 어려움

**구성요소(개념/동작원리)**
```
[외부 사용자] → [리버스 프록시(공개IP)] → [내부 웹서버1/2/3(비공개 사설IP)]
(사용자는 프록시 IP만 알고, 내부 서버의 실제 IP/구조는 은닉됨)
```
- 동작원리: 클라이언트 요청을 프록시가 대신 받아 내부서버에 전달 → 응답을 다시 클라이언트에게 전달(서버 입장의 대리인 역할, 일반 프록시는 클라이언트 대리)
- 설정방법: Nginx/Apache 등에서 `proxy_pass` 설정으로 내부서버 주소 매핑, 로드밸런싱 알고리즘(라운드로빈 등) 추가 설정

**도입효과/적용 시나리오**: 내부서버 IP 은닉으로 직접공격 방어, SSL종료(암복호화 부담을 프록시가 전담)로 내부서버 부하 경감, 여러 내부서버에 트래픽 분산(로드밸런싱)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| DDoS 사이버대피소 | 리버스프록시와 함께 결합되어 대규모 공격트래픽을 흡수하는 인프라(다음 키워드) |
| 무중단배포(Blue-Green/Canary) | 리버스프록시가 트래픽을 신규/구버전 서버로 전환배분하는 무중단배포의 핵심 인프라 |
| WAF(웹애플리케이션방화벽) | 리버스프록시 위치에 WAF 기능을 결합해 애플리케이션 계층 공격까지 방어 확장 |

## 7. DDoS 사이버대피소

**기존체계 한계**
> 중소기업·소규모 웹사이트는 자체적으로 대규모 DDoS 공격에 대응할 인프라(고용량 회선·전문장비)를 갖추기 어려워, 공격받으면 그대로 서비스마비를 감내해야 하는 상황

**구성요소(국가 제공 인프라 구조)**
```
[공격받는 기업 웹사이트] → (트래픽을 일시적으로) [사이버대피소(KISA 등 운영)]
   → 대피소의 고용량 인프라에서 정상트래픽과 공격트래픽을 필터링
   → 정상트래픽만 다시 원래 기업 서버로 전달
```

**도입효과/적용 시나리오**: 중소기업이 대규모 DDoS 공격을 받을 때, 트래픽을 일시적으로 국가 사이버대피소로 우회시켜 자체 인프라 투자 없이도 공격을 무력화하고 정상서비스를 지속

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| DDoS / 미라이봇넷 | 사이버대피소가 대응하는 공격의 실체 |
| 리버스프록시 / CDN | 사이버대피소가 작동하는 방식(트래픽 우회·필터링)과 동일한 기술적 원리 공유 |
| Anycast | 대규모 트래픽을 지역적으로 분산시켜 공격 영향을 완화하는 추가 기술 |

## 종합 흐름도

```
[탐지 인프라] SIEM(로그통합·탐지) ──→ SOAR(자동 오케스트레이션·대응)
        │
[지속관리 프로세스] CTEM 5단계(범위설정→발견→우선순위화→검증→동원)
        │
[국가/조직 정책체계] N2SF(데이터등급별 유연한 망보안) ──→ 융합보안관제(물리+IT 통합)
        │
[가용성 보호 인프라] 리버스프록시(IP은닉·부하분산) ──→ DDoS 사이버대피소(대규모공격 흡수)
```
