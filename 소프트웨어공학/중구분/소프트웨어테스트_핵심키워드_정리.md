# 소프트웨어 테스트 및 검증 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 원칙 → 기법 비교 → 실제 테스트케이스 작성

---

## 1. 테스트 7대 원칙

**원칙**
1. **테스팅은 결함이 존재함을 보여줄 뿐, 결함이 없음을 증명하지 못한다**(결함부재의 오류)
2. **완벽한 테스팅(전수테스트)은 불가능**(시간·자원 제약상 모든 경우의수 테스트 불가)
3. **조기 테스팅**(결함은 발견이 늦을수록 수정비용 급증, 개발초기부터 테스트 활동 시작)
4. **결함 집중(Defect Clustering)**: 결함은 소수 모듈에 집중되는 경향(파레토 법칙, 80:20)
5. **살충제 패러독스(Pesticide Paradox)**: 동일 테스트를 반복하면 새 결함을 못찾게 됨(아래에서 상세)
6. **테스팅은 정황(Context) 의존적**: 의료SW와 게임SW는 테스트 강도·방법이 다름
7. **오류부재의 궤변(Absence-of-errors Fallacy)**: 결함이 없어도 사용자요구를 충족못하면 품질문제

**기법 비교(원칙이 실무에 주는 시사점)**

| 원칙 | 실무 함의 |
|---|---|
| 결함집중 | 결함이 많이 발견된 모듈에 테스트 자원을 우선 집중배치 |
| 살충제패러독스 | 테스트케이스를 주기적으로 갱신·추가해야 함 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 살충제 패러독스 | 7대원칙 중 하나가 별도 핵심키워드로 출제될 만큼 중요(다음 항목에서 상세) |
| 회귀테스트 | 7대원칙의 "조기테스팅"·"결함집중"을 운영단계까지 지속 적용하는 기법 |

## 2. 살충제 패러독스 (Pesticide Paradox)

**원칙**
> 같은 살충제를 반복사용하면 벌레가 내성을 갖게 되는 것처럼, **동일한 테스트케이스 세트를 반복 실행하면 더 이상 새로운 결함을 찾아내지 못하는** 현상(이미 그 테스트들이 통과하는 코드경로의 결함은 다 잡혔기 때문)

**기법 비교(대응방안)**

| 대응 | 방식 |
|---|---|
| 테스트케이스 주기적 갱신 | 새로운 입력값·경계조건·시나리오를 지속 추가 |
| 다양한 테스트기법 혼용 | 블랙박스+화이트박스+탐색적테스트(몽키테스트 등)를 교차 적용 |
| 뮤테이션테스트 | 테스트케이스 자체의 결함탐지력을 정량평가해 약한 테스트를 보강(아래 키워드) |

**실제 테스트케이스 작성(예시)**: 기존 회귀테스트셋이 "정상입력 10건"만 반복돼왔다면, 신규로 "경계값(0, 최대값)", "이상입력(특수문자)", "동시성(동시요청)" 케이스를 추가해 테스트셋 자체를 진화시킴

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 뮤테이션테스트 | 살충제패러독스를 정량적으로 측정·극복하는 핵심 기법(아래에서 상세) |
| 탐색적테스트 / 몽키테스트 | 정형화된 테스트케이스의 한계를 보완하는 비정형적 접근(아래에서 상세) |

## 3. 화이트박스 테스트 vs 블랙박스 테스트

**기법 비교**

| 구분 | 화이트박스(White Box) | 블랙박스(Black Box) |
|---|---|---|
| 관점 | 내부 코드구조를 알고 테스트 | 내부구조를 모르고 입출력만으로 테스트 |
| 목적 | 코드의 모든 논리경로 검증 | 요구사항 충족여부 검증 |
| 대표기법 | 구문커버리지, 조건커버리지, 결정커버리지, 경로커버리지 | 동등분할, 경계값분석, 상태전이, 에러예측 |
| 수행주체 | 개발자(단위테스트 단계) | 테스터/QA(시스템·인수테스트 단계) |

**커버리지 기준 상세**
- **구문커버리지(Statement Coverage)**: 모든 코드라인이 최소1회 실행됐는지
- **조건커버리지(Condition Coverage)**: 조건문의 각 조건(True/False)이 모두 실행됐는지
- **결정커버리지(Decision Coverage)**: 각 분기(if문 등)의 모든 분기경로가 실행됐는지

**실제 테스트케이스 작성 — 동등분할(Equivalence Partitioning) & 경계값분석(Boundary Value Analysis) (139회 기출 패턴)**

> **명세**: 학점(Grade) 처리 모듈 / 입력: 점수(Score), 0~100 / 출력: 90이상→"A", 80이상90미만→"B", 70이상80미만→"C", 60이상70미만→"D", 60미만→"F", 범위외→"ERROR"

**동등분할(클래스 도출)**

| 클래스 | 범위 | 대표값 |
|---|---|---|
| 유효1 | 90~100 | 95 → "A" |
| 유효2 | 80~89 | 85 → "B" |
| 유효3 | 70~79 | 75 → "C" |
| 유효4 | 60~69 | 65 → "D" |
| 유효5 | 0~59 | 30 → "F" |
| 무효1 | 100초과 | 150 → "ERROR" |
| 무효2 | 0미만 | -10 → "ERROR" |

**경계값분석(각 구간경계 ±1 테스트)**

| 테스트케이스 | 입력값 | 기대출력 |
|---|---|---|
| TC1 | 100 | A (상한경계) |
| TC2 | 90 | A (구간시작) |
| TC3 | 89 | B (구간끝, A와B경계) |
| TC4 | 80 | B |
| TC5 | 79 | C |
| TC6 | 60 | D |
| TC7 | 59 | F |
| TC8 | 0 | F (하한경계) |
| TC9 | 101 | ERROR (상한초과) |
| TC10 | -1 | ERROR (하한미달) |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 분류트리기법(Classification Tree) | 동등분할을 시각적 트리구조로 확장한 137회 기출 명세기반기법 |
| 명세기반 vs 구조기반 vs 경험기반 테스트 | 블랙박스(명세기반)·화이트박스(구조기반)에 더해 탐색적테스트(경험기반)까지 포함하는 상위 분류체계 |
| KS X ISO/IEC/IEEE 29119 | 위 테스트설계기법들을 국제표준으로 체계화한 표준(아래에서 상세) |

## 4. TDD (테스트주도개발) vs BDD (행위주도개발)

**기법 비교**

| 구분 | TDD | BDD |
|---|---|---|
| 작성주체 | 개발자 | 개발자+QA+비즈니스(고객)가 함께 |
| 작성단위 | 함수/메서드 단위 테스트코드 | 사용자 행위(시나리오) 단위 |
| 표현방식 | 일반 단위테스트 코드(assert문) | **Given-When-Then** 자연어 형식 시나리오 |
| 목적 | 코드의 정확성 보장, 설계개선 유도 | 비즈니스요구와 구현의 일치 확인(공통언어 확보) |

**TDD 순환주기**: Red(실패하는 테스트 먼저작성) → Green(테스트를 통과시키는 최소코드 작성) → Refactor(코드 개선, 테스트는 계속 통과 유지)

**실제 테스트케이스 작성(BDD 시나리오 예시)**
```gherkin
Feature: 학점 산출
  Scenario: 90점 이상이면 A를 받는다
    Given 학생의 점수가 95점일 때
    When 학점을 산출하면
    Then 결과는 "A"이다
```

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 핑퐁 프로그래밍 | TDD를 두 사람이 교대로 수행하는 페어프로그래밍 변형(SW방법론 도메인과 연결) |
| XP 12대실천 | TDD가 속하는 상위 애자일 엔지니어링 방법론 |
| Cucumber/Gherkin | BDD의 Given-When-Then 시나리오를 실행가능한 테스트로 만드는 대표 도구 |

## 5. 정적분석 vs 동적분석

**기법 비교**

| 구분 | 정적분석(Static Analysis) | 동적분석(Dynamic Analysis) |
|---|---|---|
| 실행여부 | 프로그램을 **실행하지 않고** 코드자체를 검사 | 프로그램을 **실제 실행**하며 검사 |
| 발견대상 | 코딩표준위반, 잠재적버그패턴, 보안약점(SAST) | 실제 런타임 동작오류, 메모리누수, 성능문제 |
| 대표도구 | SonarQube, Checkstyle | 디버거, 프로파일러, DAST 도구 |
| 한계 | 실제 실행 시에만 드러나는 문제는 못잡음(예: 외부API 응답지연) | 모든 코드경로를 실행하지 않으면 누락발생 |

**실제 적용 예시**: CI파이프라인의 빌드단계에서 정적분석(SAST)으로 코드품질·보안약점 1차 차단 후, 테스트단계에서 동적분석(DAST)으로 실제 동작 중 발생하는 문제까지 2차 검증(DevSecOps 파이프라인의 표준구성)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| DevSecOps(Shift-Left) | 정적/동적분석이 실제로 파이프라인에 통합되는 보안 실천체계(SW방법론 도메인과 연결) |
| McCabe 순환복잡도 | 정적분석 도구가 자동산출하는 대표적 코드품질 지표 |
| SBOM/SCA | 정적분석의 한 종류로 오픈소스 구성요소의 취약점을 분석하는 기법 |

## 6. 회귀테스트 vs 뮤테이션테스트

**기법 비교**

| 구분 | 회귀테스트(Regression Test) | 뮤테이션테스트(Mutation Test) |
|---|---|---|
| 목적 | 코드변경(버그수정·신규기능)이 **기존기능을 깨뜨리지 않았는지** 확인 | 기존 **테스트케이스 자체의 결함탐지능력**을 평가 |
| 수행방식 | 기존 테스트셋을 변경 후 코드에 재실행 | 원본코드에 의도적 결함(Mutant, 예: `>`를 `>=`로 변경)을 주입 후 테스트셋이 그 결함을 잡아내는지 확인 |
| 결과해석 | 기존 테스트 통과/실패로 회귀버그 여부 판단 | Mutant를 잡아낸 비율(Mutation Score)이 낮으면 테스트셋이 약함 |

**실제 테스트케이스 작성(뮤테이션테스트 예시)**
```
원본코드: if (score >= 90) return "A";
뮤턴트1:  if (score >  90) return "A";   // >= 를 > 로 변경(Mutant)

기존 테스트케이스 TC2(score=90, 기대값="A")를 뮤턴트1에 실행
→ 뮤턴트1은 score=90일때 false가 되어 "A"를 반환못함(테스트 실패)
→ 테스트케이스가 뮤턴트를 정확히 "잡아냄"(Killed) → 테스트셋이 해당 경계조건을 잘 검증하고 있음을 확인
```

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 살충제패러독스 | 뮤테이션테스트가 정량적으로 극복하는 문제(테스트셋의 노화·약화) |
| 회귀테스트 vs 몽키테스트 | 회귀테스트(정형적, 기존케이스 재실행)와 몽키테스트(비정형적, 무작위입력)의 비교(129회 기출패턴, 아래에서 정리) |
| CI/CD 파이프라인 | 회귀테스트가 매 빌드마다 자동실행되는 표준 통합지점 |

## 7. 테스트 커버리지 vs 코드 커버리지

**기법 비교**

| 구분 | 코드 커버리지(Code Coverage) | 테스트 커버리지(Test Coverage) |
|---|---|---|
| 측정대상 | **코드(구현물)** 기준 — 화이트박스 관점 | **요구사항/기능** 기준 — 명세 충족 여부 관점 |
| 측정방식 | 실행된 라인/분기/조건의 비율(%) | 테스트된 요구사항/기능 항목의 비율(%) |
| 한계 | 100%여도 요구사항 자체를 놓치면 무의미(코드는 다 돌았지만 빠진 기능 존재 가능) | 코드 내부의 숨은 결함(예외처리 누락 등)은 못잡을 수 있음 |

**실제 적용 예시**: "결제 모듈의 코드커버리지 95%"이지만, 요구사항 중 "해외결제 예외처리" 자체가 테스트케이스에 없다면 테스트커버리지는 낮음(요구사항 기준 누락) — 두 지표를 함께 관리해야 진정한 품질보증 가능

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| RTM(요구사항추적매트릭스) | 테스트커버리지를 요구사항 단위로 추적·관리하는 도구(요구공학 도메인과 연결) |
| 구문/조건/결정 커버리지 | 코드커버리지를 세분화한 화이트박스 측정기준(2번항목과 연결) |

## 8. 알파/베타/인수테스트 + 몽키테스트

**기법 비교**

| 구분 | 알파테스트 | 베타테스트 | 인수테스트 |
|---|---|---|---|
| 수행주체 | 개발조직 내부(QA 등) | 실제 외부사용자(일부 공개) | 고객/발주처(계약상 검수) |
| 환경 | 통제된 개발환경 | 실사용환경(다양한 환경) | 운영과 동일한 환경 |
| 목적 | 출시전 내부품질 검증 | 실사용자 피드백 수집 | 계약요구사항 충족여부 최종 승인 |

**인수테스트 프로세스**: 인수기준(Acceptance Criteria) 정의 → 인수테스트 계획수립 → 테스트수행(고객 참관) → 결함조치 → 최종승인(Sign-off)

**몽키테스트(Monkey Test) vs 회귀테스트(129회 기출패턴)**

| 구분 | 몽키테스트 | 회귀테스트 |
|---|---|---|
| 입력방식 | 무작위(임의)·비정형적 입력으로 예측불가 시나리오 탐색 | 정해진(정형화된) 테스트케이스 재실행 |
| 목적 | 예상치못한 충돌·예외상황 발견 | 기존기능 정상동작 확인(회귀버그 방지) |
| 자동화 | 무작위입력 생성도구로 자동화 가능 | 테스트자동화 프레임워크로 반복실행 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 사용자스토리의 인수기준 | 인수테스트가 검증하는 직접적 기준(요구공학 도메인과 연결) |
| 카오스엔지니어링 | 몽키테스트의 사상을 운영환경 장애주입실험으로 확장한 현대적 기법(Netflix의 Chaos Monkey가 명칭의 유래) |
| 무중단배포(Canary) | 베타테스트의 "일부 사용자 노출" 개념이 Canary배포 전략과 유사한 철학 공유 |

## 9. KS X ISO/IEC/IEEE 29119 (소프트웨어 테스팅 국제표준)

**원칙(표준 구성 5개 Part)**

| Part | 내용 |
|---|---|
| Part 1 | 개념·용어 정의 |
| Part 2 | 테스트 프로세스(테스트관리 프로세스 + 동적테스트 프로세스) |
| Part 3 | 테스트 문서화(테스트계획서·테스트케이스 명세 양식) |
| Part 4 | **테스트 설계기법**(명세기반·구조기반·경험기반 기법 표준 정의) |
| Part 5 | 키워드기반 테스팅(자동화를 위한 테스트스크립트 표준화) |

**기법 비교(설계 및 구현 프로세스)**
```
테스트설계 → 테스트케이스 도출(Part4의 기법 적용) → 테스트절차 명세(Part3 문서양식)
   → 테스트환경 구성 → 테스트구현(실행가능한 테스트스크립트화)
```

**ISO/IEC 25010 품질특성과 명세기반 테스트기법 매핑(128회 기출패턴)**

| ISO25010 품질특성 | 대응 테스트설계기법 |
|---|---|
| 기능적합성(Functional Suitability) | 동등분할, 결정테이블 |
| 신뢰성(Reliability) | 상태전이테스트(예외상황 처리 확인) |
| 사용성(Usability) | 탐색적테스트, 사용자시나리오테스트 |
| 성능효율성(Performance Efficiency) | 부하테스트, 스트레스테스트 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| ISO/IEC 25010 | 29119의 테스트기법이 검증해야 할 목표 품질특성을 정의하는 표준(SW품질 도메인과 연결) |
| 명세기반/구조기반/경험기반 테스트 | 29119 Part4가 공식적으로 분류한 3대 테스트기법 범주 |
