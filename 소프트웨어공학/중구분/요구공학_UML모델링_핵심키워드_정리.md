# 요구사항 공학 및 UML 모델링 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 절차 → 산출물 → 다이어그램 실제 작성/변환

---

## 1. 요구사항 도출 / 분석 / 명세 / 검증 (요구공학 4단계)

**절차**
```
①요구사항 도출(Elicitation)
   인터뷰, 워크숍, 설문, 관찰, 프로토타이핑 등으로 스테이크홀더의 요구를 수집
       ↓
②요구사항 분석(Analysis)
   수집된 요구 간 모순·중복 제거, 우선순위 결정, 분류(기능/비기능 요구사항 구분)
       ↓
③요구사항 명세(Specification)
   분석된 요구를 명확하고 검증가능한 형태(SRS 문서, 유스케이스 등)로 문서화
       ↓
④요구사항 검증(Validation)
   명세서가 실제 고객의 의도와 일치하는지 검토(리뷰·워크스루·프로토타입 확인)
```

**산출물**: 요구사항정의서, SRS(Software Requirements Specification), 요구사항 우선순위표, 검토회의록

**다이어그램 실제 작성/변환**: 도출단계의 자연어 요구("회원은 주문을 취소할 수 있어야 한다")를 분석단계에서 유스케이스("주문취소")로, 명세단계에서 유스케이스 시나리오 문서로, 검증단계에서 다시 고객과 함께 시나리오를 워크스루하며 확인하는 흐름으로 구체화

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 요구사항 모호성 통제기법 | 자연어 요구의 모호함(예: "빠르게")을 정량적 기준("3초 이내")으로 구체화하는 기법 |
| 기능/비기능 요구사항 | 분석단계에서 요구를 분류하는 가장 기본적인 기준 |
| ISP/ISMP | 요구공학 4단계가 실제 정보화사업 기획서 작성 절차의 핵심 구성요소로 포함됨(경영정보시스템 도메인과 연결) |

## 2. RTM (Requirements Traceability Matrix, 요구사항 추적 매트릭스)

**절차**
```
①각 요구사항에 고유ID 부여 → ②요구사항이 어떤 설계요소(컴포넌트)에 반영되는지 매핑
   → ③설계요소가 어떤 코드모듈로 구현되는지 매핑 → ④어떤 테스트케이스로 검증되는지 매핑
(요구사항 ID 하나가 설계→구현→테스트까지 끝까지 추적 가능해야 함)
```

**산출물(매트릭스 예시)**

| 요구사항ID | 요구사항명 | 설계요소 | 구현모듈 | 테스트케이스ID |
|---|---|---|---|---|
| REQ-001 | 주문취소 기능 | 주문관리 컴포넌트 | OrderCancelService.java | TC-015 |
| REQ-002 | 결제수단 다양화 | 결제 컴포넌트 | PaymentGateway.java | TC-022, TC-023 |

**다이어그램 실제 작성/변환**: 위와 같은 표 형태로 작성하며, 신규 요구사항 추가 시 빈 칸(설계요소 매핑 없음)이 보이면 "설계 누락"을 즉시 발견할 수 있는 검증도구로 활용

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| CRUD매트릭스 | RTM과 유사하게 "교차표(매트릭스)" 형태로 추적·검증하는 데이터베이스 도메인의 도구 |
| 영향분석(Impact Analysis) | RTM이 있으면 요구사항 변경 시 영향받는 설계·코드·테스트를 즉시 파악 가능(변경관리의 핵심기반) |
| 정보시스템 감리 | 감리원이 RTM을 통해 요구사항-구현 간 누락여부를 핵심적으로 점검 |

## 3. 유스케이스 (Use Case) 모델링

**절차**
```
①액터(Actor) 식별(시스템과 상호작용하는 외부주체 — 사용자, 외부시스템)
   → ②액터별 목표(Goal) 식별 → ③유스케이스(시스템이 제공하는 기능단위) 도출
   → ④유스케이스 간 관계 정의(포함<<include>>/확장<<extend>>/일반화) → ⑤시나리오(기본흐름·대안흐름) 작성
```

**산출물(유스케이스 다이어그램 + 시나리오 명세서)**
```
        [도서예약시스템]
   (회원) ──── (도서검색)
     │  \         │
     │   \    <<include>>
     │    \        │
     │     (도서예약)──<<include>>──(예약확인발송)
     │           │
     │      <<extend>>
     │           │
     │      (예약취소)
   (관리자) ──── (도서등록)
```

**다이어그램 실제 작성/변환(시나리오 명세 예시)**
> 유스케이스: "도서예약" / 기본흐름: ①회원이 도서검색 ②원하는 도서 선택 ③예약신청 ④시스템이 재고확인 ⑤예약확정 및 확인메일 발송 / 대안흐름: ④에서 재고없음 → 예약대기 등록

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 액터(Actor) | 유스케이스 다이어그램의 핵심 구성요소(사람 또는 외부시스템) |
| 시퀀스다이어그램 | 유스케이스의 기본흐름을 더 상세한 객체 간 메시지교환으로 구체화하는 동적다이어그램(아래에서 변환예시) |
| 페르소나/사용자스토리 | 유스케이스의 "액터"를 더 구체적 인물상(페르소나)이나 짧은 요구문장(사용자스토리)으로 표현하는 보완기법 |

## 4. 페르소나 (Persona)

**절차**
```
①사용자 리서치(인터뷰·설문·행동관찰) → ②사용자 그룹의 공통패턴 도출
   → ③대표 인물상(가상의 인물) 설정(이름·나이·직업·목표·불편함 등 구체적 서술)
   → ④설계·기획 단계 전반에서 "이 페르소나라면 어떻게 생각할까"를 판단기준으로 활용
```

**산출물(페르소나 카드 예시)**
```
[페르소나: 김민준, 32세, IT기업 개발자]
- 목표: 출퇴근 시간에 짧게 뉴스를 확인하고 싶음
- 불편함: 기존 앱은 로딩이 느리고 광고가 많아 이탈함
- 사용패턴: 하루 3회, 1회당 2분 이내 사용
```

**다이어그램 실제 작성/변환**: 페르소나의 "목표·불편함"을 그대로 사용자스토리("출퇴근하는 직장인으로서, 빠르게 로딩되는 뉴스앱을 원한다, 광고로 인한 이탈을 막기 위해")로 전환해 백로그에 등록

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 사용자스토리 | 페르소나의 구체적 요구를 애자일 백로그 항목으로 변환하는 다음 단계(바로 아래 키워드) |
| 프로토타이핑 | 페르소나를 기준으로 제작한 프로토타입에 대한 사용성평가 수행 |
| UX(사용자경험) | 페르소나가 UX설계 전반의 의사결정 기준으로 활용되는 상위 분야 |

## 5. 사용자 스토리 (User Story)

**절차**
```
①페르소나/이해관계자 요구파악 → ②표준 템플릿으로 짧게 작성
   "[역할]로서, [원하는것]을 원한다, [이유/가치]를 위해서"
   → ③인수기준(Acceptance Criteria) 추가(완료의 기준 명확화) → ④백로그에 등록·우선순위화
```

**산출물(사용자스토리 카드 예시)**
```
[사용자스토리] "고객으로서, 장바구니에 담은 상품을 한번에 결제하고 싶다, 
               여러번 결제하는 번거로움을 없애기 위해"
[인수기준] - 장바구니 내 모든 상품의 합계금액이 정확히 표시되어야 한다
          - 결제수단(카드/계좌이체) 선택이 가능해야 한다
          - 결제완료 후 주문번호가 즉시 발급되어야 한다
```

**다이어그램 실제 작성/변환**: 사용자스토리는 그 자체로 다이어그램화되진 않으나, 이를 기반으로 유스케이스나 시퀀스다이어그램으로 구체화해 개발팀의 설계 산출물로 전환

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 인수기준(Acceptance Criteria) / 인수테스트 | 사용자스토리의 "완료 정의"가 테스트케이스로 그대로 연결(SW테스트 도메인과 연결) |
| 스크럼 백로그 | 사용자스토리가 실제로 관리되는 애자일 작업단위 저장소 |
| 유스케이스 | 전통적 방법론의 유스케이스 vs 애자일의 사용자스토리 — 표현방식 비교출제 빈번(유스케이스는 시나리오 전체, 사용자스토리는 짧은 한문장) |

## 6. UML 2.0 (정적/동적 구조)

**절차(UML 다이어그램 13종 분류)**

```
[구조적(정적) 다이어그램] 시스템의 "정지된 모습" 표현
  클래스다이어그램, 객체다이어그램, 컴포넌트다이어그램, 배치다이어그램, 패키지다이어그램, 복합체구조다이어그램

[행위(동적) 다이어그램] 시스템의 "동작·흐름" 표현
  유스케이스다이어그램, 시퀀스다이어그램, 활동다이어그램, 상태다이어그램, 협력(통신)다이어그램, 타이밍다이어그램, 상호작용개요다이어그램
```

**산출물 및 실제 변환 예시(126회 기출 패턴 — 협력다이어그램 → 시퀀스다이어그램 변환)**

**[협력다이어그램(개념)]**: 회원(Member) ↔ 도서예약시스템(BookingSystem) ↔ 도서DB(BookDB) 간 "도서예약" 메시지 교환관계만 표현(객체 간 연결선 중심)

**[시퀀스다이어그램으로 변환]**
```
Member          BookingSystem          BookDB
  │── 1:도서검색요청 ──→│                    │
  │                    │── 2:재고조회 ──────→│
  │                    │←── 3:재고정보 ───────│
  │←── 4:검색결과 ──────│                    │
  │── 5:예약신청 ──────→│                    │
  │                    │── 6:재고차감 ──────→│
  │                    │←── 7:차감완료 ───────│
  │←── 8:예약확정통보 ───│                    │
```
> 협력다이어그램의 "관계"를 시퀀스다이어그램의 "시간순서가 있는 메시지흐름"으로 변환 — 번호(1,2,3...)가 호출순서를 명시하는 것이 핵심 차이점

**구성요소별 표기법**: 생명선(Lifeline, 점선), 활성화바(Activation Bar, 실행구간 박스), 메시지(화살표, 동기메시지=실선화살표/비동기메시지=빈화살표), 반환메시지(점선화살표)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 클래스다이어그램 작성절차 | 정적구조를 표현하는 가장 핵심적인 UML다이어그램(별도 작성절차로 자주 출제) |
| 활동다이어그램 / 상태다이어그램 | 시퀀스다이어그램과 함께 비교출제되는 행위다이어그램 3종(137회 기출 패턴) |
| MSA / 컴포넌트다이어그램 | 구조적다이어그램이 현대 마이크로서비스 아키텍처 설계에도 그대로 활용됨 |
| OCL(Object Constraint Language) | UML 모델에 정형화된 제약조건(불변식 등)을 추가로 명시하는 보완언어 |

## 종합 흐름도

```
[요구공학 절차] 도출 → 분석 → 명세 → 검증
        │
        ├──→ RTM(요구사항-설계-구현-테스트 전체 추적)
        │
        ├──→ 페르소나(사용자 구체화) → 사용자스토리(짧은요구문장, 애자일)
        │
        └──→ 유스케이스(전통적 시나리오 명세)
                    │
              [UML 2.0으로 구체화]
              구조적(정적) 다이어그램 ── 행위(동적) 다이어그램
              (클래스/컴포넌트 등)        (유스케이스/시퀀스/활동/상태 등)
                    │
              실제 변환: 협력다이어그램 → 시퀀스다이어그램(메시지순서 명시)
```
