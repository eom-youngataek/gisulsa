# SW 품질 표준 및 메트릭 통제 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 표준 구성요소 → 측정공식 계산 → 개선기법 연계

---

## 1. ISO/IEC 25010 (제품품질모델, 8대 속성)

**표준 구성요소**

| 품질특성 | 정의 |
|---|---|
| **기능적합성(Functional Suitability)** | 명시된 기능을 정확히 수행하는 정도 |
| **성능효율성(Performance Efficiency)** | 자원사용량 대비 성능수준 |
| **호환성(Compatibility)** | 다른 시스템과 정보교환·공존 가능 정도 |
| **사용성(Usability)** | 사용자가 효과적·효율적으로 사용가능한 정도 |
| **신뢰성(Reliability)** | 명시된 조건에서 일정수준 성능을 유지하는 정도 |
| **보안성(Security)** | 정보·데이터를 보호하는 정도 |
| **유지보수성(Maintainability)** | 수정·개선이 용이한 정도 |
| **이식성(Portability)** | 다른 환경으로 옮겨 사용가능한 정도 |

**측정공식/계산(예시 — 신뢰성 측정지표)**: MTBF(평균고장간격) = 총가동시간 / 고장횟수, 가용성 = MTBF/(MTBF+MTTR)

**개선기법 연계**: 유지보수성이 낮게 측정되면 → 리팩토링·기술부채 해소 활동으로 직접 개선, 보안성 미흡시 → DevSecOps의 SAST/DAST 도입

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| ISO/IEC 29119 | 25010의 각 품질특성을 검증하는 테스트설계기법을 정의하는 표준(128회 기출 매핑패턴, SW테스트 도메인과 연결) |
| ISO/IEC 25012 | 25010의 "제품" 품질모델과 짝을 이루는 "데이터" 품질모델(데이터거버넌스 도메인과 연결) |
| SQuaRE(Software Quality Requirements and Evaluation) | ISO/IEC 25000 시리즈 전체를 통칭하는 명칭, 25010이 그 핵심 구성요소 |

## 2. ISO/IEC 12207 (소프트웨어 생애주기 프로세스)

**표준 구성요소(프로세스 분류)**

| 분류 | 내용 |
|---|---|
| **기본생명주기 프로세스** | 획득, 공급, 개발, 운영, 유지보수 프로세스 |
| **지원생명주기 프로세스** | 문서화, 형상관리, 품질보증, 검증, 확인, 검토, 감사, 문제해결 프로세스 |
| **조직생명주기 프로세스** | 관리, 기반구조, 개선, 인적자원관리 프로세스 |

**측정공식/계산**: 프로세스 자체에 대한 정량측정은 아니나, 각 프로세스의 "수행여부·성숙도"를 CMMI 등과 결합해 평가하는 것이 실무관행

**개선기법 연계**: 프로세스 누락(예: 형상관리 프로세스 부재)이 발견되면 → 해당 지원프로세스를 신설하고 표준절차서 수립

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| SDLC | 12207이 SDLC의 각 단계를 국제표준 프로세스로 공식 명세한 것(SW방법론 도메인과 연결) |
| CMMI | 12207이 "어떤 프로세스가 있어야 하는가"를 정의하고, CMMI는 "그 프로세스가 얼마나 성숙하게 수행되는가"를 평가(아래에서 상세) |
| 형상관리(Configuration Management) | 12207의 지원생명주기 프로세스 중 핵심 항목 |

## 3. McCabe 순환복잡도 (Cyclomatic Complexity)

**측정공식**
> V(G) = E - N + 2  (E=제어흐름그래프의 엣지수, N=노드수)
> 또는 V(G) = P + 1  (P=프로그램 내 판단노드/조건문의 개수)

**제어흐름 그래프 작성 및 계산 예시**
```
코드: 
1: if (a > 0) {
2:     if (b > 0) { c = 1; }
3:     else { c = 2; }
4: } else { c = 3; }
5: return c;

[제어흐름그래프]
        Start
          │
        (a>0)?──No──→[c=3]──┐
          │Yes               │
        (b>0)?               │
        │Yes  │No            │
      [c=1] [c=2]             │
        │     │               │
        └──┬──┘                │
           │                  │
           └──────────────────┴──→[return c]──→End

노드(N)=7, 엣지(E)=8 → V(G) = 8-7+2 = 3
또는 판단노드(P)=2(if a>0, if b>0) → V(G) = 2+1 = 3
```

**해석**: 복잡도 3 = "이 코드를 100% 테스트하려면 최소 3개의 독립적 실행경로(테스트케이스)가 필요"하다는 의미(테스트케이스 최소개수의 하한선 제시)

**개선기법 연계**: 일반적으로 V(G) ≤ 10을 권장기준으로 삼으며, 초과 시 함수분할·조건문단순화 등 **리팩토링**으로 복잡도 감소 필요

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 결정커버리지(Decision Coverage) | 순환복잡도가 제시하는 "최소경로 수"가 결정커버리지 테스트케이스 설계의 기준이 됨(SW테스트 도메인과 연결) |
| 기술부채 / 코드스멜 | 높은 순환복잡도는 기술부채·코드스멜의 대표적 정량 신호 |
| 제어흐름그래프(Control Flow Graph) | McCabe 계산의 전제가 되는 시각화 도구 |

## 4. 기술부채 4분면 (Technical Debt Quadrant)

**표준 구성요소 (Martin Fowler의 4분면 분류 — "의도성×신중함" 2축)**

| 구분 | 신중한(Deliberate) | 무모한(Reckless) |
|---|---|---|
| **의도적(Intentional)** | "지금은 일정상 이 방법으로 가지만, 나중에 갚을 것을 알고 있다"(전략적 부채) | "디자인할 시간이 없으니 그냥 빠르게 만들자"(무계획적 속도우선) |
| **부주의한(Inadvertent)** | "이제와서 보니 이렇게 했어야 했네"(사후에야 깨달은 더 나은방법, 학습효과) | "객체지향이 뭔지도 모르고 짠 코드"(역량부족으로 인한 무지의 부채) |

**측정공식/계산**: 기술부채를 정량화하는 방법(예: SQALE 방법론) — 부채비율 = (해결에 필요한 예상시간) / (전체 개발에 투입된 시간) × 100%

**개선기법 연계**: 의도적·신중한 부채는 계획된 시점에 리팩토링으로 상환, 무모한·부주의한 부채는 코드리뷰·교육강화로 재발방지

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 코드스멜 | 기술부채가 코드레벨에서 구체적으로 드러나는 징후(바로 다음 키워드) |
| Lehman 진화법칙 | "복잡도 증가의 법칙"이 기술부채가 누적되는 이론적 근거(SW방법론 도메인과 연결) |
| 리팩토링 | 기술부채를 실제로 "상환"하는 행위 |

## 5. 코드스멜 (Code Smell)

**표준 구성요소(대표 유형)**

| 유형 | 징후 |
|---|---|
| **중복코드(Duplicated Code)** | 동일/유사 코드가 여러 곳에 반복 |
| **긴메서드(Long Method)** | 하나의 메서드가 너무 많은 일을 처리(낮은 응집도와 직결) |
| **거대클래스(Large Class)** | 하나의 클래스가 너무 많은 책임을 가짐 |
| **기능편애(Feature Envy)** | 한 클래스가 다른 클래스의 데이터를 지나치게 많이 참조(높은 결합도와 직결) |
| **God Class** | 시스템 전체로직을 한 클래스가 독점 |

**측정공식/계산**: 코드스멜은 정성적 징후라 직접 공식화하기보다, McCabe복잡도·결합도/응집도·중복률(%) 등의 정량지표로 간접 측정

**개선기법 연계(코드스멜별 대응 리팩토링)**
- 중복코드 → Extract Method(공통메서드추출)
- 긴메서드 → Extract Method로 분할
- 거대클래스/God Class → Extract Class(책임분리)
- 기능편애 → Move Method(메서드를 적절한 클래스로 이동)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 결합도/응집도 | 코드스멜의 대부분은 결국 "낮은응집도/높은결합도"의 구체적 증상(아래에서 상세) |
| 정적분석(SAST) | 코드스멜을 자동으로 탐지하는 도구(SonarQube 등)의 핵심 분석기능(SW테스트 도메인과 연결) |

## 6. 리팩토링 (Refactoring)

**표준 구성요소(절차)**
```
①코드스멜 식별 → ②테스트코드 확인/작성(리팩토링 전후 동작이 동일함을 보장)
   → ③소규모 단위로 코드구조 개선(기능변경 없이 구조만 변경)
   → ④테스트 재실행(동일결과 확인) → ⑤반복
```

**측정공식/계산**: 리팩토링 전후 McCabe복잡도·중복률·결합도 지표를 비교해 개선효과를 정량 입증(예: 복잡도 15→6으로 감소)

**개선기법 연계(대표 리팩토링 기법)**: Extract Method(메서드추출), Rename(이름변경으로 가독성향상), Replace Conditional with Polymorphism(조건문을 다형성으로 대체), Inline(불필요한 간접화 제거)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 재공학(Re-engineering) / 역공학(Reverse Engineering) | 리팩토링이 "동일시스템 내 소규모 개선"인 반면, 재공학은 "더 큰 규모의 구조 전환"(137회 기출 비교패턴) |
| TDD | "테스트가 보장된 상태에서만 안전하게 리팩토링한다"는 원칙으로 직결 |
| 디자인패턴(GoF) | 리팩토링의 최종 목표상태가 종종 특정 디자인패턴 형태로 수렴(SW아키텍처 도메인과 연결) |

## 7. CMMI (Capability Maturity Model Integration) — 프로세스영역/성숙도레벨

**표준 구성요소(성숙도 5레벨)**

| 레벨 | 명칭 | 특징 |
|---|---|---|
| Level 1 | 초기(Initial) | 프로세스가 비정형적·임기응변(개인역량 의존) |
| Level 2 | 관리(Managed) | 프로젝트단위로 기본관리(일정·비용·요구사항관리) 수행 |
| Level 3 | 정의(Defined) | **조직표준 프로세스**가 정립되어 전사적으로 일관 적용 |
| Level 4 | 정량적관리(Quantitatively Managed) | 프로세스를 통계적·정량적으로 관리(데이터기반 의사결정) |
| Level 5 | 최적화(Optimizing) | 지속적 프로세스 개선이 조직문화로 정착 |

**프로세스영역(Process Area) 예시**: 요구관리, 프로젝트계획, 프로젝트모니터링·통제, 형상관리(Level2) / 요구개발, 위험관리, 통합프로젝트관리(Level3) 등 레벨별로 요구되는 영역이 누적됨

**측정공식/계산**: 정량적 평가는 아니나, 공식 심사(SCAMPI)를 통해 조직이 각 레벨의 프로세스영역 목표(Specific Goals)를 충족하는지 평가해 레벨 인증

**개선기법 연계**: Level1→2로 가려면 기본 프로젝트관리(일정·요구사항) 체계화, Level2→3로 가려면 조직표준화(개별 프로젝트 관행을 전사표준으로 승격)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| ISO/IEC 12207 | "어떤 프로세스가 필요한가"는 12207, "그 프로세스가 얼마나 성숙한가"는 CMMI(상호보완) |
| 소프트웨어 프로세스(SP) 품질인증 | 국내 CMMI와 유사한 자체 품질인증제도(경영정보시스템 도메인과 연결) |
| 데이터관리 성숙도모델(DMM) | CMMI의 5단계 성숙도 개념을 데이터 영역에 적용한 유사모델(데이터거버넌스 도메인과 연결) |

## 8. 소프트웨어 품질비용 4항목 (Cost of Quality)

**표준 구성요소**

| 분류 | 항목 | 내용 |
|---|---|---|
| **예방비용(Prevention Cost)** | 교육, 표준수립, 프로세스개선 | 결함이 발생하지 않도록 사전에 투자하는 비용 |
| **평가비용(Appraisal Cost)** | 테스트, 리뷰, 검사 | 결함을 찾아내기 위한 검증활동 비용 |
| **내부실패비용(Internal Failure Cost)** | 재작업, 디버깅 | 출시 전 내부에서 발견된 결함을 수정하는 비용 |
| **외부실패비용(External Failure Cost)** | 고객지원, 리콜, 손해배상 | 출시 후 고객에게 발견된 결함으로 인한 비용(가장 큼) |

**측정공식/계산**: 총품질비용 = 예방비용+평가비용+내부실패비용+외부실패비용 — 일반적으로 예방비용 1원 투자가 외부실패비용 수십~수백원을 절감하는 효과(1:10:100 법칙)

**개선기법 연계**: 외부실패비용 비중이 높게 측정되면 → 예방비용(교육·표준화)과 평가비용(테스트강화) 투자를 늘려 전체비용 구조를 좌측(예방/평가)으로 이동시키는 전략

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 테스트 7대원칙(조기테스팅) | 평가비용을 조기에 투입해 내부/외부실패비용을 줄이는 원칙과 직결(SW테스트 도메인과 연결) |
| IT-ROI / CBAM | 품질투자의 경제적 타당성을 분석하는 동일계열 비용효익분석 기법(경영정보시스템·아키텍처 도메인과 연결) |

## 9. 모듈 응집도/결합도 및 Fan-in/Fan-out

**표준 구성요소(Fan-in/Fan-out 정의)**

| 지표 | 정의 |
|---|---|
| **Fan-in** | 해당 모듈을 **호출하는** 상위모듈의 수(많을수록 재사용성은 높으나 변경시 영향범위가 큼) |
| **Fan-out** | 해당 모듈이 **호출하는** 하위모듈의 수(많을수록 복잡도·결합도가 높아짐) |

**측정공식/계산**: 모듈복잡도(Henry-Kafura 지표) = (Fan-in × Fan-out)² — 이 값이 클수록 해당 모듈은 "너무 많이 불리면서, 동시에 너무 많은 것을 호출하는" 구조적 위험모듈

**예시**: 공통 유틸함수 A를 50개 모듈이 호출(Fan-in=50)하면서, A자신도 내부에서 10개 모듈을 호출(Fan-out=10)한다면 → 복잡도 = (50×10)² = 250,000(매우 높음, 구조개선 필요신호)

**개선기법 연계**: Fan-in이 지나치게 높은 공통모듈은 변경에 신중(영향범위 분석 필수), Fan-out이 지나치게 높은 모듈은 책임분리(여러 작은모듈로 쪼개기)로 결합도 완화

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 결합도6단계/응집도7단계 | Fan-in/Fan-out은 결합도를 정량적으로 측정하는 보조지표(SW아키텍처 도메인에서 상세정리됨) |
| God Class(코드스멜) | Fan-out이 극단적으로 높은 모듈이 실제로 God Class 코드스멜의 정량적 증거가 됨 |
| MSA 서비스분할 기준 | Fan-in/Fan-out 분석으로 과도하게 의존성이 집중된 서비스를 식별해 분할 우선순위 결정 |
