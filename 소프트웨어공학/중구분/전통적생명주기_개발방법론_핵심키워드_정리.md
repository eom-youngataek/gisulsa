# 전통적 생명주기 및 개발방법론 핵심 키워드 정리 (정보관리기술사 대비)

> **공통 답안 전개 구조**: 모델 개념/단계 정의 → 적용 기준 → 타 모델과 장단점 비교

---

## 1. SDLC (Software Development Life Cycle, 소프트웨어 생명주기)

**모델 개념/단계 정의**
> 소프트웨어가 기획되어 폐기되기까지의 전체 과정을 단계별로 정의한 일반적 프레임워크 — 모든 개발방법론(폭포수·나선형·애자일 등)은 SDLC의 구체적 구현방식

**표준 단계**: 계획(Planning) → 요구분석(Analysis) → 설계(Design) → 구현(Implementation) → 테스트(Testing) → 배포(Deployment) → 운영·유지보수(Maintenance)

**적용 기준**: SDLC 자체는 만능 모델이 아니라 "단계의 틀"이므로, 프로젝트 특성(규모·요구사항 안정성·리스크 등)에 따라 어떤 생명주기 모델(폭포수형/반복형)로 구체화할지 결정해야 함

**타 모델과 비교**: 이후 정리되는 폭포수·프로토타이핑·나선형·V모델 모두 SDLC의 7단계를 "어떤 순서·반복방식으로 수행하는가"에 따라 분화된 구체모델

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| ISO/IEC 12207 | SDLC 단계를 국제표준으로 공식화한 소프트웨어 생애주기 프로세스 표준 |
| ISMP/ISP | SDLC의 "계획" 단계를 기업의 정보화 전략수립 차원으로 확장한 상위기획 프로세스(경영정보시스템 도메인과 연결) |
| DevOps/CI-CD | SDLC의 구현~운영 단계를 자동화·연속화한 현대적 접근 |
| 형상관리(Configuration Management) | SDLC 전 단계에 걸쳐 산출물 버전을 관리하는 기반 활동 |

## 2. 폭포수 모델 (Waterfall Model)

**모델 개념/단계 정의**
> SDLC의 각 단계(요구분석→설계→구현→테스트→유지보수)를 순차적으로, **이전 단계가 완전히 끝나야 다음 단계로 진행**하는 가장 고전적인 모델(위에서 아래로 흐르는 폭포 모양)

**적용 기준**: 요구사항이 초기에 명확하고 변경이 거의 없는 프로젝트(예: 정부 표준화 시스템, 임베디드 펌웨어처럼 변경비용이 큰 경우)

**타 모델과 비교**

| 구분 | 폭포수 모델 | 애자일 |
|---|---|---|
| 요구사항 변경 대응 | 매우 어려움(앞단계로 되돌아가기 어려움) | 유연(매 스프린트마다 재조정) |
| 산출물 | 단계별 문서가 명확(검증·추적 용이) | 동작하는 소프트웨어 중심(문서 최소화) |
| 적합환경 | 요구사항 안정적, 대규모 정형 프로젝트 | 요구사항 변화 많은 프로젝트 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| V-모델 | 폭포수의 각 개발단계에 대응하는 검증·확인 단계를 명시적으로 추가한 변형(아래 키워드) |
| 방법론 테일러링 | 폭포수 모델을 프로젝트 특성에 맞게 일부 단계를 가감하는 실무 조정기법 |
| 요구사항 추적표(RTM) | 폭포수 모델에서 요구사항-설계-테스트 간 추적을 보장하는 핵심 산출물 |

## 3. 프로토타이핑 모델 (Prototyping)

**모델 개념/단계 정의**
> 요구사항이 불명확할 때, **시제품(프로토타입)을 빠르게 만들어 사용자 피드백**을 받고 이를 반영해 점진적으로 요구사항을 구체화하는 모델

**단계**: 요구사항 수집(초기, 개략적) → 프로토타입 설계·제작 → 사용자 평가 → 피드백 반영(반복) → 요구사항 확정 → 본 개발 진행

**적용 기준**: 사용자가 본인의 요구사항을 명확히 표현하기 어려운 경우(신규 UI/UX 설계, 혁신적 서비스 기획 초기단계)

**타 모델과 비교**

| 구분 | 프로토타이핑 | 폭포수 |
|---|---|---|
| 요구사항 확정시점 | 프로토타입 반복 후 점진적으로 확정 | 초기에 완전 확정 필요 |
| 사용자참여 | 매 반복마다 적극 개입 | 초기 요구분석에만 개입 |
| 위험 | 프로토타입이 그대로 운영시스템화 되어 품질저하 위험(Throwaway 원칙 필요) | 요구사항 오류 발견이 늦음(후반에 발견 시 비용 급증) |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 페르소나 / 사용자스토리 | 프로토타입 제작 전 사용자요구를 구체화하는 보조기법 |
| 애자일 / 스크럼 | 짧은 반복으로 피드백을 받는다는 점에서 프로토타이핑의 사상을 계승·발전 |
| MVP(Minimum Viable Product) | 프로토타이핑의 비즈니스적 확장개념(최소기능제품으로 시장반응 검증) |

## 4. 나선형 모델 (Spiral Model)

**모델 개념/단계 정의**
> 폭포수의 "선형진행"과 프로토타이핑의 "반복" 장점을 결합하면서, 매 반복(나선의 한바퀴)마다 **리스크 분석을 명시적으로 수행**하는 것이 핵심 특징

**단계(나선 1회전 구성)**: ①목표설정 → ②리스크분석(가장 핵심 — 위험요소 식별·평가) → ③개발·검증(프로토타입 제작) → ④계획수립(다음 반복 계획) — 이를 여러 번 반복하며 점차 완성된 시스템으로 수렴

**적용 기준**: 대규모이고 리스크가 크며 불확실성이 높은 프로젝트(신기술 도입, 대형 국방·항공시스템)

**타 모델과 비교**

| 구분 | 나선형 모델 | 프로토타이핑 |
|---|---|---|
| 핵심초점 | 리스크관리(매 반복마다 위험평가) | 요구사항 명확화(사용자피드백) |
| 적합규모 | 대규모, 고위험 프로젝트 | 중소규모, UI/UX 중심 |
| 관리복잡도 | 높음(리스크분석 전문성 필요) | 상대적으로 낮음 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 리스크관리(IT프로젝트) / 부정적위험 대응전략 | 나선형모델의 핵심단계가 그대로 프로젝트관리 도메인의 리스크관리 프로세스와 직결 |
| RUP(Rational Unified Process) | 나선형모델의 반복·점증 철학을 객체지향 개발에 구체화한 방법론 |
| 애자일의 스프린트 | 나선형의 "반복" 개념이 더 짧은 주기로 경량화된 현대적 형태 |

## 5. V-모델

**모델 개념/단계 정의**
> 폭포수 모델의 각 개발단계(좌측 하강선)에 대응하는 **검증(Verification)·확인(Validation) 테스트 단계(우측 상승선)**를 V자 형태로 명시적으로 매칭한 모델 — "개발하면서 동시에 어떻게 테스트할지"를 미리 설계

**단계 매칭(V자 대응관계)**

| 개발단계(좌측) | 대응 테스트단계(우측) |
|---|---|
| 요구사항분석 | 인수테스트(Acceptance Test) |
| 시스템설계 | 시스템테스트(System Test) |
| 아키텍처설계 | 통합테스트(Integration Test) |
| 모듈(상세)설계 | 단위테스트(Unit Test) |

**적용 기준**: 품질·안전성이 매우 중요한 프로젝트(의료기기 SW, 자동차 임베디드, 항공전자) — 테스트를 사후가 아닌 설계단계부터 함께 계획

**타 모델과 비교**: 폭포수와 마찬가지로 선형적·순차적이라 요구사항 변경에는 취약하나, **테스트 누락·지연 위험을 구조적으로 방지**한다는 점에서 폭포수보다 품질보증 측면에서 우수

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 단위/통합/시스템/인수 테스트 | V모델의 각 우측단계가 실제로 대응하는 테스트 유형(소프트웨어 테스트 도메인과 직결) |
| ISO 26262 / ASIL | V모델이 실제로 적용되는 자동차 기능안전 표준의 개발프로세스 요구사항 |
| TDD(테스트주도개발) | "테스트를 먼저 고려한다"는 V모델의 철학을 코드레벨까지 확장한 애자일 기법 |

## 6. 방법론 테일러링 (Tailoring) 4단계 프로세스

**모델 개념/단계 정의**
> 표준방법론(폭포수·애자일 등)을 그대로 적용하지 않고, **프로젝트의 특성(규모·기술·팀역량 등)에 맞게 가감·조정**해 적용하는 활동

**4단계 프로세스**
```
①프로젝트 특성 분석(규모, 기간, 기술복잡도, 팀숙련도, 비즈니스중요도 등 분류기준 평가)
   → ②표준방법론의 단계/활동/산출물 선정(불필요한 활동 제거, 필요한 활동 추가)
   → ③테일러링 수행(실제 적용규칙 확정 — 산출물 간소화, 일부단계 병합 등)
   → ④검증(조정된 방법론이 프로젝트 목표달성에 적합한지 검토, 필요시 재조정)
```

**적용 기준**: 모든 프로젝트가 표준방법론을 100% 그대로 따르면 비효율 발생(소규모 프로젝트에 대규모 문서체계 강제 등) → 테일러링 기준(투입인력, 개발기간, 기술유형) 사전수립 필요

**타 모델과 비교**: 테일러링은 특정 모델이 아니라 "모든 방법론에 적용 가능한 조정활동"이라는 점에서 폭포수/애자일과는 범주가 다름(방법론을 고르는 것이 아니라 고른 방법론을 다듬는 것)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| CBD(컴포넌트기반개발) | 테일러링의 대표 적용대상 — CBD 도입 시 기존 폭포수단계를 재사용·통합 중심으로 조정 |
| SAFe(대규모애자일) | 대규모 조직에서 애자일을 테일러링한 프레임워크의 대표사례 |
| 소프트웨어 개발보안 가이드 | 공공기관 프로젝트에서 보안요구사항에 따라 방법론에 추가되는 테일러링 항목 |

## 7. CBD (Component Based Development, 컴포넌트기반개발)

**모델 개념/단계 정의**
> 시스템을 처음부터 만들지 않고, **재사용 가능한 독립적 컴포넌트(블록)**를 조합·통합해 개발하는 방법론. 컴포넌트는 표준화된 인터페이스로 서로 통신

**단계**: 요구분석 → 컴포넌트 식별(기존 컴포넌트 라이브러리 검토) → 컴포넌트 개발/구매(Make or Buy) → 컴포넌트 조립(Assembly) → 테스트(컴포넌트 자체 + 통합) → 배포

**적용 기준**: 유사 시스템을 반복적으로 구축하는 환경(공통 업무모듈이 많은 공공/금융SI), 재사용성과 유지보수성이 중요한 대형 시스템

**타 모델과 비교**

| 구분 | CBD | 전통적 폭포수(처음부터 개발) |
|---|---|---|
| 개발속도 | 빠름(재사용 컴포넌트 활용) | 느림(전부 신규개발) |
| 품질 | 검증된 컴포넌트 재사용으로 안정적 | 신규개발 부분에서 결함위험 상대적으로 높음 |
| 유지보수 | 컴포넌트 단위 교체 용이 | 시스템 전체 영향분석 필요 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 마이크로서비스아키텍처(MSA) | CBD의 사상을 서비스 단위로 확장한 현대적 아키텍처(소프트웨어아키텍처 영역과 연결) |
| 패키지SW 도입절차 | 컴포넌트를 "구매(Buy)"하는 의사결정을 한다는 점에서 CBD와 직결(다음 키워드) |
| 결합도/응집도 | CBD의 컴포넌트 설계 품질을 평가하는 핵심 기준(낮은결합도·높은응집도) |

## 8. 패키지SW 도입절차

**모델 개념/단계 정의**
> 자체개발(Custom Development) 대신, 이미 상용화된 패키지 소프트웨어(ERP, CRM 등)를 구매·도입하는 방식의 절차

**단계**: ①요구사항 정의 → ②시장조사·제품선정(RFP/BMT 등) → ③Fit-Gap 분석(요구사항과 패키지 기능의 차이 분석) → ④커스터마이징/추가개발(Gap 해소) → ⑤데이터마이그레이션 → ⑥테스트·교육 → ⑦오픈·안정화

**적용 기준**: 업무가 표준화되어 있고 시장에 검증된 솔루션이 존재하는 영역(회계·인사·ERP), 빠른 구축이 필요하거나 자체개발 역량/예산이 부족한 경우

**타 모델과 비교**

| 구분 | 패키지SW 도입 | 자체개발(Custom) |
|---|---|---|
| 구축기간 | 짧음 | 길음 |
| 초기비용 | 라이선스비용 발생하나 전체적으로 절감 가능 | 개발인력비용 全체 부담 |
| 맞춤성 | Fit-Gap의 Gap만큼 제약(과도한 커스터마이징은 향후 업그레이드 어려움) | 완전한 맞춤 가능 |
| 향후 유지보수 | 벤더 의존(라이선스 갱신·기술지원 비용) | 자체 통제 가능 |

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 상용소프트웨어 직접구매제도 / 품질성능평가시험 | 공공기관의 패키지SW 도입 시 적용되는 법적 절차(경영정보시스템 도메인과 연결) |
| CBD | 패키지SW도 일종의 거대한 "구매형 컴포넌트"로 볼 수 있어 CBD의 Make-or-Buy 의사결정과 연계 |
| BMT(Bench Marking Test) | 제품선정 단계에서 여러 패키지 후보의 성능을 비교평가하는 핵심 절차 |

## 9. Lehman의 소프트웨어 진화법칙

**모델 개념/단계 정의**
> Manny Lehman이 제시한, 소프트웨어가 출시된 이후 **시간이 지남에 따라 어떻게 변화(진화)하는지**를 설명하는 8가지 법칙(SDLC가 "최초개발"에 초점을 둔 것과 달리, Lehman법칙은 "유지보수 이후의 장기적 진화"에 초점)

**핵심 법칙(대표 항목)**
1. **지속적 변화의 법칙**: 사용되는 소프트웨어는 계속 변경(수정)되어야 하며, 변경하지 않으면 점점 비효율적/무용해짐
2. **복잡도 증가의 법칬**: 변경이 누적될수록 시스템 복잡도는 계속 증가(누군가 의도적으로 복잡도를 줄이지 않으면)
3. **자기규제의 법칙**: 소프트웨어 진화과정은 통계적으로 일정한 패턴(자기규제 시스템)을 따름
4. **조직적 안정성의 법칙**: 시스템의 생애주기 동안 작업률은 평균적으로 일정하게 유지되는 경향

**적용 기준**: 장기간 운영되는 레거시시스템의 유지보수 전략 수립, 기술부채 관리 정책 수립 시 이론적 근거로 활용

**타 모델과 비교**: SDLC/폭포수/나선형 등은 "개발 프로세스" 모델인 반면, Lehman법칙은 **"이미 개발된 소프트웨어가 운영되며 어떻게 노후화·진화하는지"를 설명하는 이론**이라는 점에서 범주가 다름(개발론 vs 진화론)

**📌 연관 키워드**
| 키워드 | 연결 포인트 |
|---|---|
| 기술부채(Technical Debt) / 코드스멜 | Lehman의 "복잡도 증가 법칙"이 실무에서 구체적으로 나타나는 현상 |
| 리팩토링 | 복잡도 증가법칙에 대응해 복잡도를 의도적으로 낮추는 핵심 실무기법 |
| 재공학(Re-engineering) / 역공학 | Lehman법칙이 설명하는 노후화된 시스템을 다시 구조화하는 대응방법론 |
| 소프트웨어 유지보수 3R | Lehman법칙의 실무적 해법(Reverse·Re-engineering·Restructuring)으로 직접 연결 |
